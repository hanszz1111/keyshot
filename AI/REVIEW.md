## 快速结论

Canny + ControlNet 是值得继续验证的**候选图方案**，但当前“一张源图、一个种子、未公开产品对照图”的证据不足以证明它稳定保留产品形状，更不能支持“85% 改动幅度也不跑形”这种普遍表述。MAE 高只能说明**全图像素变化较大**；现有剪影 IoU 与边缘 IoU 的实现也不足以作为形准验收。Windows 端的真实出图、速度和节点链路可以记为“该机器该样本跑通”，产品保真结论仍是**未验证**。

本轮最优先的工程风险是：实验脚本走 `/api/comfy/submit`，而网页走 `/api/ui/comfy/submit`；前者在 [服务端](../web/server.py) 直接调用 `comfy_submit()`，绕过 `guarded_submit()` 的结构图/模式校验。它不能作为“真实网页受控链路全部验收”的证据，且留下可以跳过受控校验的入口。

## 问题 1｜Canny 锁形的证据可靠吗？

### 1.1 MAE：**有条件能用，但不能用于当前的“材质改变/保形”结论**

[测量脚本](../docs/验收证据-20260927/bug2_cn_measure.py) 对整幅 RGB 图片计算 `mean(abs(output-source))`。深底白模变亮背景、投影或取景轻微移动，都会让 MAE 显著升高。因此 C1 的 74.80 大于 N1 的 56.58，**不能推出 C1 的产品本体材质改变得更彻底**；更不能推出形状更准。它可作为“是否近乎原样返回”的粗筛，例如旧 d0.50 得到 4.55/255 与肉眼近似恒等相符，但也应配合相同尺寸、色彩空间、输出可视核对。

下一轮把“产品本体”和“背景”分别标注或分割，分别统计颜色/纹理变化；同时给出源图与输出的主体占比、尺度/位置变化和伪文字数量。MAE 只列为辅助量，不设单独通过门槛。

### 1.2 形状保留：当前证据**不足**

[指标 JSON](../docs/验收证据-20260927/bug2_cn_metrics.json) 中，N1 剪影 IoU 0.784、C1 仅 0.267，与“C1 明显更保形”的肉眼判断相反；这足以说明**当前 IoU 口径失效**，但并不能反证模型没有变形。C1 的边缘 IoU 0.118 高于 N1 的 0.059，是方向性线索，不是合格门槛：脚本用 PIL `FIND_EDGES > 40` 检测成图边缘，而工作流送入模型的是另一套 Canny 阈值；光照、背景及新纹理都会产生边缘，且该指标没有区分外轮廓与内部细节。C3 的边缘 IoU 0.178 还高于 C1，不能直接把 C1 命名为“保形最优”。

建议先做**小样本人工真值**：选至少 3 类产品（深底白模、成品照片、反光/透明件）× 2 个机位 × 2 个种子，对无 CN 与 Canny 默认各出 1 张，约 24 张；由不知配置的评审者标注“同一产品/重大结构错误/标识错误”。在部分样本上分别标出源图和成图主体掩膜，统一尺寸/机位后算轮廓 IoU、容差边界 F1，以及关键部位（窗口、按键、孔位）的 landmark 位移。相机平移可有限配准，但不能为了提高分数任意缩放或形变对齐。

### 1.3 漏掉的失败模式与实验混杂

- [对照脚本](../docs/验收证据-20260927/bug2_cn_verify.py) 的 C3 不只改变 `denoise`：Canny 阈值从 `0.06/0.18` 变为 `0.04/0.14`，`end_percent` 从 `0.85` 变为 `0.90`。因此 C3 与 C1 的差异**不能单独归因于 denoise**。下一轮须单变量成对试验，或明确列出全部变量。
- Canny 会把源图已有的杂乱边缘、文字、水印、阴影也作为条件；即使外轮廓接近，丝印、孔位和细小形体仍可能错。需要专门统计这些失败，而不只问“整体像不像”。
- 只用一张源图、一个种子，无法评估跨产品、机位、材料和随机种子的稳定性；现有 [RESULT.md](RESULT.md) 已诚实承认这一点。建议把“推荐配置”改为“当前样本的待复测配置”。

## 问题 2｜IoU 错在哪里、怎么改？

**归因部分成立，但不能排除真实跑形。** [白模复算脚本](../docs/验收证据-20260927/iou_recheck.py) 用 `alpha.png` 的 RGB 灰度阈值得到白模掩膜，用四角均色距离阈值得到 AI 成图掩膜。后者在渐变背景、投影、反光和亮背景下会把背景误分为产品；两端都复算出 0.249，只证明同一算法被一致执行，不证明前景掩膜正确。另一个可能原因仍是构图/尺度/产品几何真有变化，不能把低分全归咎于背景。

修正顺序：先人工标注少量成图主体掩膜作真值，验证自动分割的精确率/召回率；白模端继续使用已确认的 RGB 掩膜；再在相同机位、相同尺寸和**有约束的**平移对齐下计算主体掩膜 IoU 与边界 F1。对透明件、细杆、阴影另记专项错误。自动分割未过关前，暂时不要展示一个统一的“形准通过/失败”数字。

`IoU ≥ 0.90` 目前没有标定依据，**不建议继续作为唯一硬门槛**；不能反过来把门槛调低来宣告成功。先收集人工接受/拒绝样本，画出各指标分布，确定不同产品类别的可用阈值，并继续保留人工核对关键结构与标识。对于最终交付，关键孔位/标识错误应“一票否决”，不被高整体 IoU 抵消。

## 问题 3｜这条路线还值不值得继续？

**值得保留为受限候选图工具，不宜直接铺到 2000 SKU 的量产主图。** 白模出图与图片改图的本机速度已有一机一批的运行记录，但“能生成”不等于“可交付”。[DECISIONS.md](DECISIONS.md) 的 ADR-015“产品本体真渲染、AI 做背景/氛围”与候选图用途并不冲突：可以让 img2img 帮设计师快速探索材质/灯光，再由确定性渲染和后期回贴交付产品本体。

下一步不是再堆一个大模型，而是做 10–20 SKU 的小试点：同一产品分别走现有 KeyShot+PS、真渲染+AI 背景、当前 Canny 候选图三条路线，记录人工工时、返工次数、合格率、关键结构/标识错误、GPU 成本和客户是否接受。若混合路线没有节省总工时，就不该因单张生成快而扩大投入。托管 ComfyUI 与公共 API 的价格、能力、许可属于会变化的外部条件，[DECISIONS.md](DECISIONS.md) 中的旧报价不能直接用作今天的采购决策，需另行核验。

## 其他发现｜按优先级交给 Windows 执行方

1. **P1：受控提交存在旁路。** [服务端](../web/server.py) 同时提供 `/api/comfy/submit`（直接执行）与 `/api/ui/comfy/submit`（调用 `guarded_submit`）。[端到端脚本](../docs/验收证据-20260927/bug2_e2e_cn.py) 用的是前者。建议让所有提交路径走同一个校验入口，补“缺深度/缺 mode/混入结构图/源图不存在”的 API 测试，再用网页实际路径做 1 张验收。不要靠只改测试说明来掩盖旁路。
2. **P1：端到端脚本可能选错任务。** 它提交后从 `/api/tasks` 取第一个 `pending` 且 `view=photo` 的任务，并非本次插入任务的确定 ID；队列里有旧任务时会误把别人的任务当成测试对象。应让创建接口返回插入 ID，或用唯一测试标记精确查找并断言 payload。
3. **P1：强断言应降级。** 根过程文档、[MASTER_CONTEXT.md](MASTER_CONTEXT.md) 和 [DECISIONS.md](DECISIONS.md) 对“Canny 锁住形状”“改动 85% 不跑形”的措辞，比现有证据强。建议在下一次代码/实验修复的变更记录中改为“该样本肉眼观察较接近，跨 SKU 未验证”。“IoU 主因已确定”也应改成“背景分割是明确缺陷，真实形变尚未排除”。
4. **P2：公开仓库脱敏复核。** `.gitignore` 排除了产品图和输出，但 Markdown/实验脚本仍包含真实 SKU、图片文件名及本机绝对路径。提交下一轮证据前，对客户/产品敏感信息做一次文本扫描；需要分享对照图时使用用户批准的私有渠道。
5. **P2：文档链接缺件。** 远端根目录的 README/过程文档提到了 `WINDOWS-AGENT-执行与验收.md`，但本次复审基线的 GitHub `main` 根目录并无该文件（Contents API 返回 404）。Windows 端应确认是故意不入仓还是漏传；若要公开上传，先按 v2.4 实测状态更新其内容并脱敏，再修正链接或补文件。

## 我不同意的地方

- 不同意用 C1 的**全图 MAE 最高**和一次肉眼观察，推出“材质彻底换新且形状已锁住”。这只能作为值得继续试验的假设。
- 不同意把浏览器/独立脚本复算同一个 IoU 值当成指标有效性证明。它验证实现一致，不验证掩膜真值。
- 不同意“C3 只改变 denoise”的隐含叙述；对照脚本实际同时改了阈值与控制结束点。

## 我无法判断的地方

- 产品源图、C1/N1 对照图和真实 CAD/白模并未进入公开仓库；无法独立确认窗口、分模线、滚花目镜是否真的保持，或是否有局部臆造。
- Windows 的 GPU 峰值、28 秒耗时和服务持久化日志只有执行方文字/文本索引；Mac 无法复测，应保留“Windows 执行方报告”的归属。
- KeyShot+PS 基线人工工时、产品最终合格率、客户验收标准与 2000 SKU 的分布未知，无法给出可信 ROI 数值。

## 给下一轮 R2 的最小行动

Windows 先修统一提交校验与测试脚本选错任务风险；随后做小规模成对试验，按“主体材质变化、外轮廓、关键部位、伪文字”分别计分。更新 `RESULT.md` 时列原始证据、代码 commit、样本数和失败样本；再由 Mac 针对新 commit 复审。R1 的结论为**需修订**，不是产品方案被否定，也不是 Windows 实测结果被抹消。

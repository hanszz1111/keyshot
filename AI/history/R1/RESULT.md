## 1. 缺陷 ① 白模机位角度全部相同

### 1.1 排查过程（含被我排除的假设）

| 步骤 | 假设 | 检查方式 | 结果 |
|---|---|---|---|
| 1 | 模型没导入成功 | 调 `/api/assets` | ❌ 排除：6 个模型全部在列 |
| 2 | Blender 不可用 | 调 `/api/ui/info.blender` | ❌ 排除：`blender = true`，v4.5.0 |
| 3 | STL 读不了 | 实测单次出 pass | ❌ 排除：3.58 秒成功 |
| 4 | **各机位参数是否真的不同** | 读调用方传参与脚本默认值 | ✅ **命中** |

### 1.2 根因（原始代码对比）

**调用方**（`web/server.py`）只传三个参数：

```
--model <3d文件> --sku <产品编号> --view <机位>
```

**脚本**（`scripts/blender_pass.py`）的参数定义：

```python
# 修复前
ap.add_argument("--azimuth",   type=float, default=0.0)
ap.add_argument("--elevation", type=float, default=12.0)
```

→ **五个机位全部使用默认值 `(0, 12)`**，取景完全相同。
表现：「正面」渲染成瞄准器端面/俯视管状视图；三个 3/4 视角完全没有转弯。

### 1.3 修复

新增机位查表，参数默认改为 `None`：

```python
VIEW_ANGLES = {
    "front":         (0.0,    8.0),
    "3q4_left":      (-45.0, 15.0),
    "3q4_right":     (45.0,  15.0),
    "side":          (90.0,   8.0),
    "top":           (0.0,   80.0),
    "detail_keypad": (-30.0, 35.0),
    "detail_window": (30.0,  30.0),
}

default_az, default_el = VIEW_ANGLES.get(view, (0.0, 8.0))
if args.azimuth   is None: args.azimuth   = default_az
if args.elevation is None: args.elevation = default_el
```

### 1.4 验证证据

逐机位打印实际生效角度，确认互不相同：

| 机位 | 方位角 | 仰角 | 出图表现 |
|---|---|---|---|
| front | 0 | 8 | 正面 |
| 3q4_left | -45 | 15 | 左前 3/4 |
| 3q4_right | 45 | 15 | 右前 3/4 |
| **side** | **90** | **8** | ✅ 正确侧面轮廓（滚花目镜 + 完整机身） |
| top | 0 | 80 | 俯视 |

**关键判据**：修复前 `side` 的 clay 图与 `front` 几乎相同；修复后 `side` 能清晰看到
侧面的滚花目镜与完整机身轮廓。

- 尺寸 1221×786，深色背景上的**白模/灰模**
- 直方图均值 **134.5**，标准差 **99.0**

### 2.2 量化「没渲染」（原始测量）

对 #260 的产物与源图逐像素比较：

| 项 | 源图 | 产物 | 差异 |
|---|---|---|---|
| 直方图均值 | 134.5 | 134.6 | +0.1 |
| 直方图标准差 | 99.0 | 97.4 | −1.6 |
| **平均绝对像素差** | — | — | **4.55 / 255** |

→ 输出与输入几乎完全相同，**等于恒等变换**。

### 2.3 参数扫描实验（找出问题范围）

脚本：`docs/验收证据-20260927/bug2_img2img_lab.py`

| 配置 | 平均像素差 | 观察 |
|---|---|---|
| A 8步 / d0.50 / cfg 2.0 | **4.55** | 无变化 |
| B 8步 / d0.75 / cfg 2.0 | **43.60** | 有渲染，但**臆造出一把雷达枪** |
| C 20步 / d0.60 / cfg 3.0 | 8.36 | 仍不足 |
| D 30步 / d0.70 / cfg 3.0 | 22.18 | 有渲染，但臆造水印 "Stuiio Product Deⅵer" |
| E 12步 / d0.65 / cfg 3.0 | 13.78 | 中等 |

**关键推论**：这是「不渲染 ↔ 臆造别的产品」的二选一困境，
根源是**裸 img2img 没有任何形状约束**。

### 2.4 计算有效步数（解释为什么 d0.50 没效果）

底模 `RealVisXL_V5.0_Lightning_fp16` 是**蒸馏快速版，训练时就只有 8 步**。

```
有效步数 = round(总步数 × denoise)
d0.50 → round(8 × 0.50) = 4 步
```

DPM++ SDE 采样器在 4 步内无法收敛出有意义的图像。

### 2.5 ★ Canny + ControlNet 对照实验（核心证据）

**实验脚本**：`docs/验收证据-20260927/bug2_cn_verify.py`
**量化脚本**：`docs/验收证据-20260927/bug2_cn_measure.py`
**对照图**：`docs/验收证据-20260927/bug2_lab/bug2_cn_sheet.png`

**实验条件**：同一源图、同一种子（20260927）、同尺寸（1024×656）、同提示词。
唯一变量是 ControlNet 的接入与强度。

| 配置 | 平均像素差<br>(MAE) | 剪影 IoU | 边缘 IoU | 肉眼观察 |
|---|---|---|---|---|
| N1 无 CN / 12步 / d0.85 | 56.58 | 0.784 | 0.059 | ❌ 形状全丢；臆造 "GRONAL" 标牌、水印、"Sludo W" |
| **C1 CN 0.75 / 12步 / d0.85** | **74.80** | 0.267 | 0.118 | ✅ **材质彻底换新（银金属+深灰面板）+ 形状与白模一致** |
| C2 CN 1.00 / 12步 / d0.85 | 65.22 | 0.320 | 0.133 | 偏保守，改动略不足 |
| C3 CN 0.75 / 12步 / d0.70 | 41.55 | 0.822 | 0.178 | 改动不足 |

**⚠️ 我对这份数据的两点自我质疑**（请你重点审查）：

1. **剪影 IoU 数值不可信**：C1/C2 的 IoU（0.267 / 0.320）竟然**低于**无 CN 的 N1（0.784），
   但肉眼看 C1 形状保留得明显更好。原因是源图是**深色底白模**，N1/C1 的成图都变成了亮背景，
   我的自适应阈值把大片亮背景算作前景。**这个矛盾说明该指标在这个场景下失效。**
2. **C1 的 MAE（74.80）高于 N1（56.58）**，我把它解释为「改动更彻底」。
   但更可能是背景整体变亮贡献了大部分差值 —— **MAE 混淆了「背景变化」与「本体重渲染」**。

### 2.6 端到端验证（走真实接口，非实验脚本）

第一次尝试**失败并产出了一个错误结果**，过程如下：

**失败经过**：我的验证脚本把参数放在任务对象**顶层**，而接口实际读的是嵌套的 `payload` 字段
→ `payload` 存成空对象 → 模式标记丢失 → 服务端**静默降级为纯文生图** → **产出一张人像**。

产物已隔离：`_隔离区/20260927_v24/bug2_lab_mislabeled/E2E_误提交_txt2img人像.png`

**这个失败反而暴露了一个真实缺陷**：静默降级会产出与产品毫无关系的图，而界面没有任何提示。
→ 已修复为**显式报错**（见 ADR-010）。

**修正后的端到端结果**：

| 项 | 值 |
|---|---|
| 链路 | `POST /api/tasks` → `POST /api/comfy/submit` → `GET /api/comfy/poll` |
| 返回模式 | **`img2img`** ✅ |
| 工作流节点数 | **13**（含完整 ControlNet 链） |
| 实际注入参数 | Canny `low 0.06 / high 0.18`；CN `strength 0.75`、`end_percent 0.85`；KSampler `steps 12 / cfg 3.0 / denoise 0.95` |
| 耗时 | 约 **28 秒** |
| 产物 | `outputs/stl_2/photo/ai_render_00027_.png` |

**肉眼确认**：保留大窗口梯形轮廓、下部格栅弧线、机身分模线、滚花目镜、顶部红色按键；
材质变为哑光黑工程塑料 + 银金属滚花目镜；**无臆造 LOGO**。

> 注：这次实际 denoise 用的是 0.95（复用了用户已提交的任务），比对照实验的 0.85 更激进，
> 但因为有 Canny 锁形，形状仍然保住了。这算是一个**意外的额外数据点**。

### 2.7 修复方案汇总

| 改动 | 内容 |
|---|---|
| 工作流 | `comfy_workflow_sdxl_img2img.json` 从 7 节点 → **13 节点**，接入 Canny + ControlNet Union |
| 参数基线 | 新增 `img2img` 块：`steps 12 / cfg 3.0 / dpmpp_sde / karras / denoise 0.55–0.95（默认 0.85）` |
| 前端 | 新增白模检测（96×96 画布采样）→ 命中则改写提示词 + 追加负面词 |
| 前端 | 滑块范围由 `35–90` 改为 `55–95`，默认 `85%`（**此前前后端范围不一致，滑到 35–50% 会被服务端拒绝**） |

**白模检测判据**（本轮我自定的）：
```
darkRatio > 0.25 && brightRatio > 0.10 && satMean < 0.12
```
**这个判据是我凭直觉定的，没有做系统性验证。** 请审查其合理性。

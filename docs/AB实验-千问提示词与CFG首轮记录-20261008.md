## 二、决定性结果：CFG=1 时负面提示词**零作用**（已证实，非推测）

方案文档当时只能引官方说明推断「CFG=1 时负面词不参与生成」。本轮**实测证实**：

| 对比 | 唯一变量 | 结果 |
|---|---|---|
| **C0（CFG1.0 无负面词） vs C1（CFG1.0 带负面词）** | 负面词 | **4/4 组合像素完全相同**（front/3q4_left × 种子43/1234） |
| C2（CFG1.5 带负面词） vs C3（CFG1.5 无负面词） | 负面词 | **4/4 像素不同**，MAE 1.69–2.57 → 负面词生效 |

**即：在默认配置（CFG=1.0）下，往千问的 `negative` 里写任何东西，对画面没有任何影响。**
此前放进 `negative` 的「不添孔 / 不造文字 / 不脏背景」等约束**全部等于没写**。

这条实测同时说明：想靠负面词约束千问，**唯一有效的杠杆是提高 CFG**，而不是把负面词写得更长。

> ⚠️ 判读陷阱：C0 与 C1 的**文件 SHA256 不同**，但**像素 100% 相同**。
> 原因是 ComfyUI 的 `SaveImage` 会把整个提示词写进 PNG 的 `prompt` 元数据。
> **比文件哈希会得出「两者有差异」的错误结论** —— 必须比解码后的像素。

## 三、提示词改写（v3.29）的实际效应量

三条臂（`front` 处提示词字符数）：

| 臂 | 内容 | 字符数 | 负面词 |
|---|---|---|---|
| A | 旧提示词（v3.29 前，长句式） | 956 | 458 |
| B0 | 新提示词（短指令，**无**护栏） | 630 | 458 |
| B | 新提示词 + CFG=1 正向护栏（= 线上默认） | **1053** | 458 |

**结果：臂间差异显著小于采样噪声。**

- 臂间 MAE 均值 **3.03** ｜ 种子噪声 MAE 均值 **11.88** ｜ **比值 0.255**
- 即：同一臂只换一个种子造成的画面变化，是「换整套提示词」的**约 4 倍**

逐对比（MAE / 差异像素占比）：

| 机位 | 种子 | A→B0（只改文案） | B0→B（只加护栏） |
|---|---|---|---|
| front | 43 | 2.25 / 0.9% | 0.91 / 0.5% |
| front | 1234 | 2.21 / 1.0% | 1.21 / 0.7% |
| 3q4_left | 43 | **8.10 / 13.0%** | 2.18 / 2.6% |
| 3q4_left | 1234 | 2.78 / 1.2% | 1.22 / 0.3% |

唯一较大的 3q4_left/种子43 在种子 1234 上只剩 1.2% —— 说明它**更像采样起伏，不是稳定效应**。

**一个值得注意的副作用**：v3.29 的初衷之一是缩短提示词，基础文案确实从 956 降到 630（−34%），
但为补偿失效的负面词而追加的正向护栏有 423 字符，**最终提示词反而比改动前更长**（1053 > 956）。

| 配置 | front（1 参考） | 3q4_left（2 参考） |
|---|---|---|
| CFG 1.0 | 22.1 s | 34.2 s |

## 五、本次踩到并修掉的方法学陷阱

这些都是「会让人得出错误结论」的坑，已写进脚本注释：

1. **比文件哈希 ≠ 比像素**（见 §二）。PNG 元数据含提示词，像素相同也会哈希不同。
2. **MAE 没有参照尺度就没有意义**。「A 与 B 差 2.2」是好是坏，必须与「同臂换种子的差异」比。
   这也是本脚本把「种子噪声基线」作为固定输出的原因。
3. **`comfy_upload()` 只认 `assets/` 下的素材**，解析不了 `outputs/` 下的锚点产物 →
   关联机位的第二参考上传会报「找不到素材」。已改为直接上传任意本地文件。
4. **缓存格子会丢失记录**：早先版本对缓存命中直接返回，导致重跑后的事实卡**反而比首跑少了
   参数与耗时**。已改为「先算参数再查缓存」，并从既有事实卡继承历史耗时。
5. **避免重复登记的假象**：脚本不写 `config/tasks.db`，产物全在 `outputs/_AB实验/`，
   不会与控制台的真实任务混在一起。

## 六、本文件**不宣称**什么

- **不给画质结论。** 0–2 分（结构与方向 / CMF 归属 / 材料可信度 / 背景光照 / 视觉主次）
  必须由人按 `打分表-*.csv` 逐张评。MAE 只说明「改了多少像素」，不说明「变好还是变坏」。

  八面全量、其他 SKU、更高预算/步数均未测。

- **CFG 不建议改默认。** 实测只说明「CFG>1 时负面词才生效」，未证明 CFG=1.5 的画质更好

# 第二轮：文本编码器精度（4bit vs INT8）— 2026-10-08 下午

## 背景与假设

社区 Qwen 工作流与**官方 ComfyUI 模板**用的文本编码器都是
`qwen3vl_8b_int8_convrot.safetensors`（**INT8**），而本项目为省显存一直用
`qwen3vl_8b_w4a8.safetensors`（**4bit**）。

结合第一轮的发现（换整套提示词对画面的作用**小于**换一个种子，比值 0.255），
产生一个自然假设：

> **假设**：4bit 文本编码器削弱了模型对指令的跟随能力，
> 换回 INT8 后「提示词应当重新变得有效」。

## 实验设计（2×2 交互）

| 臂 | 文本编码器 | 提示词 |
|---|---|---|
| `W4A8-A` | w4a8（4bit，项目现状） | 旧长句式 |
| `W4A8-B0` | w4a8 | 新短指令 |
| `INT8-A` | **int8_convrot（官方模板默认）** | 旧长句式 |
| `INT8-B0` | **int8_convrot** | 新短指令 |

四条臂一律 **CFG=1.0、不加护栏、负面词全开** —— 使「提示词」这一维只剩文案差异。
`SKU / 输入图 / 机位 / 种子 / 分辨率预算 / 步数` 与第一轮完全相同。
`SKU=AI渲染1`、`front`+`3q4_left`、种子 `43`+`1234`、768 预算、25 步，共 **16 格，全部成功**。

新权重已下载并校验：`qwen3vl_8b_int8_convrot.safetensors`，
sha256 `8bfd0f6e12abf2d2d697ecc888e5e90b0d6741d6708f05799f53afa560452e8f`
**与官方 LFS oid 逐字节一致**（9,350,798,360 字节，ModelScope 40.7 MB/s）。

## 结果：假设**没有被支持**

MAE 明细（越大 = 改了多少像素）：

| 机位 | 种子 | 只换 CLIP（同提示词） | | 只换提示词（同 CLIP） | |
|---|---|---|---|---|---|
| | | A 下 | B0 下 | W4A8 下 | INT8 下 |
| front | 43 | 2.73 | 2.01 | 2.25 | 3.11 |
| front | 1234 | 1.38 | 1.59 | 2.21 | 2.49 |
| 3q4_left | 43 | 7.33 | 3.20 | 8.10 | 3.82 |
| 3q4_left | 1234 | 2.46 | 2.63 | 2.78 | 2.55 |

**分组均值**：

| 量 | MAE 均值 |
|---|---|
| 只换 CLIP（同提示词） | 3.48 / 2.36 |
| **只换提示词：W4A8 下** | **3.83** |
| **只换提示词：INT8 下** | **2.99** |
| 种子噪声基线 | **11.71** |

**交互比 = 2.99 / 3.83 = 0.78（< 1）**。
即换成 INT8 后，提示词对画面的作用**没有变大，反而略小**（幅度远在噪声内）。
所有臂间差异都远低于种子噪声 11.71。

> **结论：假设不成立 —— 4bit 文本编码器不是「提示词不生效」的原因。**
> 这排除了一个看起来合理的解释，也意味着「继续换文本编码器来救提示词」这条路可以停了。

## 代价（实测）

| 项 | W4A8 | INT8 |
|---|---|---|
| 文件大小 | 5.88 GiB | **8.71 GiB**（+2.83 GiB） |
| front 单张耗时（均值） | 26.1 s | **33.1 s（+27%）** |
| 3q4_left 单张耗时（均值） | 52.3 s | 52.2 s（持平，双参考占主导） |
| 全程显存峰值 | — | **7805 / 8187 MiB = 95.3%** |

显存峰值 95.3% 是**真实风险**：本次没 OOM，但已几乎没有余量。
在 8GB 卡上换 INT8 属于「拿 27% 的速度和几乎全部显存余量，换一个没测出收益的变化」。

## ★ 附带得到一个强证据：实验可复现

第一轮 `prompt` 预设与本轮 `clip` 预设里，**「A」臂的参数完全相同**
（同提示词、同 CFG、同护栏、同 CLIP = 生产默认 w4a8）。
两轮是**相隔数小时、独立进程**跑的，结果：

| 对比 | 结果 |
|---|---|
| prompt/A vs clip/W4A8-A @ front s43 | **像素完全相同** |
| prompt/A vs clip/W4A8-A @ front s1234 | **像素完全相同** |
| prompt/A vs clip/W4A8-A @ 3q4_left s43 | **像素完全相同** |
| prompt/A vs clip/W4A8-A @ 3q4_left s1234 | **像素完全相同** |

4/4 逐像素一致。这同时说明两件事：
① 工具链是**确定性**的，同参数必然同像素；
② `payload["clip_name"]` 的覆盖接线与「显式写 w4a8 == 生产默认」等价，接线没接错。

## 视觉观察（非结论）

四臂并排看**几乎一致**；`3q4_left` 的背景出现**斑驳纹理**，
而这正与第一轮「CFG=1 时负面提示词零作用」相符 ——
那些「不脏背景」的负面约束本来就等于没写。

⚠️ 但 MAE 只说明「改了多少像素」，**不说明指令跟随是否变好**。
「INT8 是否让提示词在语义上更被遵守」仍需人工 0–2 分评分，本次**未做**。

## 本次未验证

1. **没有人工评分**，画质/语义跟随的优劣未判定。
2. 只测了 1 个 SKU、1 个分辨率预算（768）、1 个步数（25）、2 机位、2 种子。
3. 没测 INT8 在更高分辨率下的表现（显存余量已不足）。
4. 没有测「INT8 + 更大 resolution」的组合。
5. 未测 BF16 文本编码器（16.33 GiB，8GB 卡不现实）。

## 建议

- **暂不切换默认 CLIP**：本次没测出收益，代价却是 +27% 耗时与 95.3% 显存占用。
  保留 `w4a8`，把「换文本编码器」从待办里划掉。
- 若做人工评分后发现 INT8 的画质确实更好，再单独评估是否值得这个代价。
- 「让提示词更有效」的方向应转向**采样侧**（第一轮已证明 CFG>1 时负面词才生效），
  而不是继续在文本编码器上找原因。

## P2：shift 仅作 A/B（内置 0.69 vs 显式 3.1）

实现方式：在**实验脚本内**把 `ModelSamplingAuraFlow` 插到 UNETLoader 与 KSampler 之间，
生产工作流 `config/comfy_workflow_qwen21_edit.json` **一行未改**。8 格全部成功。

### 结果：shift 是**真实但很弱**的杠杆

| 机位 | 种子 | 臂间 MAE | 差异像素 | 像素完全相同 |
|---|---|---|---|---|
| front | 43 | 2.75 | 0.6% | 否 |
| front | 1234 | 2.23 | 0.7% | 否 |
| 3q4_left | 43 | 4.31 | 5.0% | 否 |
| **3q4_left** | **1234** | **0.00** | 0.0% | **是** |

臂间 MAE 均值 **2.32** ｜ 种子噪声 **12.30** ｜ 比值 **0.189**。
即：把 σ 中段从 0.4278 改到 0.7706（+80%）之后，**画面变化仍小于换一个种子**。

### ★ 但先做了「补丁是否真的生效」的诊断

「有一格像素完全相同」本身就值得怀疑，所以补了一条**极端臂 `shift=10`**（front / 种子 43）：

| 对比 | MAE |
|---|---|
| 内置 0.69 → 3.1 | 2.75 |
| 内置 0.69 → **10** | **7.10** |
| 3.1 → 10 | 4.57 |

效应随偏离幅度放大 → **补丁确实进入了采样**，不是接线问题。
（源码侧也已确认：`ModelSamplingAuraFlow.patch_aura` 走
`add_object_patch("model_sampling", …)`，KSampler 取 sigma 时用的就是它。）

### 结论

**保留内置 0.69，不采用 3.1。** 理由：没有观察到稳定收益，代价却已明确（σ 更偏高噪声、
极端值下画面变化更大）。这也**修正了我方上一轮文档里的预测** ——
当时按 σ 差异把这条列为「最值得先做」，实测表明 **σ 的数值差异并不能换算成同等量级的画面差异**。

> 附带一条实现坑（我方踩到并已修）：补丁节点 id 最初取 `max+1 = 9`，
> 而关联机位稍后也用 **9** 号节点放第二参考图 → 补丁被覆盖，
> KSampler 的 `model` 接到了 IMAGE → **HTTP 400**，表现为「front 成功、3q4_left 全失败」。
> 已改为从 900 起分配 id。**这类「只在 2 参考路径上炸」的 bug 很容易被误判成模型问题。**

## P3：8GB cache / 分辨率（`QwenImage21Cache`）

三臂：不插节点 / `device=cpu` / `device=cpu, dtype=int8`。先固定 768。12 格全部成功。

### ★ 结果：`device=cpu` 是**明确的正收益**

| 臂 | front 均值 | 3q4_left 均值 |
|---|---|---|
| 不插节点（现状） | 21.2 s | **42.4 s** |
| `device=cpu` | 20.1 s | **25.4 s** |
| `device=cpu, dtype=int8` | 20.2 s | 25.2 s |

**关联机位 42.4 s → 25.4 s，约 −40%**（单参考的 front 基本不变）。

而且 `device=cpu` 与「不插节点」的输出**逐像素完全相同**（4/4，MAE 0.00）——
**零画质代价**。

`dtype=int8` 则**不建议**：与 `default` 相比输出不再相同（MAE 0.28–0.93），
而耗时没有进一步下降（25.2 vs 25.4 s）。

### 但显存**没有**降下来

全程峰值 **7646 MiB（93.4%）**，与此前几轮的 7694 / 7805 MiB 基本同一水平。
**说明 KV cache 不是显存占用的大头**（大头是 6.76 GiB 的 UNet + 5.88 GiB 的文本编码器）。
→ **P3 的前提「腾出显存以提高 resolution」没有得到支持**；
它带来的是**速度**，不是**分辨率空间**。

### 结论

- **采用 `QwenImage21Cache(device="cpu")`**：画面不变、关联机位快约 40%。这是本轮唯一的净收益。
- **不采用 `dtype=int8`**：无额外收益且引入微小差异。
- **不据此开放更高 `resolution`**：显存峰值没变，8GB 的余量问题没有解决。

## ★ 顺带得到一个跨实验的强信号

把四个实验（`prompt` / `cfg` / `clip` / `shift`）里**同一格子**的输出按
「解码后像素的 SHA256」分组，发现：

| 机位 / 种子 | 像素完全相同的臂 |
|---|---|
| front / 43 | `prompt/B0`、`cfg/C0`（删掉全部负面词）、`cfg/C1`、`clip/W4A8-B0`、`shift/S-builtin` —— **5 个** |
| front / 1234 | 同上 **5 个** |
| 3q4_left / 43 | 同上 **5 个** |
| 3q4_left / 1234 | 上述 5 个 **+ `shift/S-3.1`** —— **6 个** |

也就是说：**在 CFG=1 + w4a8 下，「新短提示词」这一版文案，无论去掉全部负面词、
无论插不插 shift 覆盖、无论是在哪一轮实验里跑的，都产出同一张图。**

而确实改变了输出的是：**旧长提示词**（`prompt/A` 与 `clip/W4A8-A` 相同且自洽）、
**正向护栏**（`prompt/B`）、**CFG=1.5**、**INT8 文本编码器**。

这比「负面词无效」更强：它说明该配置下的**有效条件主要来自输入图**，
文本只在一个较粗的层次上起作用。方向上支持执行文档 P1（输入图决定上限）的排序。

⚠️ 但这只是**同一 SKU、同一机位、两个种子**上的观察，不足以外推。

# 补记：目视对比后，对 INT8 文本编码器的建议需要修正 — 2026-10-08

用户要求「看图片判断 int8 的效果是否更好」。为让差异可见，新增工具
`scripts/ab_visual_compare.py`（两臂并排 + **差异放大 + 红色标出改动像素**），
并另外做了「**与白模真实几何并排**的局部放大图」。

## 先澄清：本轮涉及**两个不同的 int8**

| 对象 | 是什么 | 结论 |
|---|---|---|
| **文本编码器** `qwen3vl_8b_int8_convrot` | 换掉 4bit 的 w4a8 | **画面有可见变化**，见下 |
| **KV cache `dtype="int8"`** | `QwenImage21Cache` 的存储精度 | **不建议**：MAE 0.28–0.93、改动像素 ≤1.2%，且**没有额外提速**（25.2 vs 25.4 s） |

## 差异集中在哪里（不是背景）

`ab_visual_compare.py` 的第三列显示：改动像素**集中在产品轮廓、镜头环与标贴**，
而不是背景。这一点**修正了我此前的担心** —— 我曾说「MAE 全图平均可能被背景主导」，
实测方向相反：差异恰恰落在结构上。

## ★ 与白模并排放大后，INT8 看起来**更贴近真实几何**

同一局部（front / 种子 43，放大 2×）四联对比：

| 图 | 观察 |
|---|---|
| ① 白模 clay（真实几何） | 镜头环是**外圈 + 明显倒角/台阶 + 内圆盘**，机身有细砂纹 |
| ② CMF 引导图（实际输入） | 平盘色块，几乎看不出台阶 |
| ③ **W4A8（现状）** | 环面偏平、内圆弱，**机身可见细密斑点噪声** |
| ④ **INT8** | **倒角高光与内圆盘边缘更明确**，平坦区域**更干净、斑点更少** |

即：在这一处细节上，**INT8 的结构与洁净度都更像 ① 而不是像 ③**。

## 因此修正上一轮的建议

第二轮我写的是「**维持 w4a8**」，理由是「没测出收益、代价 +27% 耗时与 95.3% 显存」。
现在需要**补充限定**：

- 第二轮测的是「**INT8 会不会让提示词更有效**」→ 答案是**不会**（交互比 0.78）。
  这个结论**不变**。
- 但「**画面是否更好**」当时明确标注为**未做人工评分**。现在的目视对比正是这块缺失的证据，
  而它**指向另一个方向**：INT8 至少在镜头环/表面洁净度上**看起来更接近真实几何**。

→ **建议改为：不把 w4a8 当作已定论的默认**，而是把「INT8 文本编码器」列入
**待人工 0–2 分评分**的候选项，按 [最佳效果执行文档](Qwen-Image-2.1-最佳效果执行文档-20261008.md)
的验收口径（结构 / 机位 / CMF / 工艺光影 / 背景洁净，结构或 CMF 得 0 直接淘汰）判定。

## 不能据此下结论的原因

1. **只有 1 个 SKU、1 个机位、1 个种子**的局部放大；另 3 格（见对比图其余行）差异更小。
2. **两者光照/影调不同**，跨光照比结构本身就不可靠。
3. 看的是**我自己的目视判断**，不是评分表；主观且未复核。
4. 代价是实测的：**+2.83 GiB 权重、front 单张 +27% 耗时、显存峰值 95.3%** ——
   若真要用，8GB 上必须先解决余量问题。

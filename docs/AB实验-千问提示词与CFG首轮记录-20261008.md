## 二、决定性结果：CFG=1 时负面提示词**零作用**（已证实，非推测）

方案文档当时只能引官方说明推断「CFG=1 时负面词不参与生成」。本轮**实测证实**：

| 对比 | 唯一变量 | 结果 |
|---|---|---|
| **C0（CFG1.0 无负面词） vs C1（CFG1.0 带负面词）** | 负面词 | **4/4 组合像素完全相同**（front/3q4_left × 种子43/1234） |
| C2（CFG1.5 带负面词） vs C3（CFG1.5 无负面词） | 负面词 | **4/4 像素不同**，MAE 1.69–2.57 → 负面词生效 |

**即：在默认配置（CFG=1.0）下，往千问的 `negative` 里写任何东西，对画面没有任何影响。**
此前放进 `negative` 的「不添孔 / 不造文字 / 不脏背景」等约束**全部等于没写**。

这条实测同时说明：想靠负面词约束千问，**唯一有效的杠杆是提高 CFG**，而不是把负面词写得更长。

> ⚠️ 判读陷阱：C0 与 C1 的**文件 SHA256 不同**，但**像素 100% 相同**。
> 原因是 ComfyUI 的 `SaveImage` 会把整个提示词写进 PNG 的 `prompt` 元数据。
> **比文件哈希会得出「两者有差异」的错误结论** —— 必须比解码后的像素。

## 三、提示词改写（v3.29）的实际效应量

三条臂（`front` 处提示词字符数）：

| 臂 | 内容 | 字符数 | 负面词 |
|---|---|---|---|
| A | 旧提示词（v3.29 前，长句式） | 956 | 458 |
| B0 | 新提示词（短指令，**无**护栏） | 630 | 458 |
| B | 新提示词 + CFG=1 正向护栏（= 线上默认） | **1053** | 458 |

**结果：臂间差异显著小于采样噪声。**

- 臂间 MAE 均值 **3.03** ｜ 种子噪声 MAE 均值 **11.88** ｜ **比值 0.255**
- 即：同一臂只换一个种子造成的画面变化，是「换整套提示词」的**约 4 倍**

逐对比（MAE / 差异像素占比）：

| 机位 | 种子 | A→B0（只改文案） | B0→B（只加护栏） |
|---|---|---|---|
| front | 43 | 2.25 / 0.9% | 0.91 / 0.5% |
| front | 1234 | 2.21 / 1.0% | 1.21 / 0.7% |
| 3q4_left | 43 | **8.10 / 13.0%** | 2.18 / 2.6% |
| 3q4_left | 1234 | 2.78 / 1.2% | 1.22 / 0.3% |

唯一较大的 3q4_left/种子43 在种子 1234 上只剩 1.2% —— 说明它**更像采样起伏，不是稳定效应**。

**一个值得注意的副作用**：v3.29 的初衷之一是缩短提示词，基础文案确实从 956 降到 630（−34%），
但为补偿失效的负面词而追加的正向护栏有 423 字符，**最终提示词反而比改动前更长**（1053 > 956）。

| 配置 | front（1 参考） | 3q4_left（2 参考） |
|---|---|---|
| CFG 1.0 | 22.1 s | 34.2 s |

## 五、本次踩到并修掉的方法学陷阱

这些都是「会让人得出错误结论」的坑，已写进脚本注释：

1. **比文件哈希 ≠ 比像素**（见 §二）。PNG 元数据含提示词，像素相同也会哈希不同。
2. **MAE 没有参照尺度就没有意义**。「A 与 B 差 2.2」是好是坏，必须与「同臂换种子的差异」比。
   这也是本脚本把「种子噪声基线」作为固定输出的原因。
3. **`comfy_upload()` 只认 `assets/` 下的素材**，解析不了 `outputs/` 下的锚点产物 →
   关联机位的第二参考上传会报「找不到素材」。已改为直接上传任意本地文件。
4. **缓存格子会丢失记录**：早先版本对缓存命中直接返回，导致重跑后的事实卡**反而比首跑少了
   参数与耗时**。已改为「先算参数再查缓存」，并从既有事实卡继承历史耗时。
5. **避免重复登记的假象**：脚本不写 `config/tasks.db`，产物全在 `outputs/_AB实验/`，
   不会与控制台的真实任务混在一起。

## 六、本文件**不宣称**什么

- **不给画质结论。** 0–2 分（结构与方向 / CMF 归属 / 材料可信度 / 背景光照 / 视觉主次）
  必须由人按 `打分表-*.csv` 逐张评。MAE 只说明「改了多少像素」，不说明「变好还是变坏」。

  八面全量、其他 SKU、更高预算/步数均未测。

- **CFG 不建议改默认。** 实测只说明「CFG>1 时负面词才生效」，未证明 CFG=1.5 的画质更好

# 第二轮：文本编码器精度（4bit vs INT8）— 2026-10-08 下午

## 背景与假设

社区 Qwen 工作流与**官方 ComfyUI 模板**用的文本编码器都是
`qwen3vl_8b_int8_convrot.safetensors`（**INT8**），而本项目为省显存一直用
`qwen3vl_8b_w4a8.safetensors`（**4bit**）。

结合第一轮的发现（换整套提示词对画面的作用**小于**换一个种子，比值 0.255），
产生一个自然假设：

> **假设**：4bit 文本编码器削弱了模型对指令的跟随能力，
> 换回 INT8 后「提示词应当重新变得有效」。

## 实验设计（2×2 交互）

| 臂 | 文本编码器 | 提示词 |
|---|---|---|
| `W4A8-A` | w4a8（4bit，项目现状） | 旧长句式 |
| `W4A8-B0` | w4a8 | 新短指令 |
| `INT8-A` | **int8_convrot（官方模板默认）** | 旧长句式 |
| `INT8-B0` | **int8_convrot** | 新短指令 |

四条臂一律 **CFG=1.0、不加护栏、负面词全开** —— 使「提示词」这一维只剩文案差异。
`SKU / 输入图 / 机位 / 种子 / 分辨率预算 / 步数` 与第一轮完全相同。
`SKU=AI渲染1`、`front`+`3q4_left`、种子 `43`+`1234`、768 预算、25 步，共 **16 格，全部成功**。

新权重已下载并校验：`qwen3vl_8b_int8_convrot.safetensors`，
sha256 `8bfd0f6e12abf2d2d697ecc888e5e90b0d6741d6708f05799f53afa560452e8f`
**与官方 LFS oid 逐字节一致**（9,350,798,360 字节，ModelScope 40.7 MB/s）。

## 结果：假设**没有被支持**

MAE 明细（越大 = 改了多少像素）：

| 机位 | 种子 | 只换 CLIP（同提示词） | | 只换提示词（同 CLIP） | |
|---|---|---|---|---|---|
| | | A 下 | B0 下 | W4A8 下 | INT8 下 |
| front | 43 | 2.73 | 2.01 | 2.25 | 3.11 |
| front | 1234 | 1.38 | 1.59 | 2.21 | 2.49 |
| 3q4_left | 43 | 7.33 | 3.20 | 8.10 | 3.82 |
| 3q4_left | 1234 | 2.46 | 2.63 | 2.78 | 2.55 |

**分组均值**：

| 量 | MAE 均值 |
|---|---|
| 只换 CLIP（同提示词） | 3.48 / 2.36 |
| **只换提示词：W4A8 下** | **3.83** |
| **只换提示词：INT8 下** | **2.99** |
| 种子噪声基线 | **11.71** |

**交互比 = 2.99 / 3.83 = 0.78（< 1）**。
即换成 INT8 后，提示词对画面的作用**没有变大，反而略小**（幅度远在噪声内）。
所有臂间差异都远低于种子噪声 11.71。

> **结论：假设不成立 —— 4bit 文本编码器不是「提示词不生效」的原因。**
> 这排除了一个看起来合理的解释，也意味着「继续换文本编码器来救提示词」这条路可以停了。

## 代价（实测）

| 项 | W4A8 | INT8 |
|---|---|---|
| 文件大小 | 5.88 GiB | **8.71 GiB**（+2.83 GiB） |
| front 单张耗时（均值） | 26.1 s | **33.1 s（+27%）** |
| 3q4_left 单张耗时（均值） | 52.3 s | 52.2 s（持平，双参考占主导） |
| 全程显存峰值 | — | **7805 / 8187 MiB = 95.3%** |

显存峰值 95.3% 是**真实风险**：本次没 OOM，但已几乎没有余量。
在 8GB 卡上换 INT8 属于「拿 27% 的速度和几乎全部显存余量，换一个没测出收益的变化」。

## ★ 附带得到一个强证据：实验可复现

第一轮 `prompt` 预设与本轮 `clip` 预设里，**「A」臂的参数完全相同**
（同提示词、同 CFG、同护栏、同 CLIP = 生产默认 w4a8）。
两轮是**相隔数小时、独立进程**跑的，结果：

| 对比 | 结果 |
|---|---|
| prompt/A vs clip/W4A8-A @ front s43 | **像素完全相同** |
| prompt/A vs clip/W4A8-A @ front s1234 | **像素完全相同** |
| prompt/A vs clip/W4A8-A @ 3q4_left s43 | **像素完全相同** |
| prompt/A vs clip/W4A8-A @ 3q4_left s1234 | **像素完全相同** |

4/4 逐像素一致。这同时说明两件事：
① 工具链是**确定性**的，同参数必然同像素；
② `payload["clip_name"]` 的覆盖接线与「显式写 w4a8 == 生产默认」等价，接线没接错。

## 视觉观察（非结论）

四臂并排看**几乎一致**；`3q4_left` 的背景出现**斑驳纹理**，
而这正与第一轮「CFG=1 时负面提示词零作用」相符 ——
那些「不脏背景」的负面约束本来就等于没写。

⚠️ 但 MAE 只说明「改了多少像素」，**不说明指令跟随是否变好**。
「INT8 是否让提示词在语义上更被遵守」仍需人工 0–2 分评分，本次**未做**。

## 本次未验证

1. **没有人工评分**，画质/语义跟随的优劣未判定。
2. 只测了 1 个 SKU、1 个分辨率预算（768）、1 个步数（25）、2 机位、2 种子。
3. 没测 INT8 在更高分辨率下的表现（显存余量已不足）。
4. 没有测「INT8 + 更大 resolution」的组合。
5. 未测 BF16 文本编码器（16.33 GiB，8GB 卡不现实）。

## 建议

- **暂不切换默认 CLIP**：本次没测出收益，代价却是 +27% 耗时与 95.3% 显存占用。
  保留 `w4a8`，把「换文本编码器」从待办里划掉。
- 若做人工评分后发现 INT8 的画质确实更好，再单独评估是否值得这个代价。
- 「让提示词更有效」的方向应转向**采样侧**（第一轮已证明 CFG>1 时负面词才生效），
  而不是继续在文本编码器上找原因。

## P2：shift 仅作 A/B（内置 0.69 vs 显式 3.1）

实现方式：在**实验脚本内**把 `ModelSamplingAuraFlow` 插到 UNETLoader 与 KSampler 之间，
生产工作流 `config/comfy_workflow_qwen21_edit.json` **一行未改**。8 格全部成功。

### 结果：shift 是**真实但很弱**的杠杆

| 机位 | 种子 | 臂间 MAE | 差异像素 | 像素完全相同 |
|---|---|---|---|---|
| front | 43 | 2.75 | 0.6% | 否 |
| front | 1234 | 2.23 | 0.7% | 否 |
| 3q4_left | 43 | 4.31 | 5.0% | 否 |
| **3q4_left** | **1234** | **0.00** | 0.0% | **是** |

臂间 MAE 均值 **2.32** ｜ 种子噪声 **12.30** ｜ 比值 **0.189**。
即：把 σ 中段从 0.4278 改到 0.7706（+80%）之后，**画面变化仍小于换一个种子**。

### ★ 但先做了「补丁是否真的生效」的诊断

「有一格像素完全相同」本身就值得怀疑，所以补了一条**极端臂 `shift=10`**（front / 种子 43）：

| 对比 | MAE |
|---|---|
| 内置 0.69 → 3.1 | 2.75 |
| 内置 0.69 → **10** | **7.10** |
| 3.1 → 10 | 4.57 |

效应随偏离幅度放大 → **补丁确实进入了采样**，不是接线问题。
（源码侧也已确认：`ModelSamplingAuraFlow.patch_aura` 走
`add_object_patch("model_sampling", …)`，KSampler 取 sigma 时用的就是它。）

### 结论

**保留内置 0.69，不采用 3.1。** 理由：没有观察到稳定收益，代价却已明确（σ 更偏高噪声、
极端值下画面变化更大）。这也**修正了我方上一轮文档里的预测** ——
当时按 σ 差异把这条列为「最值得先做」，实测表明 **σ 的数值差异并不能换算成同等量级的画面差异**。

> 附带一条实现坑（我方踩到并已修）：补丁节点 id 最初取 `max+1 = 9`，
> 而关联机位稍后也用 **9** 号节点放第二参考图 → 补丁被覆盖，
> KSampler 的 `model` 接到了 IMAGE → **HTTP 400**，表现为「front 成功、3q4_left 全失败」。
> 已改为从 900 起分配 id。**这类「只在 2 参考路径上炸」的 bug 很容易被误判成模型问题。**

## P3：8GB cache / 分辨率（`QwenImage21Cache`）

三臂：不插节点 / `device=cpu` / `device=cpu, dtype=int8`。先固定 768。12 格全部成功。

### ★ 结果：`device=cpu` 是**明确的正收益**

| 臂 | front 均值 | 3q4_left 均值 |
|---|---|---|
| 不插节点（现状） | 21.2 s | **42.4 s** |
| `device=cpu` | 20.1 s | **25.4 s** |
| `device=cpu, dtype=int8` | 20.2 s | 25.2 s |

**关联机位 42.4 s → 25.4 s，约 −40%**（单参考的 front 基本不变）。

而且 `device=cpu` 与「不插节点」的输出**逐像素完全相同**（4/4，MAE 0.00）——
**零画质代价**。

`dtype=int8` 则**不建议**：与 `default` 相比输出不再相同（MAE 0.28–0.93），
而耗时没有进一步下降（25.2 vs 25.4 s）。

### 但显存**没有**降下来

全程峰值 **7646 MiB（93.4%）**，与此前几轮的 7694 / 7805 MiB 基本同一水平。
**说明 KV cache 不是显存占用的大头**（大头是 6.76 GiB 的 UNet + 5.88 GiB 的文本编码器）。
→ **P3 的前提「腾出显存以提高 resolution」没有得到支持**；
它带来的是**速度**，不是**分辨率空间**。

### 结论

- **采用 `QwenImage21Cache(device="cpu")`**：画面不变、关联机位快约 40%。这是本轮唯一的净收益。
- **不采用 `dtype=int8`**：无额外收益且引入微小差异。
- **不据此开放更高 `resolution`**：显存峰值没变，8GB 的余量问题没有解决。

## ★ 顺带得到一个跨实验的强信号

# 补记：目视对比后，对 INT8 文本编码器的建议需要修正 — 2026-10-08

用户要求「看图片判断 int8 的效果是否更好」。为让差异可见，新增工具

## 先澄清：本轮涉及**两个不同的 int8**

| 对象 | 是什么 | 结论 |
|---|---|---|
| **文本编码器** `qwen3vl_8b_int8_convrot` | 换掉 4bit 的 w4a8 | **画面有可见变化**，见下 |

## ★ 与白模并排放大后，INT8 看起来**更贴近真实几何**

同一局部（front / 种子 43，放大 2×）四联对比：

| 图 | 观察 |
|---|---|
| ① 白模 clay（真实几何） | 镜头环是**外圈 + 明显倒角/台阶 + 内圆盘**，机身有细砂纹 |

| ③ **W4A8（现状）** | 环面偏平、内圆弱，**机身可见细密斑点噪声** |

- 但「**画面是否更好**」当时明确标注为**未做人工评分**。现在的目视对比正是这块缺失的证据，
  而它**指向另一个方向**：INT8 至少在镜头环/表面洁净度上**看起来更接近真实几何**。

→ **建议改为：不把 w4a8 当作已定论的默认**，而是把「INT8 文本编码器」列入

# 第四轮：借鉴外部模型页的「设计语言型」提示词写法 — 2026-10-09

用户给了一份**在 FLUX.dev 上训练的工业电器设计 LoRA** 的模型页截图，要求「试一下这种的提示词」。
该模型页给的关键信息：

> 触发词 **GYJ**；采样器 Euler；**30 步**；**CFG 3.5**；权重 0.8；宽高 464×744。
> 例图提示词：「High resolution photos of classic black and silver film cameras with textured
> black grips that feature a 50mm lens. The camera body has a smooth metal top plate and a small
> viewfinder. The background is a light grey surface that emphasizes the stylish vintage design of the camera.」

**本项目没有 FLUX**（链路是 Qwen-Image-2.1 与 SDXL），所以本轮**只借它的提示词写法**，在我们的链路上做对照。

## 一、两种写法的本质差别

| | 我们现在的写法 | 它那种写法 |
|---|---|---|
| 内容 | 堆**约束**：「不许改轮廓/孔位/分模线」「不许臆造 text/logo」 | 堆**意象**：「classic black and silver」「textured black grips」「smooth metal top plate」「stylish vintage design」 |
| 材质描述 | 只描述**主体**那一种材质（`#3a4148` 细砂纹塑胶） | 用**设计词汇**点名多种材质与部件（哑光黑 + 拉丝银 + 滚花握持） |
| 视角/背景 | 单列固定句 | 融进一句「背景是柔和的浅灰渐变，强调设计的现代简约」 |

★ 一个关键前提：它推荐 **CFG 3.5**，而本项目**默认 CFG=1** ——
我们已在第一轮实测「CFG=1 时提示词几乎不起作用」。所以**必须把「换写法」与「提高 CFG」分开测**，
否则很容易得出「换写法没用」的错误结论。

## 二、实验设计（4 臂 × 2 机位 × 2 种子 = 16 格，全成功）

| 臂 | 写法 | CFG | 步数 |
|---|---|---|---|
| `G-current` | 现有写法（基线） | 1.0 | 25 |
| `G-design` | 设计语言写法（**只换写法**） | 1.0 | 25 |
| `G-raw` | 设计语言写法 · **去掉全部保形语句** | 1.0 | 25 |
| `G-design35` | 设计语言写法 + **照它推荐** | **3.5** | **30** |

新增两个提示词变体 `design` / `design_raw`（`scripts/qwen_ab_experiment.py` 的 `PROMPT_VARIANTS`）。

## 三、★ 结果：**第一次有变量的作用超过种子噪声**

| 对比 | MAE 均值 | 相对种子噪声 15.03 |
|---|---|---|
| **`G-current` → `G-design`**（只换写法） | **17.84** | **1.19×** ← **首次超过** |
| `G-current` → `G-raw`（换写法 + 去保形） | 22.71 | 1.51× |
| **`G-current` → `G-design35`**（写法 + CFG3.5 + 30 步） | **45.56** | **3.03×** |
| `G-design` → `G-raw`（**去保形语句的代价**） | 8.13 | 0.54×（低于噪声） |
| `G-design` → `G-design35`（CFG + 步数的贡献） | 32.97 | 2.19× |

**总体：臂间 25.94 ／ 种子噪声 15.03 ／ 比值 1.726** ——
这是本项目**第一次出现比值 > 1**（此前所有旋钮都在 0.19–0.71）。

补充观察：
- **`G-design` 自身的种子噪声 20.12**，明显高于其他臂（11.10 / 14.50 / 14.38）
  → 说明这个写法**让输出更依赖提示词**，而不是让随机性变大。
- **去保形语句的代价只有 8.13**（低于噪声）→ 在 CFG=1 下，那些「不许改」的句子作用有限。

## 四、视觉结果：**材质感确实提升了**（这是本轮最直观的收获）

放大 2× 看（`outputs/_AB实验/design/放大对比-front_s43.png`）：

| 臂 | 镜头环 |
|---|---|
| `G-current`（基线） | **哑光深灰塑料**，平，无金属感 |
| **`G-design`**（只换写法，CFG 仍 1.0） | **拉丝银金属环**，有明显金属高光渐变，右侧还多出一条**滚花带** |
| `G-design35` | 同上，对比更强一点 |

**仅换写法、不动任何参数，就把「塑料感」换成了「金属感」。** 这正是用户说的「材质感不够」。

耗时：`G-design35` 为 42–62 s，其余 22–30 s → **约 2 倍**。显存峰值 7554 MiB（92.3%）。

## 五、⚠️ 但有两个问题必须先解决，否则不能当作「赢了」

### 5.1 银色可能落在了错误部位 —— 而根因是**引导图里铝件与背景同色**

`AI渲染1` 的 CMF 方案 v5 有 4 个部位，其中**确实有一个铝件**：

| 部位 | cmf | color |
|---|---|---|
| `alu_brushed_anodized` | 拉丝阳极氧化铝 | **`#F0F0F0`** |
| `物体.2491` | plastic_gloss | `#FFFFFF` |
| `物体.019` | gunmetal_satin | `#4B5057` |
| `物体.2487` | rubber_matte | `#4F5963` |

所以「银」不是凭空来的，**方案里真有铝件**。但是 ——
**引导图里 81.59% 的像素是 `#F0F0F0`**，而影棚背景（`PRODUCT_BG['studio']`）是 `#F3F5F6`、
铝件也是 `#F0F0F0`：**两者几乎同色**。
→ **模型在引导图里本来就分不清「铝件区」和「背景」**，于是基线把所有面都当成了主体塑胶（全暗）。

**这有两种可能的解释，本轮无法区分：**
1. ✅ **乐观**：设计语言写法刚好补偿了引导图的这个缺陷，把该做成金属的部位做成了金属 —— **那是真收益**。
2. ❌ **悲观**：模型只是「听到银就加银」，银色未必落在方案指定的那个部位上 —— **那是臆造**。

**要区分，只能用 `objectid` 分区逐像素核对银色落在哪个 id 上。本轮没做。**

### 5.2 CMF 方案里的部位名是**乱码**（真乱码，不是显示问题）

方案文件里那个铝件的部位名，UTF-8 字节是
`efbfbd d0b3 efbfbd 2d2d debf bf efbfbd 32` —— 含 **4 个 `EF BF BD`（U+FFFD 替换字符）**，
按 GBK 重解是 `锟叫筹拷--锟斤拷2`。这是 **UTF-8 ↔ GBK 往返丢失**的典型特征，
**原始名称已不可恢复**。

它之所以没报错，是因为 `objectid_map` 里存的**也是同一个乱码**（同源）—— 两边一致，校验就过了。
→ **后果**：部位身份信息丢失，无法从方案里判断这个「铝件」到底是哪个物理部件。
→ **建议单独排查**：方案文件是在哪个环节被转码的。

## 六、结论与建议

1. **这种写法的方向是对的**，而且**首次让提示词的作用超过了采样噪声**，视觉上直接补上了「材质感」。
   它值得取代我们现有那套「约束堆叠」的写法 —— **至少对材质描述部分是这样**。
2. **但它推荐的 CFG 3.5 贡献更大**（`G-design`→`G-design35` = 32.97，是「换写法」的 1.8 倍），
   代价是**耗时翻倍**。3.5 是否值得，取决于「材质正确率」的收益，**需要盲评**。
3. **不能就此宣布胜利**：必须先做 §5.1 的 `objectid` 分区核对，
   确认银色落在方案指定的铝件部位上。**若落错位置，这就是典型的「臆造材质」，比不提升更糟。**
4. **修引导图**：`alu_brushed_anodized` 与影棚背景同色会导致该分区不可见 ——
   引导图应当避免使用与背景接近的颜色（或加描边）。这是**独立于本轮、值得先修**的一个缺陷。
5. **修方案文件的乱码**（§5.2）。

**未做**：`objectid` 分区核对；盲评；跨 SKU；3q4_right/top/bottom 等其余机位。

# 第四轮·追加：**决定性核对结果 —— 本轮「材质提升」不是 CMF 生效，而是方案链断了的副产品** — 2026-10-09

承接上文 §5.1。我把「银色到底落在哪个分区」真的核了一遍，结果比预想的严重。

## 一、核对方法

输出与 `objectid.png` 同机位同构图（输出是 992×608，objectid 是 1232×752，用 NEAREST 缩放到输出尺寸对齐）。
取 `G-design` 比 `G-current` **显著变亮（>30 灰阶）** 的像素，看它们落在哪个 objectid 上；
再把 `objectid` 的 id 通过 `pass_manifest.json` 的 `objectid_map` 反解成部位名。

## 二、结果一：**方案分配的 4 个部位，在全部 10 个机位里一个都不可见**

| 机位 | 可见部位数 |
|---|---|
| front / back / side / side_left / top / bottom / 3q4_left / 3q4_right / detail_keypad / detail_window | **全部 0/4** |

前视图里实际可见的对象只有 8 个：

| objectid | 占比 | 部位名 |
|---|---|---|
| 6 | 76.60% | `物体.005` |
| 8 | 11.09% | `物体.007` |
| 3 | 11.05% | `物体.002` |
| 7 | 1.08% | `物体.006` |
| 1/2/4/5 | <0.1% | `物体` / `物体.001` / `物体.003` / `物体.004` |

而 CMF 方案分配的是 **`物体.019`(id 20) / `物体.2487`(id 1737) / `物体.2491`(id 1742) / 乱码名(id 2530)**
—— **没有一个在可见集合里**。

> **也就是说：`AI渲染1` 的 CMF 方案当前是一个「空转」的方案。**
> 它把材质分配给了在任何机位都不会出现的部件。

## 三、结果二：变亮的像素 **88% 在背景上**

| objectid | 占「变亮区」 | 名称 |
|---|---|---|
| **0** | **88.05%** | （背景） |
| 6 | 10.02% | `物体.005`（**无材质分配**） |
| 3 | 1.68% | `物体.002`（**无材质分配**） |
| 8 | 0.19% | `物体.007`（**无材质分配**） |

「变亮」的 20963 像素（占全图 3.48%）里，**88% 是背景** ——
对应提示词里那句「The background is a soft light-grey gradient surface…」。
剩下的 12% 落在 **id 6/3/8 上，而这 3 个对象在本方案里根本没有分配材质**。

→ **所以那个「拉丝银金属环」不是「CMF 方案指定的铝件被正确渲染出来」，
而是模型在「没有分配材质的可见部件」上自由发挥 + 改了背景。**
它在视觉上是好看的，但**在「CMF 分区是否被遵守」这个意义上，它什么也没证明**。

## 四、根因：**方案与 pass 用的不是同一个模型**

| 来源 | 模型 |
|---|---|
| CMF 方案文件里写 | `AI渲染1_30.3dm` |
| `load_cmf_scheme()` 解析后指向 | **`AI渲染1_32.3dm`**（`fingerprint=08ba3012…`） |
| 各机位 pass 实际渲染用 | `AI渲染1_22` / `_23` / `_25` / `_26` / `_28` |

**方案（rev30/32）与 pass（rev22–28）完全不同** → 方案里引用的部位 id 在 pass 的 `objectid_map` 里
**存在同名条目**（映射表覆盖整个网格列表，2530 项），所以名字校验能过；
但那些 id **在该机位的渲染里根本没有像素** → 分区不可见。

★ 这同时解释了 §5.2 之前看到的怪现象：**CMF 引导图里 81.59% 是 `#F0F0F0`，产品区几乎全暗** ——
因为引导图是按「有分配的部位」上色的，而**那些部位一个都没出现**，可见的部分全走了默认色。

## 五、连带发现：`validate_cmf_task` 有一个真实缺口

它只校验 `set(方案部位) - set(objectid_map.values())` 是否为空 —— **名字在映射表里就行**。
它**不校验「该部位在这个机位是否真的可见」**。
→ 于是「方案把材质分配给了一个在本机位不存在的部件」这种情况**能一路通过校验**，
一直到出图都不报错，只是分区悄悄失效。

**建议**：在 `validate_cmf_task` 里补一条 —— 用该机位的 `objectid.png` 求实际出现的 id 集合，
与方案部位的 id 求交集；**交集为空就报错**（或至少给强警告）。这会直接挡住本次这类问题。

## 六、对第四轮结论的修正

| 原先的判断 | 修正后 |
|---|---|
| 「设计语言写法补上了材质感，可能是真收益」 | **在 `AI渲染1` 上不成立** —— 那是方案空转时模型自由发挥的结果，**不能算 CMF 被遵守** |
| 「写法首次让提示词作用超过种子噪声」 | **这条仍然成立**（MAE 1.19× 噪声是客观事实），但**作用在哪、是不是我们要的，是另一回事** |
| 「要核对银色是否落在正确部位」 | **已核对：没有落在任何被分配的部位上**（因为那些部位不可见） |

**所以第四轮真正得到的结论是**：
1. 「设计语言型」写法确实更能影响画面（首次超过种子噪声）—— **但影响不等于正确**；
2. **`AI渲染1` 的 CMF 链当前是断的**（方案与 pass 不同版本），在把它修好之前，
   任何在 `AI渲染1` 上做的 CMF 相关对照（包括 E1 的 `input` 预设）**结论都不可信**；
3. **`validate_cmf_task` 需要补「可见性」校验**，否则同类问题会再次静默通过。

**建议的修复顺序**：定一个权威 .3dm 版本 → 从该版本重出 10 个机位的 pass → 重建 CMF 方案（部位 id 对齐）
→ 补可见性校验 → 再重跑本轮的 4 臂对照。

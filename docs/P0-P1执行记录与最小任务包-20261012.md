## 1. M0｜16 位部件 ID 解码精度（**完成**）

### 1.1 现状核对

`scripts/objectid_mask.py` 里**自带纯标准库的 16 位 PNG 解码器**（`read_png_raw` + `read_ids`），
注释就写着「PIL 对 16 位 RGB(A) 会降位成 8 位，把 ID 信息毁掉」——
**这条路本来就是对的，只是我在做归因分析时没用它、改用了 PIL，才引出那两处错误结论。**

### 1.2 新增回归测试 `web/test_objectid_precision.py`（7 项，全通过）

用**合成图**把解码路径钉死，不依赖私有资产：

| 测试 | 钉住什么 |
|---|---|
| `test_file_is_really_16_bit` | 夹具本身是真的 16 位 RGBA（读 IHDR 第 24/25 字节）—— 否则后面的精度测试没意义 |
| **`test_known_ids_decode_exactly`** | **ID 1 / 20 / 255 / 256 / 1737 / 1742 / 2530 逐位准确**（降位读法会压成桶值） |
| `test_no_id_is_lost_or_merged` | ID 集合完全一致：不漏、也不把不同 ID 并成一个 |
| **`test_odd_coordinate_single_pixel_not_missed`** | **奇数坐标上的 1 像素细件**（抽样读法会整条漏掉） |
| `test_edge_and_split_parts` | 图边缘件 + 被遮挡拆成两段的同一 ID |
| `test_max_scale_id_round_trip` | 65534 / 65535 不被钳制（历史上曾全饱和成 65535） |
| `test_pil_would_have_lost_precision` | **把「为什么不能用 PIL」钉成可执行证据**：断言 Pillow 读出来是 `uint8` 且**不含**真实 ID 1737 |

> 写夹具时踩了一个坑：16 位 RGBA 每像素是 **8 字节**（R/G/B/A 各 2 字节），
> 我一开始只写了 7 字节（alpha 少一个高字节），结果解码器和 PIL 都拒绝。已修正并留注释。

### 1.3 ★ 两条独立解码路径交叉核对（真机，`AI渲染1` 全 10 机位）

| 路径 | 实现 |

## 4. 我建议的下一步（按大纲顺序）

1. **P1 收尾**：用这份逐部件表请用户指定 `物体.2526` / `2527` / `2488` / `2500` / `2509` 等大件的材质
   —— 覆盖率从 25.84% 往上走，比再调参数见效快。
2. **P2 缓存签名**（对应报告 M1 的一部分）：把 `blender_pass.py` 的着色逻辑哈希、
   CMF 预设库哈希、灯光版本纳入 `scene_id`；**不修这条，以后每次改材质都会同名覆盖旧底图。**
3. **P2 外部 PBR 接入**（M1/M2）：先手工导入一套 PBR 打通，再做三档灯光。
4. `渲染3` 的权威版本问题顺手定一下（它才是真有分歧的那个）。

# 一、文档说明与留痕规范

## 1.1 为什么要有这个过程文档

这个项目的性质是「**长期演进的产线建设**」，不是一次性交付。它会持续吸收：

- 新出的开源模型（几乎每月都有）
- 调参过程中积累的经验值
- 真实跑批暴露的失败模式
- 类目扩展（激光水平仪 → 气体检测仪 → 其他）
- 硬件与许可环境的变化

如果这些只存在于聊天记录和零散文件里，三个月后就找不回来了。所以本文档承担三个职责：**汇总、分析、留痕**。

## 1.2 留痕规范（强制）

### 版本号规则

| 位 | 含义 | 示例 |
|---|---|---|
| 主版本 | 架构级变更（分层、路线、核心决策改动） | v1.0 → v2.0 |
| 次版本 | 内容新增或重要修正（新模型接入、参数基线调整、阶段完成） | v1.0 → v1.1 |
| 修订号 | 错别字、链接修正、表述优化 | v1.1 → v1.1.1 |

### 每次更新的标准动作

1. **在「二、变更记录」表格顶部追加一行**，字段：日期 / 版本 / 类型 / 摘要 / 触发原因 / 影响章节。
2. **在正文被修改的章节末尾追加一行**：`> 留痕：v1.1（2026-10-02）将 depth 默认权重从 0.60 上调至 0.65，依据见变更记录。`
3. **不得删除原文**。若某结论被推翻，保留原结论并加 `~~删除线~~` 标记 + 说明替代结论，同时移入附录 D。
4. **量化优先**。写"成品率从 68% 提升到 84%"而不是"效果更好了"。没有数据的更新标注「待补数据」。

### 变更类型代码

| 代码 | 含义 |
|---|---|
| `NEW` | 新章节、新模块、新工具 |
| `MOD` | 修改既有结论、参数、流程 |
| `FIX` | 修正错误（链接失效、参数写错、结论有误） |
| `DEL` | 废弃（须同时写入附录 D） |
| `DATA` | 新增实测数据 |
| `STAGE` | 阶段状态变更 |

# 三、项目概述与需求拆解

## 3.1 一句话定义

**构建一条把「产品白模」自动转换为「可用于电商主图与详情页的写实渲染图」的产线**，支持三种输入方式（文字描述、结构化参数卡、参考产品图仿照），要求可批量、可复现、可回滚。

## 3.2 资产背景

| 项 | 现状 |
|---|---|
| 存量资产 | 约 2000 个详情页 PSD（中英文双版本） |
| 主要类目 | 激光水平仪、气体检测仪 |
| 已有管线 | KeyShot 三维建模与渲染、PSD 详情页排版 |
| 目标 | 存量资产的渲染图批量再生 + 新品的快速出图 |

## 3.3 需求拆解

原始诉求拆成 6 件事，技术难度与成熟度差异极大：

| # | 需求 | 技术归属 | 成熟度 | 可行性判断 |
|---|---|---|---|---|
| 1 | **自动化渲染模型**（白模进去、图出来、可批量） | 引擎 headless + 任务队列 | ★★★★★ | 纯工程问题，无技术风险 |
| 2 | **描述外观 / 材质 / 光照** | 提示词工程 + 参数卡 + ControlNet / IC-Light | ★★★★☆ | 主力路线，已可生产 |
| 3 | **给参考图仿照渲染** | IP-Adapter / FLUX Redux + 蒙版限定 | ★★★★☆ | 已可生产，可控性需调试 |
| 4 | **模型上真 PBR 材质** | DreamMat / TRELLIS.2 / Hunyuan3D-2.1 | ★★★☆☆ | 能跑，但慢且许可受限 |
| 5 | **细节零失真**（丝印 / 刻度 / LOGO / 透明件） | 无纯 AI 方案 | ★★☆☆☆ | **必须靠后处理回贴** |
| 6 | **完全无人值守跑批** | 任务队列 + QC 抽检 | ★★★☆☆ | 需保留人工抽检关口 |

> **关键判断**：第 5 项是整个方案的架构决定因素。你的类目（刻度盘、按键、丝印品牌、认证标识、透明视窗、镜面金属）在纯 AI 生成下必然失真。任何"一句 prompt 出产品图"的方案在这个类目上都会翻车。

# 四、设计理念

这一章是**判断依据**，不是实现细节。后面所有的技术选择，都是从这里推导出来的。

## 4.1 第一原则：保真优先于美观

电商产品图的第一性要求是「**和实物一致**」，不是「好看」。虚假或失真的产品图不只是审美问题，是**广告合规风险**。

由此确定需求优先级：

```
形状保真  >  材质真实  >  光影合理  >  视觉冲击
```

任何为了"更好看"而牺牲形状保真的做法，一律否决。

## 4.2 第二原则：按能力边界切分工，不让 AI 一把梭

AI 的能力边界很清晰：

| AI 擅长 | AI 不擅长 |
|---|---|
| 材质质感（磨砂 / 拉丝 / 类肤） | 精确几何（厚度、倒角、比例） |
| 光影氛围（柔光、逆光、环境反射） | 文字与数字（丝印、刻度、LOGO） |
| 背景场景（桌面、工地、车间） | 认证标识、型号、量程 |
| 快速风格变体 | 透明材质的物理正确性 |

**所以架构设计的核心动作是「按能力边界切分」**：AI 只负责它擅长的部分，其余交给 3D 引擎和后期图层。

- 形状 → ControlNet（用引擎出的 depth/normal 锁死）
- 材质与光影 → AI 生成
- 文字与标识 → 图层回贴（不经过 AI）
- 透明件 → 引擎真渲染合成

## 4.3 第三原则：确定性优先于智能性

批量生产要的是**可复现、可回滚、可审计**，不是每次给你惊喜。

- 批量执行走**确定性脚本**，不让 LLM 参与批量决策（LLM 只用在"自然语言 → 参数卡"这一步，且结果要人工复核）。
- 每组参数、每个 seed、每个工作流版本都可追溯。
- 同一输入必须得到同一输出（固定 seed + 固定工作流版本）。

## 4.4 第四原则：像素级对齐是一切的前提

ControlNet 的工作原理是"按输入的 depth/normal 图重建结构"。**如果 pass 图和目标构图没对齐，ControlNet 传递的就是噪音**，你再怎么调权重都是在跟错误信号对抗。

这条看着像工程细节，实际是**最容易浪费几十小时的地方**（在错误的方向上调 prompt）。所以方案把「对齐校验」提升为核心机制而非可选项。

## 4.5 第五原则：中间产物都是资产

Pass 图、参数卡、seed、工作流 JSON、参考图库 —— 这些不是临时文件，是**可复用资产**。

- 参考图库按「材质 / 打光 / 构图」三类归档，跨 SKU 复用。
- 参数卡按类目沉淀为预设模板。
- 工作流 JSON 进版本控制。

## 4.6 第六原则：先窄后宽

不要一开始就做"通用渲染器"。**从一个 SKU、一个视角、一种材质跑通闭环**，验证形准率，再横向铺开。

理由：这个项目的失败模式高度集中在"形准"这一关。如果这一关没过就铺量，得到的是 16000 张废图，不是 16000 张成品。

## 4.7 第七原则：许可先于效果

商用项目里，**"效果差 10% 但许可干净"永远优于"效果好 10% 但法务有风险"**。

所以选型的第一道过滤是许可，第二道才是效果。这条原则直接否决了本方案初期最想用的 Hunyuan3D-2.1（非商用）和 Pixal3D（学术许可）。

## 4.8 第八原则：人机分工的界面要清晰

不追求"全自动"，追求"**把人的时间花在只有人能做的事上**"。

| 人必须做的 | 机器做的 |
|---|---|
| 需求意图转述（"要什么感觉"） | 参数卡生成、pass 生成、出图 |
| QC 抽检判断 | 抠图、超分、命名、归档 |
| 关键标识的核对与回贴校对 | 图层回贴的批量执行 |
| 合规判断 | 数据登记与追溯 |

# 五、设计分析

## 5.1 总体架构

### 五层结构

```
┌──────────────────────────────────────────────────────────────────────┐
│ L5 交付层   PSD 详情页占位替换 / 命名规范 / 中英双版 / QC 抽检          │
├──────────────────────────────────────────────────────────────────────┤
│ L4 后处理层  抠图(BiRefNet) → 超分(Real-ESRGAN) → LOGO丝印回贴 → 色彩统一│
├──────────────────────────────────────────────────────────────────────┤
│ L3 生成层    ComfyUI 工作流                                            │
│              结构控制(ControlNet depth/normal/canny)                   │
│            + 参考注入(IP-Adapter / FLUX Redux，可蒙版限定部位)          │
│            + 重打光(IC-Light) + 材质 LoRA + 采样                        │
├──────────────────────────────────────────────────────────────────────┤
│ L2 结构层    KeyShot headless  /  Blender(-b -P)  /  BlenderProc        │
│              批量出多机位多通道 Pass：beauty / depth / normal / alpha    │
├──────────────────────────────────────────────────────────────────────┤
│ L1 输入层    LLM 参数解析：自然语言 ─┐                                  │
│                                参数卡 JSON ─┼─▶ 渲染参数卡（统一结构）    │
│                                参考图 ─────┘                            │
├──────────────────────────────────────────────────────────────────────┤
│ L0 资产层    白模库 / 参考图库(材质·打光·构图) / 相机机位预设 / 提示词模板 │
└──────────────────────────────────────────────────────────────────────┘
```

### 为什么是这五层

| 分层依据 | 说明 |
|---|---|
| **按「产物形态」分层**，不按工具分层 | L2 产出是「几何信息图」，L3 产出是「材质光影图」，L4 产出是「可交付图」。每层有明确的输入输出契约，工具可以整体替换（比如 L2 的 KeyShot 换成 Blender，L3 不动） |
| **L1 独立成层** | 因为"意图 → 参数"是最容易变更的一层（今天用文字、明天可能接表单/接 CAD 元数据），隔离出来避免污染下层 |
| **L0 独立成层** | 资产库的价值随时间增长，是**资产而非流程**，需要独立管理和版本化 |

> **设计取舍**：没有做成三层（输入 / 处理 / 输出）。因为那样 L2 和 L3 会混在一起，导致"引擎换版本"和"模型换版本"互相牵连 —— 而这两件事的变更频率差一个数量级。

## 5.2 分层设计详解

### L0 资产层

| 资产 | 内容 | 管理方式 |
|---|---|---|
| 白模库 | `.ksp` / `.blend` / `.glb` / `.obj` | 按类目 / SKU 归档；**白模版与材质版分离保存** |
| 参考图库 | 材质参考 / 打光参考 / 构图参考 | 三类分目录，命名带材质或光照关键词，支持跨 SKU 复用 |
| 相机机位预设 | 球坐标（方位角 / 仰角 / 距离）+ 目标点 | 一套预设跨模型复用，保证多 SKU 构图一致 |
| 提示词模板库 | 材质词表 / 光照词表 / 背景词表 / 通用负向词 | 见第 9.5 节 |
| 参数卡预设 | 按类目的默认参数组合 | 见 5.4 节 |

**设计要点**：白模版 KSP 独立保存，不要在脚本里动态改材质 —— 脚本改材质容易污染原资产，且不可回溯。

### L1 输入层

统一收敛为**渲染参数卡**（见 5.4）。三种输入方式的处理：

| 输入 | 处理 |
|---|---|
| 自然语言 | LLM 解析为参数卡 → **人工复核** → 入库 |
| 结构化表单 / 已有参数卡 | 直接入库 |
| 参考图 | 作为参数卡的 `reference` 字段，按 L1/L2/L3 三档强度（见 5.5） |

### L2 结构层

**职责**：把「几何」变成「几何信息图」。不做任何美化。

| 输出 Pass | 用途 | 格式 |
|---|---|---|
| Beauty（白模） | 底图参考、Canny 来源 | PNG 16bit |
| Depth | ControlNet Depth | PNG 8bit 归一化 或 EXR |
| Normal | ControlNet Normal | PNG RGB（**必须确认空间约定**） |
| Alpha / Mask | 抠图、局部重绘、蒙版限定参考 | PNG 8bit |
| AO / Curvature（可选） | 强化倒角、缝隙、按键细节 | PNG |

**工具选择与组合策略**：

| 工具 | 用在什么上 | 原因 |
|---|---|---|
| **KeyShot headless** | Beauty + 多机位编排 | 已有资产和材质库；相机、模型集、Studio 可脚本控制。**注意：Headless scripting 是 Pro 独占功能（9.3+）** |
| **Blender `-b -P`** | Depth / Normal / Alpha | 完全免费，Cycles 的 AOV / Compositor 出通道最灵活 |
| **BlenderProc** | 想省事时的替代 | `pip install blenderproc`，内建 RGB/depth/normal/seg 输出；官方支持 Linux/macOS，**Windows 为社区支持** |

**推荐组合**：KeyShot 出 beauty + 定机位；Blender / BlenderProc 出 depth/normal/alpha；两边用**同一套相机参数**（焦距、机位、朝向），保证像素级对齐。

### L3 生成层

**职责**：在锁定的几何上生成材质与光影。**不负责形状**。

见第 9 章技术基线。

### L4 后处理层

**职责**：把"生成图"变成"可交付图"。

| 步骤 | 工具 | 作用 |
|---|---|---|
| 抠图 | BiRefNet | SOTA 边缘，透明件表现显著优于传统方案 |
| 对齐校验 | OpenCV 叠图 diff | 生成图 vs 白模 beauty，轮廓偏移超阈值打回重跑 |
| 超分 | Real-ESRGAN / Topaz | 2–4x |
| **标识回贴** | Photoshop 脚本 | **最关键一步**，见 4.2 原则 |
| 色彩统一 | LUT / 直方图匹配 | 同 SKU 多图色调一致 |

### L5 交付层

**职责**：落进现有详情页流程。

| 项 | 内容 |
|---|---|
| 命名规范 | `{类目}_{SKU}_{视角}_{风格}_{版本}_{语言}.png` |
| 归档 | `output/raw/{SKU}/` 与 `output/final/{SKU}/` |
| PSD 对接 | 智能对象占位替换脚本 |
| 中英双版 | 注意英文文案长度不同，需留排版余量 |
| QC | 抽检 + 合规校验 |

## 5.3 数据流（单张图）

```
白模.ksp
  │  KeyShot headless（或 Blender）
  ▼
beauty.png + depth.png + normal.png + alpha.png     ← 2048 长边
  │
  ▼  ComfyUI（常驻 8188 端口）
  │   ① depth   → ControlNet  权重 0.55–0.75   ← 锁体积关系
  │   ② normal  → ControlNet  权重 0.35–0.50   ← 锁曲面朝向 / 高光走向
  │   ③ 参考图   → Redux / IP-Adapter  0.5–0.8  ← 注材质与影调
  │   ④ prompt   → 材质 + 光照 + 背景 + 镜头
  │   ⑤ IC-Light → 按指定方向重打光（可选）
  ▼
raw_1024.png
  │  后处理：抠图 → 精修 → 超分 2–4x → LOGO/刻度回贴
  ▼
{类目}_{SKU}_{视角}_{风格}_{版本}_{语言}.png
```

## 5.4 关键接口设计：渲染参数卡

参数卡是本方案的**核心接口契约**。它把"意图"和"执行"解耦：上层可以换（文字 / 表单 / CAD 元数据），下层也可以换（不同底模、不同 ControlNet），只要契约不变。

```jsonc
{
  "asset": {
    "model": "D:/Models/LS-360G.ksp",
    "category": "激光水平仪",
    "sku": "LS-360G",
    "views": ["front", "3q4_left", "3q4_right", "top", "detail_keypad"]
  },
  "material": {
    "body":   { "type": "ABS", "finish": "fine_sandblast", "color": "#2B2F33",
                "roughness": 0.75, "metallic": 0.0 },
    "trim":   { "type": "aluminum", "finish": "anodized_brushed", "color": "#9AA0A6",
                "roughness": 0.35, "metallic": 1.0 },
    "window": { "type": "PMMA", "transmission": 0.92, "ior": 1.49 }
  },
  "lighting": {
    "scheme": "studio_softbox_3point",
    "key":  { "dir": "front_left_45", "temp": 5600, "size": "soft_large" },
    "fill": { "dir": "front_right_60", "temp": 5600, "ratio": 0.35 },
    "rim":  { "dir": "back_right", "temp": 6000, "intensity": 0.8 },
    "shadow": "soft_contact",
    "hdr_env": "studio_soft_02.hdr"
  },
  "camera": { "focal": 85, "height": "product_level", "perspective": "mild_tele" },
  "background": { "type": "gradient_gray", "from": "#F5F6F7", "to": "#DDE1E4" },
  "reference": {
    "image": "D:/Refs/ref_01.jpg",
    "strength": "L2_material",
    "target_part": "body_upper",
    "mask": "D:/Refs/ref_01_mask.png"
  },
  "output": { "resolution": [2048, 2048], "count": 4, "upscale": 2, "lang": "CN" }
}
```

**设计要点**：

| 决策 | 理由 |
|---|---|
| 用结构化卡而不是长 prompt | 可校验、可版本化、可批量、可审计；长 prompt 无法做参数扫描 |
| 材质用**参数**（roughness/metallic）而不是形容词 | 参数可映射到引擎，形容词只能映射到 AI 的模糊理解；两者都保留，引擎侧用参数、AI 侧用词表 |
| `reference.strength` 用 L1/L2/L3 枚举 | 强制用户明确"我要仿照到什么程度"，避免无意义的权重试错 |
| 保留 `_` 前缀的下划线字段 | 运行时注入（seed、pass 目录、权重覆盖），与业务字段隔离 |

## 5.5 参考图仿照的三档强度

"给一个类似的产品进行仿照渲染"实际有三种完全不同的需求，必须在参数卡里区分：

| 档位 | 目标 | 实现 | 参数 |
|---|---|---|---|
| **L1 风格轻参考** | 只借色调、影调、氛围 | IP-Adapter Plus | weight 0.4–0.6 |
| **L2 材质参考** | 借某个具体部位的材质质感 | FLUX Redux + 蒙版限定 | `downsampling_factor` 2–3，`mode=autocrop with mask` |
| **L3 整体仿照** | 连打光带构图一起学 | FLUX Redux 高权重 + 图生图 | `downsampling_factor` 1–2，denoise 0.5–0.7 |

> ⚠️ **FLUX Redux 的已知行为**：高权重时会**完全忽略提示词**，只复刻参考图。解决方式是加 `ComfyUI_AdvancedRefluxControl`，用 `downsampling_factor` + `weight` 把"复刻参考图"和"听提示词"这两个力掰开。
> ⚠️ **FLUX Redux 的已知限制**：**只接受正方形输入**，所以插件提供三种裁切策略（center crop / keep aspect ratio / autocrop with mask）。

## 5.6 自动化调度设计

### 组件拓扑

```
┌─────────────────┐
│ 任务队列 (SQLite) │  ← 参数卡列表 + 状态 + 重试次数
└────────┬────────┘
         │
    ┌────┴─────┐
    ▼          ▼
┌────────┐  ┌──────────────┐
│ KeyShot│  │ ComfyUI 常驻  │  http://127.0.0.1:8188
│headless│  │ (--listen)    │  POST /prompt → poll /history/{id}
└────────┘  └──────────────┘
                 │
            多卡：启动多个实例，不同端口 8188/8189，队列侧轮询分发
```

### 设计决策

| 决策 | 理由 |
|---|---|
| **ComfyUI 常驻服务**，不循环起进程 | 冷启动 10–30s。循环跑 16000 张 = 白扔 13–40 小时 |
| **多卡用多个实例**（不同端口），不用单实例多卡 | 实测经验：**多卡独立实例比单实例多卡快 2–3 倍**，避免显存抖动 |
| **SQLite 持久化任务** | 需要断点续跑、需要追溯"哪张图用了哪组参数"、需要失败重试计数。内存队列做不到 |
| **`running` 状态在启动时重置** | 进程被杀后不会永久卡住任务 |
| **工作流必须用 API format 导出** | UI 格式的节点 ID 是字符串，API 要求数字。必须开 Dev Mode → Save (API format) |

### 七个必踩的坑（已固化进脚本）

| 坑 | 表现 | 解法 |
|---|---|---|
| 工作流 JSON 格式错 | `KeyError on node ID` | 开 Dev Mode → Save (API format) |
| `/history` 查不到在途任务 | 误判为失败 | `/history` **只返回已完成任务**，在途任务不出现；必须轮询直到 `prompt_id` 出现，**第一次查不到 ≠ 失败** |
| 节点静默失败 | 队列卡住不报错 | 节点 CUDA 报错**不通过 API 返回**，会静默堵队列。必须读 ComfyUI 终端日志 + 设超时 |
| 服务器重启丢历史 | 长批次中断 | `/history` 重启后清空 → **prompt_id 持久化到 SQLite**，重连后续跑 |
| 输出路径 | 拿到相对路径 | API 返回相对路径，实际写绝对路径；启动用 `--output` 指定 |
| 显存瓶颈 | 1080p 叠 3 个 ControlNet 爆显存 | 1024 可叠 3 个，**1536 实际只能叠 2 个**（24GB 卡） |
| 批次跑到一半质量下降 | 某张 pass 生成失败串了数据 | 加 pass 目录完整性校验 |

## 5.7 架构决策记录（ADR）

> 本节记录**为什么这么设计**。每条 ADR 包含：决策、背景、理由、代价。后续若推翻某条，须在本条下追加 `> 留痕：vX.Y 该决策被 vY.Z 替代，原因……`，并写入附录 D。

### ADR-001 采用五层架构，而非端到端单模型

- **背景**：社区存在"一张图进、一张图出"的端到端产品图生成模型。
- **决策**：不自研端到端模型，采用五层可替换架构。
- **理由**：端到端模型无法保证形状保真（第 4.1 原则），无法接入已有的 KeyShot 资产，无法做参数扫描，且训练数据需要长期积累。分层架构每一层都有现成成熟轮子。
- **代价**：组件多、胶水代码多、需要维护相机参数一致性。

### ADR-002 AI 只负责材质与光影，形状与文字交回引擎和图层

- **背景**：最初设想是"用 prompt 描述形状 + 材质 + 光照，一把生成"。
- **决策**：prompt 中**禁止写形状描述词**，形状由 ControlNet 锁；文字与标识由图层回贴。
- **理由**：形状描述词是 AI 最不可控的输入，且会与 ControlNet 信号冲突；丝印/刻度/LOGO 的准确性 AI 完全不可靠（4.2 原则）。
- **代价**：多一道 PS 图层回贴工序；需要维护标识图层资源。

### ADR-003 以参数卡为主要输入，长 prompt 为派生输出

- **背景**：可以直接让用户写 prompt，或让 LLM 生成 prompt。
- **决策**：用户输入统一收敛为参数卡；prompt 由参数卡**程序化拼装**。
- **理由**：prompt 不可校验、不可扫描、不可审计；参数卡可以（5.4）。
- **代价**：需要为每个新类目维护词表映射；灵活性略低于自由写 prompt。

### ADR-004 批量执行走确定性脚本，LLM 只做意图解析

- **背景**：直觉上可以让 Agent 自主决定每个 SKU 用什么参数。
- **决策**：LLM 只在"自然语言 → 参数卡"这一环介入，且结果人工复核；批量执行全部走脚本。
- **理由**：批量生产要求可复现、可回滚、可审计（4.3 原则）。LLM 决策无法保证同一输入同一输出。
- **代价**：失去部分"智能调参"能力，需要人工兜底特殊 SKU。

### ADR-005 参考图仿照分三档强度，强制显式选择

- **背景**：用户说"参考这张图"时，意图可能是借色调、借材质、或整体复刻。
- **决策**：参数卡强制指定 `L1_style` / `L2_material` / `L3_full`。
- **理由**：这三档对应的权重差异巨大（IP-Adapter 0.5 vs Redux factor 1），混为一谈会导致大量无效试错。
- **代价**：用户需要理解三档的区别；参数卡复杂度上升。

### ADR-006 Pass 出 2048、成图出 1024、按需超分

- **背景**：可以直接出高分辨率成图。
- **决策**：pass 出 2048 长边（留放大余量）；生成固定 1024 打稿；只对筛选通过的 20% 做 2–4x 超分。
- **理由**：高分辨率下 ControlNet 叠加数量受限（1536 只能叠 2 个），且耗时线性增长。**先出草稿筛选能把总机时砍掉 60% 以上**。
- **代价**：需要一轮人工筛选；超分可能引入轻微细节漂移。

### ADR-007 任务持久化用 SQLite，而非内存队列或消息中间件

- **背景**：可选内存队列、Redis、RabbitMQ、SQLite。
- **决策**：SQLite 单文件。
- **理由**：单机场景，量级（万级任务）SQLite 完全够用；零运维、可随项目目录一起备份、可直接用工具查（可审计）。引入中间件是过度设计。
- **代价**：不适合多机分布式（若未来要多机，届时再迁移）。

### ADR-008 商用选型以许可为第一过滤条件

- **背景**：效果最好的模型（Hunyuan3D-2.1、Pixal3D）恰是许可受限的。
- **决策**：商用项目只用 MIT / Apache 许可的模型。
- **理由**：4.7 原则。
- **代价**：放弃部分效果上限。

### ADR-009 用 KeyShot 出 beauty 而非纯 Blender

- **背景**：可以全流程用 Blender（免费）。
- **决策**：beauty 和机位编排用 KeyShot，pass 用 Blender。
- **理由**：已有 KeyShot 资产、材质库、HDR 环境库，重建成本极高；且**用真三维光照重出底图，比让 AI（IC-Light）猜光照可靠得多**。
- **代价**：需要维护两套软件，且要保证相机参数一致（这是主要风险点）。

### ADR-010 保留人工 QC 抽检关口，不追求 100% 无人值守

- **背景**：目标是"自动化渲染"。
- **决策**：自动化到"出图 + 归档"，但保留 5% 抽检 + 合规校验。
- **理由**：广告合规风险不可用自动化概率覆盖（4.1 原则）；16 项 QC 里"与实物一致性"只有人能判断。
- **代价**：需要人工工时；批次交付有等待。

# 六、可行性分析

## 6.1 技术可行性

逐项拆解，给出评级与理由：

| # | 能力项 | 评级 | 可行性理由 | 主要制约 |
|---|---|---|---|---|
| 1 | 白模多通道 Pass 自动生成 | ★★★★★ | KeyShot headless（Pro 9.3+）与 Blender `-b -P` 均为成熟方案，函数文档完整 | KeyShot 需 Pro 授权；两套引擎相机参数需对齐 |
| 2 | ControlNet 锁定形状 | ★★★★★ | depth/normal 双 ControlNet 是已验证的成熟组合（Blender → SD 是社区常见管线） | 权重需要按类目调；Normal 空间约定易错 |
| 3 | 文字描述材质与光照 | ★★★★☆ | 材质词 + ControlNet 的组合已验证有效；词表可枚举 | 形容词映射到材质不完全线性；透明件仍是弱项 |
| 4 | 参考图仿照 | ★★★★☆ | IP-Adapter / FLUX Redux 均为成熟方案，社区有可控性补丁 | Redux 只吃正方形；高权重时忽略 prompt；需蒙版流程 |
| 5 | 3D 模型生成 PBR 材质 | ★★★☆☆ | DreamMat / TRELLIS.2 可跑通，输出标准 PBR 贴图 | 慢（每模型 10min–1h）；几何质量要求高；商用许可受限 |
| 6 | 细节零失真（丝印/刻度/LOGO） | ★★☆☆☆ | **无纯 AI 方案**。必须走图层回贴 | 需要维护标识图层资源；回贴需要透视对齐 |
| 7 | 透明件物理正确 | ★★☆☆☆ | AI 对透射材质能力不足 | 只能降低 AI 占比，走引擎真渲染合成 |
| 8 | 批量无人值守 | ★★★★☆ | 队列 + HTTP API + 断点续跑，工程上完全可行 | 节点静默失败需额外监控；显存瓶颈需分批 |

### 综合技术可行性结论

**整体可行，但必须接受「能力天花板」的存在。**

- ★★★★★ 与 ★★★★☆ 项（1、2、3、4、8）覆盖了 80% 的需求，这部分是**确定能做成生产线的**。
- ★★★☆☆ 项（5）**可以做成，但作为辅助线**，不适合纳入日常批量。
- ★★☆☆☆ 项（6、7）**不要试图用 AI 解决**。这两项一旦被正确识别为"非 AI 问题"，方案就从"不可行"变成"可行" —— 这正是本方案设计的核心价值。

> **一句话**：技术可行性不是"AI 能不能生成好看的产品图"（能），而是"AI 能不能生成**和实物一致**的产品图"（不能，必须混合）。方案的设计就是围绕这个边界组织的。

## 6.2 工程可行性

| 维度 | 评估 | 说明 |
|---|---|---|
| 组件成熟度 | 高 | ComfyUI、KeyShot、Blender、OpenCV、SQLite 全是成熟件 |
| 集成复杂度 | 中 | 主要复杂度在"相机参数一致性"和"pass 对齐校验"两个点 |
| 环境稳定性 | 中 | Python 3.11 + CUDA 是敏感组合，需锁定版本；ComfyUI 生态插件质量参差 |
| 可测试性 | 高 | 对齐校验可自动化（IoU/diff），成品率可量化 |
| 可回滚性 | 高 | pass 与参数卡可复现，工作流 JSON 可版本控制 |
| 运维负担 | 低 | 单机场景，无分布式依赖 |

**主要工程风险**：插件生态兼容性（ComfyUI 自定义节点更新频繁可能破坏既有工作流）。**对策**：锁定工作流 JSON 版本 + 记录插件版本号。

## 6.3 许可与合规可行性

| 许可类型 | 项目 | 商用可行性 |
|---|---|---|
| MIT | DreamMat、TRELLIS.2、OpenX clay 编排器、blender-mcp 系 | ✅ 可商用 |
| Apache-2.0 | ControlNet、StableMaterials、InstantMesh、BiRefNet、Real-ESRGAN | ✅ 可商用 |
| GPL-3.0 | ComfyUI、BlenderProc | ⚠️ **内部使用没问题**；修改后分发需开源 |
| 非商用 / 学术 | **Hunyuan3D-2.1 权重、Pixal3D、Stable Zero123** | ❌ **商用项目禁用** |
| 商业软件 | KeyShot（已有授权） | ✅ 需确认 Pro 版本覆盖 headless scripting |

**合规风险（独立于模型许可）**：

| 风险 | 说明 | 对策 |
|---|---|---|
| 广告虚假宣传 | 生成图与实物不符（多/少部件、参数标识错误） | 强制与实拍照片比对；关键参数禁止 AI 生成 |

**结论**：许可与合规可行性 **成立，但需要建立强制过滤机制**（选型时先过滤许可、交付前强制合规校验）。

# 七、实用性分析

## 7.1 与传统渲染流程对比

| 维度 | 传统（KeyShot 手动） | 传统（C4D + Octane） | 本方案（AI 辅助） |
|---|---|---|---|
| 单张耗时 | 20–60 分钟（含调材质、灯光） | 1–2 天（含建材质） | 6–30s（生成）+ 10–15s（后处理） |
| 出 20 张候选 | 数小时～数天 | 不现实 | 3–5 分钟 |
| 多风格对比 | 每换一次风格重调一遍 | 极慢 | 换 prompt 一行 |
| 形状保真 | 100% | 100% | 高（靠 ControlNet 锁，非 100%） |
| 材质物理正确性 | 100% | 100% | 中（"像"而非"是"） |
| 多视角一致性 | 天然一致 | 天然一致 | 需固定 seed + 参考图 |
| 可批量 | 需脚本 | 难 | 原生 |
| 成本 | 人力时间 | 人力时间 + 渲染农场 | 边际成本 ≈ 0 |

**结论**：本方案在**速度和批量性**上是碾压性的（差 2–3 个数量级），在**物理正确性**上不如传统渲染。

> **关键判断**：这不是"替代"关系，而是"**分工**"关系 —— AI 负责快速铺量、多风格试错、次要位置配图；KeyShot 负责需要 100% 准确的主图和细节图。正确用法是让两者各干擅长的事。

## 7.2 人工介入点分析（诚实版）

宣称"全自动"是不诚实的。实际必须人工介入的环节：

| 环节 | 人工介入程度 | 能否优化掉 |
|---|---|---|
| 参数卡生成（自然语言 → 卡） | 需复核 | 可通过坐实词表降低频率，不能消除 |
| P0 形准验证 | 必须人工判断 | **不能**，这是主观判断 |
| 批次抽检 | 5% 抽检 | 不能，合规要求 |
| LOGO / 刻度回贴校对 | 首次需校对，后续复用 | 可优化成模板 |
| 特殊 SKU 兜底（透明件、异形件） | 需人工改流程 | 部分可沉淀为专用模板 |
| 词表与预设维护 | 持续投入 | 不能 |
| 成品率统计与复盘 | 需人工归因 | 可半自动化 |

**估算人工占比**：稳态运行下，人工工时约为总工时的 **5–15%**（主要是抽检和异常处理）。P1 阶段这个比例会高于 50%（调参期）。

## 7.3 ROI 分析

以 800 个 SKU 全套（16000 张）为基准：

| 方案 | 成本估算 |
|---|---|
| 本地自建（已有 4090，不含硬件成本） | 电费 + 维护 ≈ 边际成本趋近于 0 |
| 外包摄影修图（¥150–400/张） | **¥240 万 – ¥640 万** |
| 云 GPU 租用（¥1.5–3/小时 × 200–260 小时） | **¥300 – ¥800** |
| 商业 API（Kontext Pro $0.04/张） | **约 $640（¥4600）**，且可控性更差 |

**一次投入（估算）**：硬件（若需新购双 4090 约 ¥4–6 万）+ 人力（约 6 周） + 软件（KeyShot Pro 已有）。

**回本周期**：以"替代 200 张外包图"计，约 ¥3–8 万，**回本周期以周计，不是以年计**。

> **ROI 结论**：这是本项目最有说服力的一点。只要 P0 通过，投入产出比是碾压性的。
> **但注意隐性成本**：调参期的人力黑洞、词表与预设的长期维护。这两项不体现在上面表格里，但真实存在。

## 7.4 与现有工作流的契合度

| 现有资产 / 流程 | 契合方式 | 契合度 |
|---|---|---|
| KeyShot 模型与材质库 | 直接作为 L2 结构层输入 | ★★★★★ |
| KeyShot HDR 环境库 | 直接用于 L2 出 beauty，比 IC-Light 猜光照更可靠 | ★★★★★ |
| 2000 个详情页 PSD | L5 层智能对象占位替换 | ★★★★☆（需建命名映射表） |
| 中英文双版本 | 命名规范带语言位 + 排版留余量 | ★★★★☆ |
| 现有修图/设计流程 | LOGO 回贴环节可无缝接入 PS 脚本 | ★★★★★ |

**结论**：契合度很高，**因为方案是围绕"已有 KeyShot 资产"设计的（ADR-009），而不是要求重建资产**。这是本方案相对"从零搭一套 AI 管线"的关键优势。

## 7.5 适用 / 不适用场景（边界声明）

### 适用

| 场景 | 原因 |
|---|---|
| 次要位置配图、场景化氛围图 | 不要求字体级精度，AI 性价比极高 |
| 多风格快速试错（给客户选方向） | 生成速度是核心优势 |
| 白色/灰色/纯色壳体产品（本类目主力） | 材质简单，AI 表现稳定 |
| 已有白模、需要快速出多视角 | 天然契合 |
| 存量资产批量再生 | 批量化能力碾压人工 |
| 背景替换、场景合成 | AI 强项 |

### 不适用（或需谨慎）

| 场景 | 原因 | 替代做法 |
|---|---|---|
| 需要 100% 精确刻度 / 丝印的主图 | AI 不可靠 | 走图层回贴，或直接用 KeyShot 真渲染 |
| 透明件（亚克力视窗、玻璃）为主体的图 | AI 物理不正确 | 引擎真渲染 + 合成 |
| 镜面金属反射要求严格 | AI 会产生幽灵物体 | 提 normal 权重 + 负向词，或真渲染 |
| 需要标注量程 / 精度 / 认证的图 | 合规风险 | 禁止 AI 生成，必须原图叠加 |
| 极细结构（螺纹、细密网格） | AI 会糊 | 真渲染 |
| 需要视觉冲击力的主视觉大图 | 精度优先级最高 | 真渲染 + AI 只做背景 |

> **这张表是整个方案最重要的"边界声明"**。它决定了哪些需求要交给 AI、哪些必须回退到传统流程。把边界划清楚，方案才是可落地的。

## 7.6 实用性综合结论

| 评估项 | 结论 |
|---|---|
| 效率提升 | **碾压级**（单张 6–30s vs 20 分钟–2 天） |
| 质量可用度 | **大部分场景可用**，关键精度场景需回退 |
| 人工负担 | 稳态下 5–15%，调参期 > 50% |
| ROI | **极高**（回本周期以周计） |
| 与现有流程契合 | **高**（围绕已有 KeyShot 资产设计） |
| 主要实用性风险 | 调参人力黑洞、词表长期维护成本、AI 幻觉导致的合规风险 |

**总结论**：**实用性成立，但前提是把它定位为「效率工具」而不是「替代方案」。** 它的价值在于把 80% 的常规出图从"小时级"压缩到"秒级"，让设计师把时间花在那 20% 真正需要精度和创意的工作上。

# 九、技术基线与参数规范

> 本章参数为**起始基线**，需在实测中校准。任何调整须按留痕规范登记。

## 9.1 L2 Pass 输出规范

| Pass | 用途 | 格式 | 说明 |
|---|---|---|---|
| **Beauty（灰模）** | 底图参考、后续 Canny 来源 | PNG 16bit | 统一 0.8 中性灰，无材质，可保留基础 AO |
| **Depth** | ControlNet Depth | PNG 8bit（归一化）或 EXR | 近白远黑；EXR 更好，可自行归一化 |
| **Normal** | ControlNet Normal | PNG RGB | **必须确认为相机空间**，与训练约定一致（通常 OpenGL：X 右、Y 上、Z 朝观察者） |
| **Alpha / Mask** | 抠图、局部重绘、蒙版限定参考 | PNG 8bit | 主体蒙版必出，省掉后期抠图 |
| **AO / Curvature**（可选） | 强化倒角、缝隙、按键细节 | PNG | 对仪表类产品提升明显 |
| **Lineart**（可选） | 硬结构约束（刻度、棱边） | 后处理生成 | 不额外出，用 Canny/Lineart 预处理器现算 |

**分辨率策略**（ADR-006）：Pass 出 **2048 长边**，成图出 **1024–1536**，交付 **2048–4096**。

**相机参数一致性要求**：KeyShot 与 Blender 必须使用同一焦距、机位、朝向、目标点。**Pass 不对齐 = ControlNet 失效**。

## 9.2 L3 生成基线

| 环节 | 选型 | 参数 |
|---|---|---|
| 底模 | FLUX.1-dev fp8 / Qwen-Image / SDXL-Lightning（快出草稿） | — |
| ControlNet-Depth | FLUX depth 或 controlnet-union-sdxl | weight **0.55–0.75**，end 0.6–0.7 |
| ControlNet-Normal | 对应底模的 normal 模型 | weight **0.35–0.50**，end 0.5–0.6 |
| 参考注入 | FLUX.1-Redux-dev + AdvancedRefluxControl | factor 2–3 |
| 参考注入（备选） | IP-Adapter Plus | weight 0.5–0.8 |
| 重打光 | IC-Light（优先 `fc`） | 见 9.4 |
| 采样 | euler / dpmpp_2m | Flux: steps 20–28, cfg 1.0；SDXL: steps 25–30, cfg 7.0 |
| 高清修复 | latent upscale 1.5x + denoise 0.3–0.4 | 或 Ultimate SD Upscale |
| 放大 | Real-ESRGAN 或 Topaz | 2–4x |
| 抠图 | BiRefNet | 输出带 Alpha |

## 9.3 参数调优顺序（踩坑顺序）

**不要平行调参。** 按此顺序逐层锁定：

1. **先只开 Depth**，权重从 0.60 起，调到"轮廓和厚度关系一眼对"。**这一步不过关，后面全部白搭。**
2. **加 Normal**，权重从 0.35 起，观察曲面高光走向是否合理（金属拉丝方向、球面反射）。**Normal 权重过高会让画面发"塑料感"和"死灰"，超过 0.5 要警惕。**
3. **加参考图**，先低权重（Redux factor 3 / IP-Adapter 0.5），确认只借了影调没借错形状。
4. **最后调 prompt**。到这一步 prompt 只负责材质词和氛围词，**不负责形状**。如果发现要写很长的形状描述才能出对图，说明第 1 步没调好，回去调第 1 步。
5. **打光单独一轮**，用 IC-Light 或直接改 KeyShot 的 HDR 重出 beauty。

## 9.4 IC-Light 定位与坑

IC-Light 是"重新打光"模型，不是"生成"模型。

| 模型 | 用途 | 结论 |
|---|---|---|
| `iclight_sd15_fc` | 纯文本条件，无背景图输入 | **首选** |
| `iclight_sd15_fbc` | 背景条件，有背景图输入 | **已知坑：会把背景颜色"渗"到主体上**，产品图容易出现壳子被染色。遇到就退回 `fc` 并把背景写进 prompt |
| `iclight_sd15_fcon` | 训练加了 offset noise | **不用下**，效果不如 fc |

模型放 `ComfyUI/models/unet/`。

> **更稳的做法**：别用 IC-Light，**直接在 KeyShot 里换 HDR 环境重出 beauty**（ADR-009）。IC-Light 只用在"手里只有一张现成图、要改光"的场景。

## 9.6 参数调整速查表（贴墙版）

| 现象 | 原因 | 调法 |
|---|---|---|
| 轮廓不对 / 厚度关系错 | Depth 权重太低 | depth 0.60 → 0.75 |
| 画面发灰、死塑料感 | Normal 权重过高 或 Depth 过高 | normal 0.50 → 0.35；depth 降 0.05 |
| 高光走向不合理（金属拉丝方向错） | Normal 空间搞错 | 确认是**相机空间**法线，与训练约定一致 |
| 参考图只复刻、不听 prompt | Redux 权重太高 | `downsampling_factor` 1 → 3，或降 `weight` |
| 参考图影响太弱 | Redux 权重太低 | `downsampling_factor` 3 → 1 |
| 背景颜色渗到产品上 | 用了 IC-Light `fbc` | 换 `fc`，背景写进 prompt |
| 刻度 / 文字糊掉 | prompt 里没排除 | 负向词加 `text, numbers, markings`；LOGO 走回贴 |
| 透明件崩 | AI 对透明材质能力不足 | 降低 AI 占比，透明区域用 KeyShot 真渲染合成 |
| 同 SKU 多图不一致 | seed 与参考图漂移 | 固定 seed 基数 + 同一参考图 + prompt 骨架只换风格词 |
| 1536 分辨率爆显存 | ControlNet 数量太多 | 1536 最多叠 2 个；或 1024 出图后超分 |
| 队列卡住不报错 | 节点静默失败 | 读 ComfyUI 终端日志，必设 timeout |

| **批处理写法约束** | 必须 **CRLF 换行 + cp936(GBK) 编码**；分支只用 `if errorlevel` + `goto :label`，**禁用 `\|\|` 和 `&&`**（LF 换行下 `cmd.exe` 会报「此时不应有 ‖」） |

## 10.5 出图台重构（v1.3 新增）

> **本节取代 10.4「六个页面」的导航结构。** 原六页设计在 10.4 与 `web/index.classic.html` 中保留不删，仅作对照。

### 为什么要重构

v1.1 的控制台按**文档章节**组织导航：参数卡 / 提示词引擎 / 任务队列 / 对齐校验 / 项目看板 / 变更记录。它忠实映射了架构分层（L0–L5），但把**「文档结构」误当成了「使用结构」**：

| 症状 | 后果 |
|---|---|
| 出一次图要在 3 个页面之间来回跳（参数卡 → 提示词 → 任务队列） | 操作路径长，形不成「调参 → 出图 → 看结果」的快速循环 |
| 40+ 个表单控件平铺，权重完全相同 | 高频项（颜色、场景）与低频项（IOR、透视）挤在一起，决策成本高 |
| 提示词在独立页面 | 改一个颜色要切页才知道提示词变成什么样，**失去所见即所得** |
| 项目看板 / 变更记录与「出图」混在同一侧栏 | 生产工具里混进管理内容，视觉噪音大 |

参照 TapNow 一类 AI 出图站的电商套图流程（**选风格 → 填少量字段 → 一键生成 → 出图网格**），重构为「一屏出图台 + 抽屉」。

### 新的信息架构

| 层 | 内容 | 设计意图 |
|---|---|---|
| **顶栏** | 品牌 · `出图` / `队列` 两个主 tab · 阶段 chip · 文档 chip · `⋯` 高级 | 主入口从 6 个降到 2 个 |
| **左栏（参数）** | 01 产品 / 02 外观 / 03 场景与光照 / 04 机位与输出 / 05 高级（折叠） | 高频在前，低频折叠 |
| **右侧（出图台）** | 提示词折叠条 → 批次概览 → 结果网格 → 吸底操作条 | 一屏完成「调参 → 生成 → 看结果」 |
| **抽屉 `⋯`** | 对齐校验 / 项目看板 / 变更记录 | 管理类内容移出主流程 |

### 三个「变快」的具体动作

**① 一键预设取代逐项填表。** 这是「快速出图」的核心，也是 TapNow 那类站点的通行做法：

| 预设组 | 数量 | 一次点击改动的字段 |
|---|---|---|
| **材质预设** | 6（黑塑料+铝 / 全铝拉丝 / 高光黑 / 工程黄+黑 / 类肤灰 / 镜面不锈钢） | `material.body.*` + `material.trim.*` 共 8 个字段 |
| **一键场景** | 8（棚拍白底 / 影棚浅灰 / 深色影调 / 桌面场景 / 工地场景 / 车间场景 / 白底无影 / 硬光高对比） | `lighting.scheme` + `background.type` + `background.from` + `background.to` |

预设只是**写入同一张参数卡**，不引入新的数据源 —— 与 ADR-003（参数卡是唯一接口契约）保持一致。预设命中时 chip 高亮，用户仍可继续微调单项。

**② 提示词常驻可见。** 从独立页面降为出图台顶部的一条折叠栏，默认显示当前机位的正向提示词单行摘要，展开看正 / 负向全文。改任何参数即时重拼 —— 仍是程序化拼装，**不提供手写输入框**（ADR-002）。

**③ 任务以卡片网格呈现，而非表格。** 每个机位 × 每个变体 = 一张卡，卡上直接改状态（开始 / 完成 / 失败）。表格视图保留在「队列」tab，用于看 seed、重试次数与 ComfyUI 载荷。

### 交互与视觉约定

| 项 | 约定 |
|---|---|
| 快捷键 | `Ctrl` + `Enter` = 生成；`Esc` = 关闭抽屉 |
| 命中反馈 | 预设 / 机位 chip 选中即主色填充；阶段与文档版本始终可见 |
| 空态 | 结果网格为空时给出三步引导（材质预设 → 一键场景 → 生成），不留纯空白 |
| 校验前置 | SKU 为空或未选机位时生成按钮置灰，并在批次条标红说明，**不做静默失败** |
| 主题 | 浅色中性灰背景。产品图工具用深色 UI 会影响对成图色调的判断 |
| 排序 | 机位选中顺序按 `VIEWS` 键序归一化，保证 `seed = 基数 + 变体号` 的可复现性 |

### 本次一并修掉的缺陷

| 缺陷 | 说明 |
|---|---|
| **`renderAll()` 未定义** | v1.1 中机位复选框的 change 处理器调用了从未定义的 `renderAll()`，点机位会抛 `ReferenceError`：状态被改了但界面不刷新（提示词预览停留在旧机位）。本次以真正的 `renderAll()`（预设态 + 提示词 + 批次 + 底栏）实现 |
| **UI 拼接无转义** | 卡片列表 / 看板 / 坑位表直接拼接后端字符串，本次统一走 `esc()`，避免 SKU 或备注里的 `<` `&` 破坏 DOM |
| **`.empty b{display:block}` 作用域过宽** | 会命中空态段落里的行内 `<b>`，把整句拆成多行。改为 `.empty > b` |

### 自检补充

`selftest.py` 保持 **16 项断言不变**（后端接口契约未变）。界面侧另做了无头浏览器校验：页面零 console 错误、零 page error；点材质 / 场景预设后 `l-scheme` / `b-type` / `m-body-*` 与提示词同步变化；增减机位后批次数量与生成按钮计数一致；生成 16 条任务后网格渲染 16 张卡、tab 角标同步。

界面截图见 `web/preview/`（5 张）。旧版界面保留在 `web/index.classic.html` 可对照。

> **留痕：v1.3（2026-09-19）新增本节，把网页控制台重构为「一屏出图台 + 抽屉」；10.4「六个页面」的导航结构由本节取代，原内容不删除。**

## 10.6 白模投放区（v1.5 新增）

### 为什么要改

v1.3 的出图台把交互简化了，但**「路径」这件事没简化** —— 它仍然是三处手打字符串：

| 症状 | 后果 |
|---|---|
| 「白模路径」是一个纯文本框 | 要自己去资源管理器里找到文件、复制完整路径（含中文目录）粘贴进来，一个人一天做不了几个 SKU |
| pass 图的实际落盘位置藏得深 | 得手工在 `output/passes/` 下建 `<SKU>/<机位>/` 三级目录，还要把文件名改成 `depth.png` / `normal.png` 后端才认 |
| `_pass_dir` 在 `formToCard()` 里被硬编码为 `D:/Dsektop/AI渲染/output/passes/<SKU>` | 换机器、换目录就失效 |
| **双重 SKU 路径缺陷** | `_pass_dir` 已含 SKU，而 payload 里 `depth_img` 又拼了一次 SKU → 实际指向 `output/passes/LS-360G/LS-360G/front/depth.png`。**这条路径永远不会存在**，P0 一旦照此接线必然报「找不到 depth 图」，且极难看出原因 |

一句话：**结构对了，但入口太重。** 所以 v1.5 把「路径」整个收进一个**投放区**。

### 新的约定：一个文件夹解决所有路径问题

```
assets/
├── 白模/                       ← 3D 源文件（.ksp/.blend/.glb/.gltf/.fbx/.obj/.stp/.step/.3dm/.c4d/.max/.rhi/.stl）
│   ├── LS-360G.ksp
│   └── QA-200.blend
├── passes/                     ← 白模渲染出的 pass 图
│   └── LS-360G/                ← 目录名 = SKU
│       ├── front/              ← 目录名 = 机位
│       │   ├── clay.png        ← 文件名 = 通道
│       │   ├── depth.png
│       │   └── normal.png
│       └── 3q4_left/
│           ├── clay.png
│           └── depth.png
└── _待归类/                     ← 认不出来的先扔这儿，绝不丢文件
```

**三种投放方式，效果完全一样：**

| 方式 | 操作 |
|---|---|
| **拖拽** | 把文件或**整个文件夹**拖到出图台的「白模投放」区，自动读子目录结构 |
| **直接拷** | 用资源管理器把文件/文件夹拷进 `assets/` 对应位置（界面提供「打开投放区」按钮） |
| **命令行** | `robocopy` / `cp` 批量灌入，后端每次刷新都会重新扫描 |

> **关键设计：只新增，不删除、不改名。** 同名冲突时默认**覆盖**（重传同一张图是常态），可取消勾选改为自动加 `_2` 序号保留两份。原文件在任何情况下都不会被移动或删除。

### 归类规则（后端一套规则，扫描与上传共用）

**机位别名**（中英混写都认）：

| 标准值 | 认得出来的写法 |
|---|---|
| `front` | front / 正面 / 正视图 / 前视 / 主视 / 正 |
| `3q4_left` | 3q4_left / left / leftfront / 左前 / 左45 / 左三四 / 3q4l |
| `3q4_right` | 3q4_right / right / rightfront / 右前 / 右45 / 右三四 / 3q4r |
| `side` | side / profile / 侧面 / 侧视 / 侧 |
| `top` | top / topdown / 俯视 / 顶视 / 正俯 / 上视 |
| `detail_keypad` | detail_keypad / keypad / 按键 / 键盘 / 面板 / 特写按键 |
| `detail_window` | detail_window / window / 透明件 / 视窗 / 窗口 / 镜片 |

**通道别名**：`clay` ← clay / beauty / rgb / shaded / color / 白模 / 灰模 / 素模；`depth` ← depth / z / disparity / 深度 / 景深；`normal` ← normal / nrm / nmap / 法线；`alpha` ← alpha / mask / 蒙版 / 遮罩。

**SKU 推断 —— 有证据才用，没证据就听用户填的：**

| 路径形态 | SKU 来源 |
|---|---|
| `<SKU>/<机位>/<通道>.png` | 目录名直接当 SKU（最可靠） |
| `<SKU>_<机位>_<通道>.png` | 文件名剥离机位/通道词后的剩余部分 |
| `<机位>/<文件>` | 机位目录取机位，SKU 用界面上填的 |
| `裸文件名.png`（如 `depth.png`、`我的图.png`） | **一律用界面上填的 SKU** |
| 名字里完全没有线索（`新建文件夹/`、`毫无线索.png`） | 进 `_待归类/`，并在界面上提示改名 |

> ⚠️ **一个刻意的保守设计**：`guess_sku` 只在「确实剥离过机位/通道词」时才返回结果。否则 `IMG_0231.png` 会被当成一个叫 `IMG-0231` 的 SKU，界面上凭空多出一堆假 SKU —— **这比认不出来更糟**，因为认不出来的会被明确列出来，假 SKU 会静默污染队列。

## 12.3 通用 QC 标准（每批必查）

**结构**

- [ ] 与白模叠图 diff，轮廓偏移在阈值内
- [ ] 按键 / 旋钮 / 接口 / 刻度盘**数量和位置**正确
- [ ] 厚度关系正确（不能把圆柱拉成方的，不能丢倒角）
- [ ] 无多余部件、无融合畸变

**材质**

- [ ] 金属件有合理的高光走向，不是"画上去的反光"
- [ ] 磨砂件的颗粒感合理，不是均匀噪点
- [ ] 透明件有折射和边缘高光，不是半透明色块
- [ ] 无"背景颜色渗到产品上"

**合规（重点）**

- [ ] **生成图与实物照片对比，无结构性差异**
- [ ] 量程 / 精度 / 认证标识 / 型号 **禁止由 AI 生成**，必须原图叠加
- [ ] 无 AI 幻觉出的功能部件（实物没有的东西不能出现）
- [ ] 无异国文字乱码
- [ ] 不出现他人品牌 / 商标

**交付**

- [ ] 分辨率 / 色彩模式 / 命名符合规范
- [ ] 文件已按类目 / SKU 归档
- [ ] 版本号递增，旧版未覆盖

## 12.4 常见失败模式速查

| 症状 | 最可能的原因 | 第一个该动的地方 |
|---|---|---|
| 形不准、整体"胖了/瘦了" | Camera 参数不一致 或 Depth 权重低 | 先查 pass 对齐，再提 depth 权重 |
| 局部结构错乱（按键多了少了） | Depth/Normal 权重平衡问题 | 提 normal 到 0.45+，看是否锁定 |
| 金属像塑料 | Normal 权重过高、Normal 空间错 | 降 normal，**核对相机空间法线** |
| 透明件变成灰块 | AI 对透射材质能力不足 | 别硬刚，改走"真渲染合成" |
| 参考图完全不起作用 | Redux 权重太低 | `downsampling_factor` 3 → 1 |
| 参考图把形状带歪了 | Redux 权重太高 或没做蒙版限定 | 降权重，或改 L2 + 蒙版 |
| 同款多图风格漂 | seed / 参考图不固定 | 固定 seed 基数 + 同一参考图 |
| 批次跑到一半整体变差 | 某张 pass 生成失败，串了数据 | 检查 pass 目录完整性，加文件校验 |
| 队列静默卡住 | 节点 CUDA 报错未通过 API 返回 | 看 ComfyUI 终端，必设 timeout |

## 14.1 先把「AI 渲染方式」摊开：五条可行路线

原始诉求里「AI 渲染」是一个模糊词。把所有可落地的方式穷举后，实际只有 **5 条路线**，它们的差别不在「效果好不好」，而在**「结构由谁负责锁定」**：

| 代号 | 路线 | 结构由谁锁定 | 需要本地 GPU | 本项目中的定位 |
|---|---|---|---|---|
| **R-A** | **本地自建 ComfyUI**（原方案主线） | ControlNet Depth/Normal，pass 自己出 | ✅ 需要（8G 显存起） | **基准线，主链路** |
| **R-B** | **3D 材质线**（模型上真 PBR 再真渲染） | 3D 几何本身，天然 100% 锁定 | ✅ 需要（材质生成那一步） | P3 可选增强 |
| **R-C** | **云端图像 API 直连**（文生图 / 图生图 / 指令编辑） | 只能「松约束」，**绝大多数不接受 depth/normal** | ❌ 不需要 | v1.4 新增，**辅助 pass** |
| **R-D** | **托管 ComfyUI**（把我们自己的工作流原样部署成 API） | ControlNet，**与 R-A 完全相同** | ❌ 不需要 | v1.4 新增，**关键发现** |
| **R-E** | **引擎云渲染**（KeyShot / 云渲染农场） | 真 3D 光照渲染，100% 锁定 | ❌ 不需要 | 透明件 / 镜面件的兜底通道 |

> **一句话概括这五条路线的分工**：
> **R-A / R-D 负责形状，R-C 负责质感，R-B / R-E 负责「AI 搞不定的那部分」。**

## 14.2 核心判据：能不能「锁形」，是选型的唯一硬门槛

这是本次调研**最重要的一张表**，也是决定「纯 API 方案是否成立」的关键。判断依据来自第 4.4 原则（像素级对齐）与 P0 验收指标（`align_check.py` IoU ≥ 0.90）。

| 服务 / 模型 | 接受 depth/normal 结构图？ | 结构保真度 | 能否单独满足 IoU ≥ 0.90 |
|---|---|---|---|
| **ComfyUI + ControlNet**（R-A 本地 / R-D 托管） | ✅ depth / normal / canny / lineart | ★★★★★ 像素级 | ✅ **能** |
| **FLUX.1 Depth [pro] / [dev]** | ✅ **depth**（原生 control 模式） | ★★★★☆ | ✅ **能**（API 侧唯一选项） |
| **FLUX.1 Canny [pro] / [dev]** | ✅ canny（仅边缘） | ★★★☆☆ | ⚠️ 边缘锁得住，**丢厚度信息**，只能当补充 |
| FLUX.1 Kontext [pro] / [max] | ❌ 只接受图像 + 文本指令 | ★★☆☆☆ 布局近似 | ❌ 不能 |
| FLUX.1 Redux | ❌ | ★★☆☆☆ 复刻参考图 | ❌ 不能 |
| Gemini 2.5 Flash Image（Nano Banana） | ❌ | ★★☆☆☆ | ❌ 不能 |
| Gemini 3 Pro Image（Nano Banana Pro） | ❌ | ★★☆☆☆ | ❌ 不能 |
| OpenAI GPT Image 1 / 1.5 / 2 | ❌ | ★★☆☆☆ | ❌ 不能 |
| 通义千问 Qwen-Image-Edit（阿里百炼） | ❌ | ★★☆☆☆ | ❌ 不能 |
| 火山 Seedream 5.0（即梦） | ❌ | ★★☆☆☆ | ❌ 不能 |
| 腾讯混元生图 | ❌ | ★★☆☆☆ | ❌ 不能 |
| KeyShot 云 / Deadline Cloud（R-E） | ✅ N/A（真渲染，几何本身） | ★★★★★ | ✅ **能** |

### 结论（直接回答用户的疑问）

> **「纯调 API、完全不碰 GPU」这条最省事的路，在本项目的类目上是不成立的。**
> 因为 90% 的图像 API 都是「**看图说话**」型 —— 它们把输入图当作**语义暗示**，不是**几何约束**。你给它一张白模图 + 一句「不锈钢外壳」，它会还你一张**长得像但不是同一台仪器**的漂亮图。
>
> **唯一的两个例外：**
> 1. **FLUX.1 Depth [pro] API** —— 官方 control 模式，接受 depth map，可在一次调用里同时完成「锁形 + 上材质」。单价约 $0.05–0.06/张。这是**纯 API 路线里唯一能过 P0 的方案**。
> 2. **托管 ComfyUI（R-D）** —— 把我们第 9 章那套 ControlNet 工作流原样上传，按 GPU 秒付费。能力与本地 ComfyUI **完全等价**，只是从「买显卡」变成「租显卡」。

以 **L40S @ $2.99/h** 为例，单张图（含上传 pass、ControlNet + FLUX 采样、返回）实测约 **15–25 秒**：


## 14.10 本次新增架构决策

### ADR-011 主链路的锁形环节不上公共图像 API

**决策**：形状锁定只能由 ControlNet（R-A / R-D）或 FLUX.1 Depth（R-C1）承担，**禁止**用 Kontext / Redux / Nano Banana / gpt-image / Seedream / Qwen-Image-Edit 承担主 pass。

**原因**：这四个系列均不接受 depth/normal 输入，形状靠语义猜测，无法满足 4.4 的像素级对齐，会导致 P0 验收（IoU ≥ 0.90）失败。

**代价**：无法使用「一句 prompt 出图」的极简链路。

### ADR-012 引入供应商抽象层，而非绑定单一 API

**决策**：所有外部模型调用统一走 `provider adapter`，暴露 `submit(workflow, inputs) / poll(task_id) / download(result)` 三个方法。R-A 本地 ComfyUI、R-D 托管、R-C 各家 API 都实现同一接口。

**原因**：云厂商调价与下架频繁（FLUX 系列一年三降、多家模型已 deprecate）；具体工作流的节点 schema 也在变。抽象层让「换一家」变成改配置，而不是改业务代码。

**代价**：多一层间接，调试时多跳一次。

### ADR-013 无显卡环境下用「托管 ComfyUI」而非「图像 API」替代本地算力

**决策**：需要临时扩容或在不具备 GPU 的机器上跑批时，**优先选 R-D（RunComfy / RunPod / Modal）**，而不是改用 R-C 图像 API。

**原因**：R-D 单张成本（≈¥0.12）**低于**几乎所有图像 API 直连（¥0.28–0.43），且能力与本地完全等价、无需重写工作流。

**代价**：需要把 workflow 导出为 API 格式并上传，存在冷启动延迟。

# 十五、本机运行可行性（v1.6 新增）

不把现状钉死，后续就会按 4090 的节奏做工期规划 —— 然后全线延误。本章先把这台机器测清楚。

## 15.3 结论一：能装，且不需要配环境

| 组合（1024px） | 峰值显存 | 8GB 结果 | 单张耗时（本机预期） | 4090 级参考 |
|---|---|---|---|---|
| SD1.5 + ControlNet（512） | ~7GB | ✅ 可跑，但分辨率低 | 20–40s | — |
| SDXL 底模 | ~8GB | ⚠️ 临界，需 `--lowvram` + 分块 VAE | 20–40s | — |
| **SDXL + 1~2 ControlNet** | 10–14GB | ⚠️ 靠卸载硬撑 | **60–120s** | 6–10s |
| FLUX GGUF Q4 底模（无 CN） | ~7GB | ✅ 可跑但慢 | 90–150s | — |
| **FLUX + 1 ControlNet** | **20–22GB** | ❌ **基本不可用**（swap，5–15min 或直接失败） | — | 18–30s |

> ⚠️ **数字陷阱（务必记住）**：6.4 节与第 9 章的「SDXL+2CN+IPAdapter = 6–10s」「FLUX dev fp8+2CN+Redux = 18–30s」是 **4090 级**数据。**本机需按 5–10 倍折算**，直接引用会严重误判工期。

**本机现实产能**：走 **SDXL + depth 单 ControlNet** 路线 ≈ **60–120s/张（1024）**；1000 张 ≈ **17–33 小时**连续跑。

## 15.5 结论三：卡住商用的不是画质，是许可

| 模型 | 许可 | 本机商用可用性 |
|---|---|---|
| **FLUX.1 [dev]** | **非商用许可** | ❌ **本地下载权重出的图不可商用**（ADR-008 否决） |
| FLUX.1 [schnell] | Apache-2.0 | ✅ |
| FLUX.2 Klein 4B | Apache-2.0 | ✅ |
| SDXL 基座 | CreativeML Open RAIL++-M | ✅ 可商用（有使用限制） |
| SDXL 社区写实底模（Pony Realism / RealVisXL / Juggernaut…） | **各不相同** | ⚠️ **必须逐个核** |

> 这条最容易踩：**「本地跑 FLUX」听起来最香，但下的是非商用权重**（且第 14 章推荐的 Replicate FLUX.1 Depth [pro] 之所以能商用，是因为走的是 BFL 的商业服务，许可由服务方承担）。本地商用要换 schnell / Klein。

**本机质量天花板**：SDXL 写实底模 + depth/normal 双 ControlNet，1024 下产品图可达「可交付」，配 BiRefNet 抠图 + Real-ESRGAN 超分（本机均可跑）。**达不到** FLUX 一次成型的高级感与包装小字清晰度 → **本机出的是「稳」，不是「惊艳」**。

## 15.6 结论四：「中转站」有两种，结论完全相反

> **本章最关键的一条。混为一谈必然得出错误结论。**

| 维度 | 本机 8GB（SDXL+CN） | 中转站①＝图像 API 聚合 | 中转站②＝托管 ComfyUI（R-D） |
|---|---|---|---|
| 观感 / 质感 | 中上 | **更好** | 好（FP8 无量化损失） |
| **锁形（depth/normal）** | ✅ 像素级 | ❌ **完全不接受** | ✅ **同一套 ControlNet** |
| 单张速度 | 60–120s | 秒级 | **15–25s** |
| 1000 张耗时 | 17–33h | — | **4–7h** |
| 1000 张成本 | ¥20–50 | ¥280–430 | **¥120–190** |

**读法①（图像 API 聚合：Nano Banana / GPT-Image / Seedream / MJ 转售等）**
它出的图「更好看」是事实，但**在本项目里是无效优势**。第 4.1 原则是「保真优先于美观」，P0 验收线是 **IoU ≥ 0.90** —— 它连 depth/normal 都不收，**形状锁不住，一张都过不了**。第 14 章已论证 R-C 单独使用不可行（ADR-011）。

**读法②（托管 ComfyUI）**
**不会「不够优质」。** 它跑的是**同一套工作流**，只是显存从 8GB 变 48GB（L40S），因此：更快、更稳、能叠更多 ControlNet（1536 可叠 2 个）、**且 FP8 无量化损失 —— 画质只升不降**。

> → **真正「不够优质」的对比，是「8GB 比 4090 级本地机」，而不是「本地比托管」。**

## 15.7 结论五：本机的定位

| 项 | 结论 |
|---|---|
| **能承担** | P0 形准验证、参数调试、小批量打样（几十张） |
| **不承担** | 量产跑批（1000 张要 17–33 小时） |
| **量产通道** | R-D 托管 ComfyUI（¥0.12/张，快 4–5 倍） |
| **是否需升级显卡** | **不需要**。本机当「控制台 + 打样机」，托管当产能 |

**推荐路径：A（本机跑通 P0）→ B（本机打样定参 + 托管跑批）**

## 15.8 前提与风险

- ⛔ **前置动作仍是 P0 形准验证**（第 12 章 + 附录 E 第 1 项）。本机 8GB 够做验证；**这一步不过，后面所有投入都是白费。**
- 🟠 本机 8GB 跑 SDXL+ControlNet 依赖 `--lowvram` 与内存卸载，**稳定性未经实测**，须在 P0 阶段记录失败率并回填 15.4（见附录 E 第 20 项）。
- 🟠 32GB 内存是 FLUX 路线的硬前提；若同时跑 KeyShot / Photoshop，须注意内存竞争。
- 🟡 本机单卡串行，**并行度只能靠「先出 1024 草稿筛选、只对选中项超分」来换**（沿用 ADR-006）。

> **留痕：v1.6（2026-09-19）新增本章。依据本机硬件实测（RTX 4060 Ti 8GB / i5-14600KF / 32GB DDR5 / 无 git-pip 环境）。核心结论：① 用官方便携版可免环境配置部署；② 8GB 只能走 SDXL + depth 单 ControlNet，FLUX + ControlNet（峰值 20–22GB）不可用；③ FLUX.1 [dev] 权重为非商用许可，本地商用须换 schnell / Klein；④「中转站」须区分「图像 API 聚合」（锁不住形，无效）与「托管 ComfyUI」（同工作流、更快更优）；⑤ 本机定位为验证/打样机，量产走 R-D。新增 ADR-014。**

### 工程坑清单（都踩过，写脚本时别改回去）

1. **`curl.exe` 的 `-o` 必须给 Windows 路径** —— `-o /f/xxx/a.bin` 会 **`http=206` 但 `bytes=0`、文件不落地**（静默失败，日志只有一行 `Failed to open the file`）。必须写 `F:/...` 或 `F:\...`；`stat` / `sha256sum` 也认 `F:/`，可全脚本统一。
2. **`ghfast.top` 对完整 GET 返回 0 字节，只放行 Range** → GitHub 资产必须**分块 Range 下载再拼接**。
3. **不要用 `-o /dev/null` 量速度**（会报 0 字节，误判成断网）；要写真实文件再取长度。
4. **本机 `rm` 被「安全删除」拦截会静默失败**（同一轮删除数超过 50 即触发），会造成「以为删了旧文件、其实把新数据追加到旧文件后面」的**隐蔽损坏**。清空文件请用**截断**（`> file` / `: > file` / `FileStream.Create`），别依赖 `rm`。
5. **大文件分块 Range 方案不可靠**：实测同一文件 8 路并发分段，**个别分块「尺寸正确但内容错误」**，且「首/尾 1MB 抽样比对」抓不住中间段损坏 —— 最终靠**整文件 SHA-256** 才暴露。
   → **纪律：大文件优先「完整 GET + 续传」；只有源站拒绝完整 GET 时才分块，且分块后必须做全文件哈希校验。**
6. **下载期间不要并发测速**：3 个大文件并行时，新起的测速请求 25 秒内拿到 0 字节，结论完全失真。
7. **后台任务跨会话不会自动清理**：上一轮遗留的下载任务会继续跑、抢带宽、往同一个日志写。排查下载异常**先查残留进程**。

## 16.4 P0 判据重写（本次最有价值的产出）

### 为什么必须改写

原 P0 把「AI 能不能锁住形状」当作**唯一一票否决项**，于是**整个项目悬在一根线上**。
mac 分支指出了一条更稳的路：**让 AI 根本不碰产品**。那么「锁形」就不再是前置条件，而只是「背景质量」的参数。

### P0-A · 结构优先链路（**硬门槛，低风险**）

**动作**：KeyShot 出产品本体（透明底 PNG + alpha）→ AI 出 3 张背景候选 → 合成。

**判据**：

| # | 项 | 标准 |
|---|---|---|
| 1 | **产品像素保真** | 与 KeyShot 原图**逐像素完全一致**（diff = 0）。不是 IoU 0.90 —— 因为产品根本没经过 AI |
| 2 | alpha 合成质量 | 边缘无白边 / 黑边（预乘 alpha 处理正确） |
| 3 | 接触阴影 | 连续、无明显接缝 |
| 4 | 格式 | 分辨率 / 色彩空间 / 命名符合规范 |

**通过 → 拿到保底产能，业务可跑。** 风险极低，因为它不验证任何 AI 能力。

### P0-B · 创意探索链路（**升级项，高风险**）

**动作**：只开 Depth ControlNet、prompt 不含形状词，对产品本体做受控图生图。

**判据**：沿用原标准 —— 肉眼「一眼辨认为同一产品」+ **IoU ≥ 0.90** + 关键结构点核对。

**通过 → 可对产品本体做受控改造，用于外观探索 / 无实物渲染的场景。**

> **这个重排的意义**：原方案的 P0 是「不过就停」；新方案是「**先拿到 A 的保底产能，再逐步争取 B**」。项目不再被单一风险点绑架。

## 16.5 从 mac 分支吸收的 8 项

2. **确定性基线可独立交付 + `baseline_completed`**（→ ADR-016）

## 16.9 新增决策记录

### ADR-015 默认采用「结构优先」模式，AI 不生成产品本体像素

**决策**：默认模式下，产品本体的最终像素来自确定性渲染（KeyShot / Blender），AI 仅负责背景、氛围与允许区域。

**原因**：把 P0 的唯一一票否决风险从「全链路」压缩到「仅背景」；透明件 / 镜面 / 丝印 / 刻度 / 量程 / 认证标识**天然正确**，不再需要单独的兜底通道。

**影响**：5.2 的 L2/L4 重新定义；第 11 章 P0 拆为 A/B 两级；创意探索降为可选模式。

### ADR-016 确定性基线为可独立交付产物

**决策**：AI 阶段不可用或被跳过时，任务以 `baseline_completed` 结束并照常交付基线渲染，**不得标记为 AI 成功**。

**原因**：2000 个详情页是持续业务，不能因 AI 服务波动而停摆。且报表必须能区分「AI 成功」与「仅基线交付」。

### ADR-017 全 pass 走工件清单 + 哈希 + 显式色彩空间与坐标约定

**决策**：L2 每个产物必须登记 `artifact_manifest.json`，含逻辑名、文件名、MIME、尺寸、色彩空间、坐标约定、SHA-256、上游工件。缺少必需工件或元数据**即在进入 L3 前失败**。

**原因**：缺元数据则 P0 结论不可复现。数值型控制图（depth/normal/alpha/objectID）**不得套用摄影图像的色彩变换**。这是 12.4「金属像塑料」头号根因的正解。

### ADR-018 KeyShot 与 Blender 分工：KeyShot 出产品本体与材质，Blender 出控制图与几何处理

**决策**：KeyShot 负责产品本体 beauty 与材质表现（复用既有材质库）；Blender 负责 depth / normal / alpha / objectID、接触阴影与反射承接、CAD-网格转换与几何检查。**两者必须使用同一套相机参数**（焦距 / 机位 / 朝向 / 目标点）。

**原因**：用户真实资产与客户认可度在 KeyShot；而控制图、AOV、法线空间与几何处理在 Blender 更可控且免费可脚本。原 ADR-009 只分了「beauty vs pass」，未覆盖几何处理与合成承接，本 ADR 补齐。

### ADR-019 云端图像 API 分层使用，且不硬编码模型名

**决策**：按用途分档调用（背景 → 低价档；终稿 → 高价档）；优先使用 **Batch 档**（约半价）；模型 ID 全部走 provider adapter 配置，**不写进代码**。

**原因**：本次复核发现原方案引用的两个模型已下线或即将下线 —— 硬编码模型名会直接导致线上失效。分层 + Batch 同时压低成本。

> **留痕：v1.7（2026-09-24）新增本章。对 `ai渲染mac/` 平行方案（经 Codex with ChatGPT 审阅）做 15 项逐项裁决：吸收 8 项、保留 5 项、合并 2 项。最重要产出为 **P0 判据重写为两级**（P0-A 结构优先低风险硬门槛 / P0-B 创意探索高风门升级项），把项目的单一否决风险拆解掉。同步复核出原方案引用的两个 API 模型已下线或即将下线，并新发现 Gemini SynthID 水印风险。新增 ADR-015~019。**

# 十九、参考图接入（v1.10 新增）

## 19.1 三条路线与裁定

「接入参考图」在 ComfyUI 生态里有三条互斥的技术路径。本节按 **许可（ADR-008）→ 硬件 → 收益** 的顺序逐条裁定。

| 路线 | 原理 | 许可 | 本机可行 | 裁定 |
|---|---|---|---|---|
| **① IPAdapter Plus** | CLIP-Vision 图像编码 → 交叉注意力注入，可分别调「风格 / 材质 / 构图」 | 插件 `cubiq/ComfyUI_IPAdapter_plus` 是 **GPL-3.0**，且作者 2025-04-14 起声明**仅维护**；权重 `h94/IP-Adapter` 是 **apache-2.0** | ✅ SDXL 可用，**8GB 实测未爆** | ✅ **已落地（v1.11）** —— 插件与 ComfyUI 0.37 **兼容正常**（35 个节点全出）；GPL 按「本地工具」对待（与 ComfyUI 本体同理，不注入产出物）。详见 19.4 / 19.6 |
| **② FLUX Redux** | `StyleModelApply` + Redux 权重，风格迁移强 | **Redux 权重属 FLUX.1 [dev] 家族＝非商用** | ❌ 8GB 跑不了 FLUX + ControlNet（15.4 已测：20–22GB） | ⛔ **否决** —— ADR-008 一票否决，硬件也不允许 |
| **③ 视觉特征提取** | 读参考图的**配色 / 影调**，翻成提示词里的材质与配色词 | 无第三方依赖 | ✅ 立刻可用 | ✅ **本轮落地** |

> **关键判断**：本文档 §三.3 要求「参考图**只借视觉特征**（材质 / 配色 / 光照 / 构图），**参考产品的形状不自动替换**源白模」。
> 路线 ③ 恰好是这条原则**最忠实的实现** —— 它从物理上就无法替换形状。路线 ① 才是「把图片送进模型」的那条，但需要付出插件与显存代价。

## 19.2 本轮落地：视觉特征提取（怎么用）

在「形照」控制台的 **第 2 步「描述想要的效果」** 里新增了「参考图」区块：

1. **上传参考图** → 存进 `assets/refs/<SKU>/`（**只新增不覆盖**，重名自动加序号）；
2. 浏览器内用 canvas 采样（96×72）→ 量化出 **6 个主色**（含占比）+ 计算**平均明度**与**背景亮度**；
3. 自动生成影调描述，例如背景亮度 >200 → `high-key lighting`，<70 → `low-key dramatic`；
4. 选择**参考强度**（三档，ADR-005 要求显式选择）：
   - `L1_style` → 只借「氛围与光感」
   - `L2_material` → 借「材质、配色与表面处理」（默认；参数卡自动带 `target_part`）
   - `L3_full` → 借「材质、配色、光照与构图」，仍声明不改形状
5. 点任一色块可**直接设为主体色**；出图时提示词里会追加一段，例如实测输出：

> `Borrow materials, colour palette and surface finish from a supplied reference photo. Its dominant colour palette is #828282, #787878, #292929, #181917. clean mid-grey seamless background, soft studio lighting. Do not copy the reference product's silhouette; keep the supplied product shape.`

**实测**（用 `F:\ID设计-杨\GF望远镜改款\渲染图\GF.29.jpg`）：提取到 `#828282`(69.9%)、`#787878`(14.3%)、`#292929`(7.7%)、`#181917`、`#306B2C`(屏幕绿)、`#505050` —— 与肉眼判断一致。

## 19.3 边界（界面如实标注，不假装）

- ✅ **图片已真正参与条件注入**（v1.11 起）：装了 IPAdapter 后，`_meta.reference.applied` 会从 `prompt_palette_only` 变为 **`ipadapter+prompt`**，参考图经 CLIP-ViT-H 编码后注入交叉注意力。**界面会如实显示当前是哪一种**，不会假装已生效。
- ⚠️ **不改形状**：提示词里固定带 `Do not copy the reference product's silhouette`；与 §三.3、ADR-015 一致。**且形状的最终约束来自 ControlNet 的深度/法线图**，参考图只影响材质与配色。
- ⚠️ **不改形状**：提示词里固定带 `Do not copy the reference product's silhouette`；与 §三.3、ADR-015 一致。
- 参考图落在 `assets/refs/`，与 `白模/` `passes/` `_待归类/` 并列，同样受「只新增、不删除、不改名」铁律保护。

# 二十、统一网页复审与批量出图优化（v1.12）

## 20.1 审查结论与设计边界

当前真正运行的是 `AI渲染/web/`：`启动控制台.bat` 与 `启动全部.bat` 均启动同一 `web/server.py`，旧版单文件界面归档为 `web/index.v17.html`，`AI渲染/ui/` 和外层 `ui/` 只作设计对照。因此本轮不再创建第二个网页服务，而是在同一个「形照」工作台里继续收敛流程。过程文档记录的方案不等于运行能力，能力判断以当前 `web/` 代码和接口为准。

原版主流程已涵盖白模导入、材质/光照、参考图、深度与法线、ComfyUI 出图、任务/结果、参数卡和轮廓对齐；但主表单每次只生成一个视角，和产品白模多机位交付不匹配；参考图抽屉仍写“尚未接入控制节点”，与 v1.11 已接入 IPAdapter 的运行状态相冲突；断线文案仍提示已废弃的“启动新版UI.bat”。这些是本轮优先修复点。

## 20.2 GitHub 对照与吸收原则

## 20.3 本轮设计与实现

1. 「预览视角」只决定主画布当前显示的机位；「出图范围」可选当前视角或正面、左前 3/4、右前 3/4、侧面四个标准机位。默认仍为当前视角，降低新手负担。
2. 批量结构约束模式逐机位查深度图；缺失时禁用出图并列出具体机位。法线图缺失只警告。候选张数按每个机位计算，按钮显示本次总张数。
3. 提交载荷按每个机位各取自己的深度/法线，不复用预览机位的数据；结果区在四机位模式展示同一产品的跨机位任务。
4. 参考图说明随服务实际检测结果变化；已装 IPAdapter 才说图像条件注入，未装时仅说配色和影调进入提示词。移除裸露在用户界面里的 Markdown 符号和 ADR 编号。
5. 补主内容跳转、预览/缩略图固有尺寸、参考色板按钮可读名称、抽屉内部滚动约束，并修正断线后的启动入口。
6. IPAdapter 探测失败不再永久记为“未安装”（失败缓存 5 秒，成功缓存 60 秒）；网页每 30 秒刷新一次服务状态和参考图能力说明。

## 20.4 验证与未决项

- 静态语法：`node --check web/app.js`；隔离服务 HTTP：待本轮验收记录回填。
- 关键手测（Windows 主机待做）：四机位齐备 pass 时按 1 张/机位创建 4 张任务；任一机位缺 depth 时阻止提交并列出机位；IPAdapter 在线/离线时分别核对参考图说明；断开 ComfyUI 时核对恢复提示。
- 本轮没有运行 RTX 4060 Ti 实机生成，也没有证实跨 4 机位的质量、速度和显存占用。长批次目前仍由网页前端串行轮询；浏览器关闭后需到任务抽屉手动续跑/更新，后续应移到后端持久队列。

| **IoU** | 交并比，用于量化轮廓重合度 |
| **ΔE** | 色差指标，ΔE < 3 通常人眼难以分辨 |
| **headless** | 无界面运行模式 |
| **depth map / 深度图** | 每个像素记录到相机距离的图，ControlNet 用它锁形体轮廓与厚度 |

| **provider adapter** | 供应商抽象层，屏蔽各家 API 差异（见 ADR-012） |
| **按 MP 计费** | 按百万像素计费，与「按张」口径不同，不可直接比较 |
| **便携版 / Portable** | v1.6 引入。ComfyUI 官方 Windows 独立包，自带嵌入式 Python 3.13 + PyTorch CUDA，解压即用、**无需 git / pip**，是「本机无开发环境」时的低摩擦路径（见 15.3） |
| **GGUF / 量化** | 把模型权重压到更低精度以降低显存占用。FLUX.1 dev 的 Q4_K_S ≈ 6.8GB、Q5_K_M ≈ 8.3GB，代价是轻微质量损失（见 15.4） |
| **显存预算** | 一个工作流同时常驻的**所有**组件的峰值显存之和：底模 + VAE + 文本编码器 + ControlNet + LoRA + 工作缓冲。**本机上限 8GB**（见 15.4） |

# v3.1 渲染、多视角与 CMF 优化大纲

> 2026-09-28 · 方案文档，**尚未实现**。基线：`origin/main` 的 `e0f182c`。本文件供 Windows 执行端拆任务与验收，不替代正在进行的 R2 `AI/TASK.md` / `AI/RESULT.md`。

## 0. 阅读口径与目标

- **CODE**：在上述提交中可从代码核对的实现事实。
- **WINDOWS-REPORT**：过程文档中的 Windows 实机观察；本次 Mac 端未复跑显卡/视觉测试。
- **PROPOSED**：待实施的设计方案，不表示产品现已具备。
- **GATE**：要收集的可复核证据，通过后才可升级为项目事实。

当前代码进度已超过 `AI/MASTER_CONTEXT.md` 标称的 v3.0、`AI/DECISIONS.md` 标称的 v2.4；这两份文件仍提供架构约束，但新功能是否存在以当前代码为准。坚持 ADR-002（标识、刻度、认证信息、透明件不能由 AI 臆造）与 ADR-015（面向生产的产品主体优先确定性真渲染；AI 重绘主体仍是实验路线）。用户想要的终态是：**选模型 → 选六视图或特写 → 自动出对应白模/深度/法线 → 按部件指定 CMF → 选设计/布光方案 → 预览并生成 → 对照质检**。图片改图保持独立入口，不能假装从单张图推出真实六面。

## 1. 六视图预览到六套结构图：先打通操作链

### 现状与根因

**CODE**：`web/app.js` 已有 `SIX_VIEWS`、`VIEW_ANGLES_3D` 和六个预览机位；`scripts/blender_pass.py` 的 `VIEW_ANGLES` 也可对这些机位逐一生成 pass。后端 `web/server.py` 的 `start_pass(sku, view)` 每次只启动一个机位并检查产物。问题不是深度图技术上只能有一个面，而是**预览相机、出图选择器、结构图任务尚未闭环**：`setCameraToView()` 只移动 Three.js 镜头；`makePass()` 却取 `selectedView()`（普通视角下拉框），没有取刚点的六视图按钮。`web/index.html` 的普通视角下拉框还缺 `side_left`。自由旋转的 OrbitControls 姿态也未保存或提交。当前预检发现多个机位缺深度时，仍提示用户逐个生成。

同样重要：角度相同**不等于像素完全对齐**。Three.js 预览使用自己的透视镜头、缩放与中心点；Blender pass 用另一套镜头/取景。过程文档中“3D 里摆好的角度就是出结构图的角度”只可解释为**预置方向映射**，不能解释为“点击即生成”或“任意旋转即完全同画面”。

### P0：固定六视图先可用

1. 建立唯一机位表 `config/view_presets.json`，含 `key/中文名/方位角/仰角/分组/可渲染`；服务端做权威校验，网页从接口读取，Blender 接收明确角度（内部表仅作回退/自检）。消除 JS、服务端和 Blender 的三份重复定义。
2. 六视图按钮写入持续的 `cameraViewKey`，同步普通视角选择；把 `side_left` 加入下拉框。“生成此视角结构图”明确取当前预置机位，不再暗中取旧选择。
3. 增加“生成六视图结构图”按钮，后端接受一个视角数组，**顺序**执行现有 Blender 出图及 `verify_pass_outputs()`，避免 8 GB 显卡上六个 Blender 进程并发。任务状态显示 `当前/总数/成功/失败`，支持逐机位重试、取消与继续；不要靠网页连续发六次请求碰当前单任务锁。
4. 每个机位独立保存 clay、alpha、depth、normal、object ID 和 manifest，并记录模型指纹、机位参数、分辨率、生成时间；模型或参数变化后标记旧 pass 失效，禁止混用旧深度图。

**P1**：自由旋转先明确标“仅预览”；如确需自由机位出图，再设计“保存为自定义机位”，保存角度、投影、镜头参数、目标点及模型归一化数据，给它独立名称与目录，不伪装成六个固定机位。

**GATE**：六个机位都能从网页提交并逐项获得非空产物；同机位 clay/depth/normal/object ID 尺寸一致，manifest 角度等于机位表；`side_left` 在正常 UI 可选可运行；六机位完成后多视角预检不再报缺深度。Windows 再对六组“三维预览截图 ↔ Blender 白模”人工核方向、朝向、主体占比与遮挡；截图若含客户产品，不上传公开仓库，只提交脱敏测试记录。

## 2. 按部位渲染：从“点中部件”变成真正工作流

### 现状与边界

**CODE**：网页可射线点选、高亮模型部件；`scripts/objectid_mask.py` 可由同机位的 16 位 `objectid.png` 按 ID 导出掩膜；后端在收到 `base_img` 与 `mask_img` 时有 inpaint 工作流，使用深度/法线控制。但网页尚未把“部件 ID → 指定机位掩膜 → 底图 → 局部任务”串起来，`web/app.js` 没有提交这两个字段；点选不等于已可一键分部位换材。当前部件查询未传 `view`（`web/app.js`），后端会回退到第一个可用 manifest（`web/server.py`），因此页面显示的部件 ID 不保证与后续所选机位的 object ID 图一致。`config/comfy_workflow_sdxl_inpaint.json` 的默认遮罩扩张固定为 6 像素。**WINDOWS-REPORT**：v3.1 记录了 object ID 饱和修复、部件拾取及导出掩膜的 Windows 观察；尚未发现已提交的局部 inpaint 实跑或画质验收记录。

### P0：可控、可追溯的局部编辑

1. 记录明确状态 `{sku, view, partId, partName, baseImageId}`。部件名常是无语义编号，只用于显示；任务身份绑定 `模型/pass 指纹 + 机位 + manifest 内部 partId`，不把数字 ID 当作跨模型替换、重新导入或重生成后仍稳定的全局身份。部件列表请求明确传 `/api/model/parts?sku=...&view=<当前机位>`。
2. 提供服务端“生成部件掩膜”接口：限定路径在项目目录，要求该机位 manifest、object ID 文件及模型指纹匹配，确认 ID 存在且可见像素大于零；不匹配即拒绝；输出到隔离工作区，绝不改写源 CAD、旧 pass 或已有候选图。
3. 在点中部件后显示三个主要动作：“选材质/颜色/纹理”“预览选择区域”“生成局部候选”；提交载荷必须带同机位的 base、mask、depth、normal。若视角不一致、部件不可见、底图缺失或结构图过期，直接报可读错误。
4. 局部编辑底图优先选**已完成的产品候选图或确定性真渲染图**；每次接受结果可作为下一次底图，形成可回退的版本链。白模作为底图只用于明确标注的实验模式，否则未选区域仍保持白模，不能算完成整机换材。

### P1：小部件质量提升

掩膜取外接框并按部件尺寸留边；对底图、掩膜、深度、法线裁同一 ROI，适度放大给局部生成，再缩回。最后由程序**只在掩膜及羽化边内**合成到原底图，边外像素严格保留，不依赖模型“自觉不改”。扩张/羽化与部件尺度成比例，不全用固定 6 像素。极小按钮、孔边、镜圈等分别测，不把外壳大块结果套到全部部件。透明件、标识、刻度仍走真渲染/回贴，不能纳入 AI 局部批准。

**GATE**：ID 对应的掩膜非空且视角正确；四张输入尺寸/相机一致；输出掩膜外与所选底图逐像素相同；点选一个部件不得改到相邻件。Windows 对小/中/大部件、塑料/金属/橡胶等多材料、至少两个随机种子比较“全幅局部重绘 vs ROI”，保留逐样本评分和失败案例，不只报平均分。人工检查边界、材质串色、新增孔/螺丝/文字。

## 3. 可直接选择的材质、纹理与 CMF

### 现状

**CODE**：`web/app.js` 的 12 种材质主要是英文提示词，`web/index.html` 另有固定选项；当前正向提示词主要一次性套一个材质、一种颜色。参数卡记录粗糙度/金属度等元数据，但不是一套可给每个网格真实赋材的系统；三维预览当前以统一白色材质展示，尚无纹理贴图选择。不能把“文字材质选项”称为已实现的完整 CMF。

### P0：一个结构化预设库，简单入口

新增 `config/cmf_presets.json` 作为唯一数据源，预设字段建议：`id、中文名、材料基体、表面处理、默认色、粗糙度、金属度、纹理/法线图与比例、纹理方向、工艺、提示词片段、是否允许 AI 编辑、预览参数`。界面先只露出“推荐组合 / 材料 / 颜色 / 表面纹理”，高级参数折叠；先提供不依赖品牌的“深灰细砂纹塑胶、喷砂阳极铝、拉丝不锈钢、哑光橡胶”等通用组合。工艺字段描述**如何表现已有几何**，不可暗示增加实体筋条、倒角或新开孔。

参数卡保存预设 ID、版本及覆盖项，能精确回读。三维预览可近似展示，但要标“效果预览”；真正生产图片要由 Blender/其他确定性渲染器按同一 CMF 分配赋材。可参考 [glTF `KHR_materials_variants`](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_materials_variants/README.md) 做同几何多外观预览，参考 [MaterialX](https://github.com/AcademySoftwareFoundation/MaterialX) 组织可移植材质定义；是否引入依赖须单独核许可和 Windows 兼容性。

### P1：按部件指定 CMF

支持“外壳、饰圈、握持区、按键、镜圈”等**用户可命名分组**，按 `partId → cmfPresetId + 可选颜色覆盖` 保存；导入文件的部件名常只是编号，不自动猜语义。预览仅改选中网格；局部候选只使用该部件 CMF；透明件、标识和认证信息路由到确定性渲染。可将一整套分配保存为可复用“CMF 方案 A/B/C”。

**GATE**：预设 JSON 校验、ID 唯一；HTML/JS/参数卡不再维护冲突的材质列表；卡片保存再打开后 ID 与覆盖项不变；切换机位后部件分配不串位；预览只改目标网格，局部任务拿到同一材料定义；透明/标识预设走禁止 AI 或确定性路径。

## 4. 更强的设计感与工艺美感：产品主体真渲染为主

**CODE**：当前只有三类背景、四类泛化布光，以及较概括的“高端商业产品摄影”提示词；缺少明确的设计语言、工艺层级和针对工业产品的验收词表。这里的画质瓶颈不只在采样步数。更大图或更强 API 也不能自动保证孔位、丝印和表面工艺准确。

**PROPOSED**：增设独立于 CMF 的 `config/design_presets.json`，可选“精密仪器、户外耐用、实验室设备、克制高端工业极简”等通用设计语言。每套只定义布光、机位、背景、材质反射组织、边缘高光、阴影与细节优先级，不“设计”CAD 中不存在的结构。工艺表现重点为现有倒角的高光、注塑表面细纹、按指定方向的金属拉丝、材质交界、真实接触阴影；负面约束增加“假通风孔、假螺丝、额外缝线、伪刻字、玩具感、颗粒过大”等。

推荐两条明确模式：

| 模式 | 产品主体 | AI 的职责 | 使用场景 |
|---|---|---|---|
| 保真成品（优先） | Blender Cycles/现有可用真渲染器按 CMF 确定性渲染，保留 alpha/对象 ID/阴影 | 背景、氛围与非主体区域；必要时局部实验稿 | 电商主图、客户确认、批量生产 |
| 外观探索（明确标实验） | 白模 + 深度/法线约束或已有候选底图 | 试新材料、视觉方向、局部候选 | 早期概念，不可免质检交付 |

从快速白模预览到高质量真渲染分档，不把 4060 Ti 8 GB 的显存一次占满。`00-AI白模渲染器-过程文档.md` 记录的 1536/2048 显存与速度为 **WINDOWS-REPORT**，尤其 2048 贴近上限，须在 Windows 同模型、多视角、多种子复验后才给默认值。布光建议提供“大柔光箱+轮廓边光”“白底电商”“深灰技术展示”“局部工艺特写”等可选方案；颜色与输出用一致的色彩管理配置，防止预览和导出颜色漂移。可借鉴 [BlenderProc](https://github.com/DLR-RM/BlenderProc) 的多机位/多通道批处理思路、[OpenColorIO](https://github.com/AcademySoftwareFoundation/OpenColorIO) 的色彩管理与 [ComfyUI 局部重绘文档](https://github.com/Comfy-Org/workflow_templates/blob/main/site/knowledge/concepts/inpainting.md) 的工作流组织；这些是参考，不代表已接入，也不绕开项目许可约束。

**GATE**：盲评同一模型的旧版/新版，分开记“几何与细节准确、材质可信、工艺层次、灯光可读、整体设计美感、电商可用性、臆造数量”；给原始逐样本记录、失败例和评价人数，不预设无来源的万能分数线。保护产品原图与模型，公开 GitHub 仅放脱敏样本 ID、参数、统计与结论。

## 5. 横向缺陷、优先级与 Windows 执行顺序

**P0 一致性缺陷**：`web/app.js` 定义“精细=20 步、最高=32 步”，但 `web/index.html` 可见文案为“精细 24 步、最高 40 步”。先统一真实参数与文字，再做画质实验；否则评价记录中的档位不可复现。另须将 `web/app.js` 里“六视图=正交六面/相同角度即相同出图”的注释改成准确的“方向预置”，以免误导开发和验收。

| 顺序 | 交付 | 最小可验收结果 |
|---|---|---|
| P0-1 | 统一机位表、六视图与视角选择联动、六 pass 后端顺序队列 | 六面均可从网页生成且预检通过 |
| P0-2 | 修质量档文案与参数、记录任务真实参数 | UI 展示与任务日志一致 |
| P0-3 | 部件 ID → 同机位掩膜 → 局部任务入口 | 能指定一个可见部件并可回退 |
| P0-4 | 单一 CMF 预设库与参数卡回读 | 选择、保存、恢复同一方案 |
| P1-1 | 候选底图版本链、ROI 局部重绘、确定性掩膜合成 | 非编辑区像素不变，局部质量 A/B 有记录 |
| P1-2 | 按部件 CMF 与三维近似预览、设计/布光方案 | 多材料方案在 UI 可操作且不改几何 |
| P2 | CMF 驱动真渲染、批量质检和跨 SKU 试验 | 生产用途按几何、工艺、标识逐项验收 |

这份大纲仅授权下一轮拆解，不把任何 P0/P1/P2 记作“已交付”。后续实施每次先登记根目录过程文档“二、变更记录”，再修改代码、记录 Windows 实机结果并接受另一台电脑复审。现有 R2 交接文件不在本轮改写范围内。

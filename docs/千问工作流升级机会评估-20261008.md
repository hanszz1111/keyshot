## 二、★ 最值得做的一项：本项目缺一个采样 shift 覆盖节点

### 事实（用 ComfyUI 自身代码跑出来的，不是推算）

ComfyUI 0.37.0 给 Qwen-Image-2.1 内置了一个**固定** shift：

```python
# comfy/supported_models.py
class QwenImage21(supported_models_base.BASE):
    # scheduler mu at 1024x1024 (base 0.5 @ 256 tokens, max 0.9 @ 8192)
    sampling_settings = {"multiplier": 1.0, "shift": 0.69}
```

而官方 ComfyUI **每一个** Qwen 模板都在采样前插一个 `ModelSamplingAuraFlow` **覆盖它**：

| 官方模板 | `ModelSamplingAuraFlow` | KSampler |
|---|---|---|
| Image Edit (Qwen 2509) | **3** | 4 步 / cfg1 / euler / simple |
| Image Edit (Qwen 2511) | **3.1** | 40 步 / cfg4 / euler / simple |
| Text to Image (Qwen-Image) | **3.1** | 8 步 / cfg1 |
| Text to Image (Qwen-Image 2512) | **3.1** | 50 步 / cfg4 |
| Image Inpainting (Qwen-image) | **3.1** | 4 步 / cfg1 |
| Image Outpainting (Qwen-Image) | **3.1** | 4 步 / cfg1 |

**本项目的工作流没有这个节点**，因此用的是内置的 0.69。

> 顺带确认：`euler` + `simple` 就是官方的选择，**本项目这点没错**，缺的只是 shift 覆盖。
> ⚠️ 若要自己插这个节点：它的**自身默认值是 1.73**，官方模板填的是 3.1 —— 默认值大概率不是你要的。

### 数值后果（用 `comfy.model_sampling` + `simple_scheduler` 真跑，25 步）

| 调度 | σ[1]（第 2 步） | σ[12]（中段） |
|---|---|---|
| **本项目现状**（无覆盖，shift=0.69） | 0.9431 | **0.4278** |
| 官方 ComfyUI 模板（shift=3.1） | 0.9867 | **0.7706** |
| 官方 diffusers（992×608，mu=0.6058） | 0.9778 | **0.6650** |

**中段差 0.34（相对本项目 +80%）**：本项目在高噪声区停留的时间远少于两个官方参考，
采样一开局就快速降噪。这类差异通常表现为**结构先糊掉、细节补不回来**。

### 边界（为什么不直接改默认）

1. 上表那些模板是给 `Qwen-Image-Edit-2511` / `Qwen-Image(1.0)` 的，**不是 2.1 专属**。
2. ComfyUI 给 2.1 写的 0.69 也许是有意校准过的。
3. 因此本文只主张**「值得用同种子做单变量对照」**，不主张「现状是错的」。

**验证成本**：插入节点前后各出一张，同输入同种子，一张约 22 秒。

## 三、其余三项能力缺口

### 3.1 文本编码器精度（**已测，结论是否定**）

社区与官方模板都用 INT8（`qwen3vl_8b_int8_convrot`），本项目用 4bit（`w4a8`）。
曾假设「4bit 削弱指令跟随」，已做 2×2 交互对照证伪 ——
交互比 0.78，且代价是 +27% 耗时与 95.3% 显存峰值。
**结论：维持 w4a8**。详见 [A/B 记录](AB实验-千问提示词与CFG首轮记录-20261008.md) 第二轮章节。

### 3.2 LoRA 不能直接合并进 int8 权重

社区自定义节点的源码注释直接指出了这个问题：

> `LoraLoaderModelOnly` merges it into the weights instead: on bf16 weights round-to-nearest
> keeps only ~70% of this LoRA's update, **on int8 weights the stochastic requantization keeps
> all of it but adds noise ~4x its size.**

本项目的 UNet 正是 **int8**。所以将来**只要用任何 LoRA**（提速 / 扩图 / 一致性），
都应走**运行时旁路**（`y = Wx + BAx`），不要用 `LoraLoaderModelOnly` 合并。
> 该结论来自社区作者注释，**本项目未自测**。

### 3.3 `QwenImage21Cache` 是核心节点但本项目没接

`comfy_extras/nodes_qwen.py` 里的核心节点，控制 Qwen 编辑链路的 **KV cache 设备与精度**：

> `device`: auto / gpu / **cpu** / off —— cpu 把 cache 放内存、在计算背后预取，几乎不掉速；
> `dtype`: default / **int8** / int4 —— int8 约等于 bf16 精度但 cache 减半。

本项目 8GB 显存实测峰值已到 95%，`resolution` 被压在 768。
**把 KV cache 挪到 CPU 有可能腾出显存跑 896/992**，且不改模型、不加插件。

## 四、社区工作流里的两项本项目完全没有的能力

### 4.1 高分局部编辑（掩膜裁切 + 缝合）

节点构成（已从工作流 JSON 确认）：

```
DrawMaskOnImage（掩膜）
  → InpaintCropImproved（裁到掩膜区，ensure minimum resolution 1024×1024）
  → 千问编辑（等于「局部放大后再编辑」）
  → InpaintStitchImproved（缝回原图）
  → easy imageColorMatch（调色，消接缝色差）
  配合 Qwen21-无位移一致性 consistency LoRA（保证未编辑区不位移）
```

**与本项目现状对比**：SDXL 链路上已有等价实现（`scripts/roi_crop.py` +
`scripts/composite_masked.py`，掩膜外逐像素还原、自检最大差 = 0），
但**千问链路上完全没有掩膜能力** —— 这正是方案里 P1 的核心缺口。

### 4.2 扩图

`ImagePadForOutpaint`（向外补灰边）+ outpaint LoRA
（触发词 `Outpaint the image: replace the solid gray areas with a seamless continuation...`）。
对电商详情页有实际价值（换背景、延长画幅）。

## 八、Krea-2 评估（2026-10-08 追加）

> ## ⚠️ 本文这一节的「关键结论」已被后续核实推翻，见下方「八·修正」小节
> 下面保留原始判断过程（**错误的是结论，不是过程** —— 错在只看了模板清单，
> 没去追「风格参考」那条链路的实际接线）。

本机 ComfyUI **0.37.0 已原生支持 Krea-2**（有蓝图、模板与 `comfy/ldm/krea2/` 实现），
因此顺手评估它对本项目是否有用。

### 官方提供什么（`Comfy-Org/Krea-2`，license = `krea-2-community-license`）

| 类别 | 文件 | 大小 |
|---|---|---|
| 主模型 | `krea2_turbo_nvfp4` | **7.15 GiB**（最小） |
| | `krea2_turbo_int8_convrot` | 12.57 GiB |
| | `krea2_turbo_fp8_scaled` | 12.24 GiB |
| | `krea2_turbo_bf16` | 24.48 GiB |
| | （另有 `krea2_raw_*` 同规格，即非 turbo 版） | 同上 |
| 文本编码器 | `qwen3vl_4b_fp8_scaled` | 4.88 GiB |
| VAE | **`qwen_image_vae`** | 0.24 GiB |
| 风格 LoRA | `krea2_style_reference` 等 11 个 | 各 0.43–0.44 GiB |

> 架构上它与本项目**同源**：VAE 就是 Qwen-Image 的 VAE，文本编码器也是 Qwen3-VL（4B，比现在的 8B 小）。

### ★ 关键结论：**它做不了本项目的核心活**

ComfyUI 为 Krea-2 只提供两类模板：

- `image_krea2_turbo_t2i`（+ `_int8`）—— **文生图**
- `image_krea2_turbo_int8_image_style_reference` —— **风格参考**

**没有 edit / inpaint / ControlNet 模板。** 核对实现后确认「风格参考」走的是
`LoadImage` + `LoraLoaderModelOnly(['krea2_style_reference', 1])` ——
即**用 LoRA 教风格**，参考图并没有送进主生成链路。

模型内部**确实存在 `ref_latents` 通路**（`comfy/ldm/krea2/model.py:310-329`，
支持 `ref_method="index_timestep_zero"`，与 Qwen-Image-Edit 同源），
但 ComfyUI **没有为 Krea-2 暴露任何编辑模板或专用节点**（`nodes_krea.py` 里只有云端 API 节点）。
→ 也就是说：**做「参考图编辑」属于要自己开发，不是即插即用。**

### 与本项目需求对照

| 项目需要 | Krea-2 现状 |
|---|---|
| 按结构图/白模**保形编辑**（核心） | ❌ 无编辑通路 |
| 深度/normal ControlNet 锁形 | ❌ 无 |
| 局部掩膜重绘 | ❌ 无 |
| 背景/氛围生成 | ✅ 可以（turbo 更快） |
| 借参考图风格 | ✅ 可以，但项目已有 IPAdapter |

### 另外两条要注意的

1. **许可是自定义的** `krea-2-community-license`，**不是 MIT/Apache**。
   按 [ADR-008] 的口径（商用只选 MIT/Apache），**商用前必须先读 LICENSE.pdf**。
2. **体积上它反而更轻**：最小组合 `7.15 + 4.88 + 0.24 ≈ 12.3 GiB`，
   低于当前 INT8 Qwen 2.1 组合的 `6.76 + 8.71 + 0.63 ≈ 16.1 GiB`。
   若将来要腾 8GB 的余量，**Krea-2 nvfp4 值得纳入候选**（但前提是它能做我们需要的活）。

### 结论

**暂不接入。** 理由是能力不匹配（无编辑/无 ControlNet），而不是质量或速度问题。
若将来只做「纯背景生成」，可以用它换速度；但那不是本项目的瓶颈。
**先解决许可问题再谈任何商用用途。**

## 八·修正：**Krea-2 能做参考图编辑**，我上一节的判断是错的

上面那句「它做不了本项目的核心活」**不成立**。错在**只看了模板清单，没追接线**。

### 怎么查错的

回头把官方 `image_krea2_turbo_int8_image_style_reference.json` 的实际连线打出来，发现它用的是：

```
LoadImage（参考图）
  → TextEncodeQwenImageEditPlus(clip, vae, image1, prompt)   ← 与 Qwen-Image-Edit 同一个节点
  → FluxKontextMultiReferenceLatentMethod(reference_latents_method="index_timestep_zero")
  → CFGGuider → SamplerCustomAdvanced
```

**也就是说，官方那个「风格参考」模板走的就是 `ref_latents` 参考图编辑通路**，
参考图是**真的送进主生成链路**的；「风格参考」只是它配的用途（再叠一个
`krea2_style_reference` LoRA），**不是它的能力上限**。

### 三处代码互相印证

| 位置 | 内容 |
|---|---|
| `comfy/ldm/krea2/model.py:310-329` | `ref_method = kwargs.get("ref_latents_method", …)`；`ref_latents` 非空时把参考 token 拼进图像序列；`"index_timestep_zero"` 分支专门处理 |
| `comfy/model_base.py` → `class Krea2.extra_conds` | **显式**把 `reference_latents` 编码为 `ref_latents` 并 `CONDList` 转发给模型；`memory_usage_factor_conds = ("ref_latents",)` |
| `comfy_extras/nodes_qwen.py` → `TextEncodeQwenImageEditPlus` | 收 `clip/prompt/vae/image1..3`，构造 `ref_latents`，并用 Qwen3-VL 先描述图像再拼指令 |

所以「ComfyUI 没为 Krea-2 暴露编辑节点」这个说法也是错的 ——
它暴露的是**通用节点**，Krea-2 直接复用 Qwen-Image-Edit 那套。

### 复核结果（节点存在性已全部确认）

本机 8190 实例 `/object_info` 逐个查，11 个节点全部存在；
`CLIPLoader.type` 的可选值里**包含 `krea2`**。

### 已搭好的实验件（未接入生产）

| 文件 | 作用 |
|---|---|
| `config/comfy_workflow_krea2_edit.json` | Krea-2 参考图编辑工作流（API 格式）。采样取自官方 t2i int8 模板：**8 步 / CFG 1 / euler / simple / denoise 1** |
| `scripts/krea2_probe.py` | 探针：先做权重与节点前置检查，再提交一次并把图落到 `outputs/`。**不写任务库、不碰引擎列表** |

Krea-2 的内置采样设置：`shift 1.15` / `multiplier 1.0` / `latent_format Wan21` /
`memory_usage_factor 2.2`。

**★ 值得注意**：Krea-2 Turbo 只有 **8 步**，而项目现在跑 Qwen 2.1 是 **25 步**。
若两者画质可比，这是约 **3 倍**的步数优势 —— 但这需要实测，不能凭步数下结论。

### 修正后的结论

**Krea-2 是项目主链路的一个真实候选**，而不是「只能做生图」。
需要实测才能定的三件事：

1. **保形能力**：参考图编辑能不能守住白模的轮廓/孔位/分模线 —— 这要拿
   [最佳效果执行文档](Qwen-Image-2.1-最佳效果执行文档-20261008.md) 的验收口径打分。
2. **8 步 vs 25 步**：画质是否等价。
3. **显存**：Krea-2 Turbo INT8 主模型 12.57 GiB，比现在的 Qwen 2.1 INT8 组合更重；
   但最小组合（nvfp4 7.15 + qwen3vl_4b 4.88 + qwen_image_vae 0.24 ≈ 12.3 GiB）更轻。

**许可仍是硬门槛**：`krea-2-community-license`，非 MIT/Apache，
按 ADR-008，商用前必须先读 LICENSE.pdf。**这一条与技术能力无关，但不解决就不能商用。**

## 九、Krea-2 编辑探针实测（2026-10-08）：**通路成立，但 int8 版不可用**

上一节说「能做编辑」只是读代码的推断。这里是**真机跑出来的结果**。

### 跑通了

按 `config/comfy_workflow_krea2_edit.json` 提交，**5 次全部成功**（同一参考图/两个种子/两个画幅）：

| 运行 | 画幅 | 步数 | 种子 | 耗时 |
|---|---|---|---|---|
| 首次（含 12.57 GiB 磁盘加载） | 1024×1024 | 8 | 43 | 53.8 s |
| 稳态 | 1024×1024 | 8 | 1234 | 36.7 s |
| 稳态（3q4_left 机位） | 1024×1024 | 8 | 43 | 40.1 s |
| **同画幅公平对比** | 992×608 | 8 | 43 | **30.2 s** |
| 同画幅 | 992×608 | 8 | 1234 | 64.2 s（离群，见下） |

**几何确实守住了**：机身轮廓、镜头环与内圈、凹槽面板、底部 USB-C 口都在。
这一点上它与 Qwen-Image-2.1 表现相当。

### ★ 但 int8 版有严重臆造纹理，**两个种子都消不掉**

输出表面覆盖一层**规则块状/马赛克点阵**，背景还散落同类碎块。
**换种子（43 → 1234）后依旧存在** → 这不是采样噪声，
而是**该 int8 量化版本本身**的问题。

同时产品明显偏浅（提示词要求 `#3a4148` 深灰板岩），背景也不干净。

对照：`qwen3vl_8b_w4a8`/`int8` 那套上从未出现此类规则块状伪影。

### 速度：**3 倍步数优势在实际使用中被抵消**

| | Krea-2 Turbo | Qwen-Image-2.1 |
|---|---|---|
| 步数 | **8** | 25 |
| 同画幅（992×608）单张 | **30.2 s** | 30.2–36.5 s |
| 主模型大小 | 12.57 GiB | 6.76 GiB |
| 显存峰值 | **7554 MiB（92.3%）** | 7805 MiB（95.3%） |

**步数少 3 倍，但墙钟时间基本相同** —— 被更大的主模型与 `ref_latents` 前缀开销吃掉了。
（1024×1024 时 Krea-2 明显更慢：36.7–40.1 s vs Qwen 在小画幅下的 30 s。）
唯一确定的收益是**显存峰值略低**（92.3% vs 95.3%）。

> 那个 64.2 s 的离群值：前一次运行用的是 1024×1024，改成 992×608 触发了 VRAM 重新 staging。
> 单次计时的波动主要来自 staging，不是采样本身。

### 踩到的坑：工作流 JSON **不能带 `_` 前缀的注释键**

第一版把说明写成了顶层 `_comment` / `_why` / `_status` / `_sampling`，提交直接
**HTTP 500「Server got itself in trouble」**（没有任何有用的报错）。
剥掉后立刻变成可读的 **400 + 指出具体节点**。
→ **给 ComfyUI API 工作流加注释只能在文档里写，不能塞进 JSON**。
（项目现有的 5 个工作流都是纯格式，这个坑是新增文件时才踩到。）

### 结论与下一步

**通路成立，几何能力可用，但这个 int8 权重不能用于生产。**

要继续评估，只剩一个便宜且合理的动作：**换 `krea2_turbo_fp8_scaled`（12.24 GiB）**。
理由：伪影的形状（规则块状）非常像量化缺陷，而 fp8 通常比 int8 保留更多精度；
bf16（24.48 GiB）在 8GB 上不现实；nvfp4（7.15 GiB）在 40 系卡上支持情况未知。

**✅ 哈希已于 2026-10-09 补验通过**：三个权重的 sha256 与官方 LFS oid **逐字符一致**
（`krea2_turbo_int8_convrot` `8e4eeda7…`、`qwen3vl_4b_fp8_scaled` `54bd5144…`、
`qwen_image_vae` `a70580f0…`）。文件取自 ModelScope 的同一仓库，内容与官方一致。

**许可仍是硬门槛**：`krea-2-community-license`，非 MIT/Apache。

### 12.3 但「更好」这件事**没有得到证明**

**文生图路径**（见 `outputs/_SDXL探针/三联对比-SDXL工业LoRA.png`）：

**ControlNet 路径**（项目真正用的那条，见 `CN路径对比-含白模.png`）：
- 几何**守住了**：②③ 的轮廓、凹槽、分模线都与白模 ① 一致 ✓
- 但 LoRA 的主要作用是把**中央颜色由橙改成红、蓝环加深** —— 属**材质/色调位移**，
  **不是结构或设计语言的创新**。而且「橙→红」本身谈不上更好。

→ **诚实结论**：这张 LoRA 能跑、能控强度、几何不坏，
**但它解决不了「整体设计的创新度」**。要判断它对「材质感」有没有净收益，
必须在**多 SKU × 多机位**上做 0–2 分盲评，本轮没做。

### 12.4 「设计创新度」这条路的现状

到目前为止试过的所有外部模型（千问侧 5 个 + SDXL 1 个 + Viggle 6 步）：

| 方向 | 结论 |
|---|---|
| 千问平台换文本编码器 / 调 shift / 调 CFG / KV cache | 都**不影响**设计感（效应量远小于种子噪声） |
| 千问 2.1 原生 LoRA | 生态太薄，**没有**提升设计感的 |
| 千问 2511 LoRA | **一律静默失效** |
| SDXL 工业设计 LoRA | **生效且可控**，但主要改色调，**不改设计** |
| Viggle 6 步 | 只提速，不改设计 |

→ **「设计创新度」目前靠换模型/LoRA 是走不通的。** 它更可能来自
**输入侧**（白模/CMF 方案本身的造型、配色与分件）与**提示词之外的设计语言约束**，
而不是出图引擎的参数。**这条值得单独立项讨论，不该继续在模型上试。**

**未做**：多 SKU × 多机位盲评；SDXL LoRA 在 0.3–0.5 低强度段的摸底；设计预设体系的重构。

## A. 当前未解决的问题（按优先级）

### P-01【高】`AI渲染1` 的 CMF 覆盖率只有 **25.84%**

| | |
|---|---|
| **现象** | 八面合计前景 2,196,659 像素、可见部件 **744 个**，而方案只指派了 **4 个**。占比最大的 `物体.2526`（**19.19%**，8/8 机位可见）**根本没被指派**；`物体.2527` 11.08%、`物体.2488` 6.79%、`物体.2500` 5.82%、`物体.2509` 4.23% 也都没指派。 |
| **影响** | **74.16% 的前景像素使用主体材质**。这些区域中哪些本应使用其他材料，必须看原产品和材料意图；当前数字本身不能证明渲染错误或画质收益。 |
| **根因** | 方案只做了 4 个部位；系统里**没有「覆盖率」这个指标**来提醒这件事，所以一直没人发现。 |
| **当前状态** | 数据已产出（`outputs/_CMF重指派/逐部件统计-AI渲染1.csv`，744 行；该 CSV 未入公开仓库，外部复审不能独立核验逐行数值）。 |
| **建议** | ① 展示“显式指派比例”和“使用主体材质比例”，不设置通用 ≥90% 门槛；② 提供占比大的未指派部件清单与高亮定位；③ 对确需不同材质的部件由用户确认后批量绑定。 |
| **需要谁定** | **用户**（哪个部件配什么材质）。 |

### P-02【高】`渲染3` 的目录里有 **5 种不同模型内容**

| | |
|---|---|
| **现象** | `渲染3` 共 8 个 `.3dm`，其中 **5 种不同内容**（`6e03b706…`/`af8c9539…`/`824887fa…`/`4a54d63b…`/`d7eebc66…`）。现有八面 pass 记录的 `渲染3_8.3dm` 与 `_6`/`_7` 同哈希，**所以现有八面是自洽的**。 |
| **影响** | 下次做这个 SKU 的材质实验，**挑不同文件会得到不同结果**，而且事前看不出来。 |
| **根因** | 保存次数产生的多版本，内容确有分歧。 |
| **建议** | 首轮实验暂用现有八面 pass 记录的模型**内容哈希**作固定基线，保留其他文件原样；若要改变实际设计版本，再由用户选定并另起系列。 |
| **需要谁定** | 基线可从现有八面清单读取；改变产品设计版本需要用户决定。 |
| 对照 | `AI渲染1` 32 个文件只有 **1** 种内容；`渲染444` 2 个文件也只有 **1** 种 —— **版本风险只在 `渲染3`**。 |

## B. ★ 已撤回 / 已解决 —— **不要再追这些**

这几条我们反复过，其中两条是我判断错误造成的。列在这里是为了**防止下一轮又去排查它们**。

| # | 曾经的结论 | 现状 |
|---|---|---|
| B-1 | 「CMF 方案与 pass 不是同一个模型版本」（E0 的 B2） | ❌ **撤回**。`AI渲染1` 的 **32 个 `.3dm` 文件 SHA-256 全同**（`08ba3012e49f10b7bf78…`）。文件名在变（保存次数），内容一模一样。**"选定唯一权威 .3dm"这一步不需要。** |
| B-2 | 「方案分配的 4 个部位在 10 个机位全不可见」 | ❌ **撤回**。正确读取下，单机位可见 **325–392** 个、八面共 **744** 个部件，**4 个分配部位全都可见**（`物体.2491` 还是合计像素第 2 大）。 |
| B-3 | 「设计语言写法的改动落在背景 / 未分配部件上」 | ❌ **撤回**。front 的变亮像素 **83.1% 落在 `物体.019`（分配部位之一）**，背景只占 5.2%。 |
| B-4 | 「`objectid.png` 是 8 位、ID 被压成 10 个桶」 | ❌ **撤回**。文件**本来就是 16 位**（读 IHDR 第 25 字节 `bit_depth=16`）。看着像 8 位是 **PIL 读 16 位 RGBA 时静默降位**造成的。 |
| B-5 | 「B1：现有 PBR 底图不可追溯」 | ◐ **部分解决**。Windows 报告称 `渲染3` 与 `渲染444` 各 8 机位、同一 `scene_id`、`fresh` 8/8；原缓存未包含渲染脚本内容。本分支补签名后还需重出并核验，不能把原记录当作完整可追溯。 |
| B-6 | 「抽样读 objectid 会漏细部件」 | ✅ **已修**。`visible_object_ids()` 改全像素 + numpy 连续数组；实测同图从 **26 → 63** 个可见 ID（旧抽样漏 59%）。 |
| B-7 | 「16 位解码精度没验证」 | ✅ 合成夹具测试已提交；Windows 报告称两路在 10/10 机位一致，但原 `_crosscheck_ids.py` 只输出 Blender 一侧。**本分支已补真正的逐 ID 比对**，仍需在 Windows 真机复跑并回填摘要。 |
| B-8 | 「自检的清理任务表警告」 | ⚠️ Windows 复测未见；Mac 上一次独立运行曾出现且最终 93/93。SIGPIPE 只是猜测，尚无根因证据；按环境与完整日志再定位。 |

**根因更正**：B-1（仅凭文件名推断版本）与 PIL 无关；B-2/B-3 的部件可见性和变化落点误判与 16 位 PNG 被降位有关；B-4 是错误读取位深的直接后果。
详见 [`docs/更正记录-PIL位深误导导致的两处错误结论-20261010.md`](更正记录-PIL位深误导导致的两处错误结论-20261010.md)。
**正确做法：用 `scripts/objectid_mask.py::read_ids()`（项目自带 16 位解码路径，需 numpy，不经 Pillow 降位）。**

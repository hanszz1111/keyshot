## A. 当前未解决的问题（按优先级）

### P-01【高】`AI渲染1` 的 CMF 覆盖率只有 **25.84%**

| | |
|---|---|
| **现象** | 八面合计前景 2,196,659 像素、可见部件 **744 个**，而方案只指派了 **4 个**。占比最大的 `物体.2526`（**19.19%**，8/8 机位可见）**根本没被指派**；`物体.2527` 11.08%、`物体.2488` 6.79%、`物体.2500` 5.82%、`物体.2509` 4.23% 也都没指派。 |
| **影响** | **74.16% 的画面走主体材质** → 本该多材质的产品看起来接近单色。这是「材质感不够」最直接的来源之一，且**比换模型见效快**。 |
| **根因** | 方案只做了 4 个部位；系统里**没有「覆盖率」这个指标**来提醒这件事，所以一直没人发现。 |
| **当前状态** | 数据已产出（`outputs/_CMF重指派/逐部件统计-AI渲染1.csv`，744 行，含每机位像素数与可编辑/太小状态）。 |
| **建议** | ① 把「CMF 覆盖率」做成一个可见指标（例：门槛 ≥ 90% 前景像素被指派）；② 提供「未指派但占比大」的**待指派清单**，让人直接点材质；③ 默认未指派件走主体材质是合理的，但要在界面上写明"这部分未指定材质"。 |
| **需要谁定** | **用户**（哪个部件配什么材质）。 |

### P-02【高】`渲染3` 的目录里有 **5 种不同模型内容**

| | |
|---|---|

### P-03【中】PBR 缓存签名**不含渲染逻辑**，改材质会静默覆盖旧底图

| | |
|---|---|
| **现象** | `product_base_spec()` 的文件名摘要 = `sha256({algorithm, scene_id, view, manifest_mtime_ns, camera, resolution})`。`scene_id` 含模型/CMF/预设库/相机，**但不含 `blender_pass.py` 的着色逻辑哈希、灯光配置版本**。 |
| **影响** | 改了材质节点或灯光后重新生成，**文件名不变 → 直接覆盖已有底图**。旧图被吃掉、无法回退、也无法区分"新旧两版"。本轮做 P1 纹理验证时，是**手动输出到 `outputs/_P1验证/`** 才避开覆盖的。 |
| **根因** | 签名维度漏了"渲染代码"这一项。 |
| **建议** | 新增 `renderer_signature`：纳入 `blender_pass.py` 内容 SHA-256、`cmf_presets.json` SHA-256、灯光配置/版本、Blender 大版本；同时进入 `scene_id`、每机位 digest 与场景报告。发布改为「写临时文件 → 校验 PNG 与签名 → 原子发布」，**旧路径保留**以便回退。 |
| **需要谁定** | 不需要，建议直接做（我下一步就做这个）。 |

## B. ★ 已撤回 / 已解决 —— **不要再追这些**

这几条我们反复过，其中两条是我判断错误造成的。列在这里是为了**防止下一轮又去排查它们**。

| # | 曾经的结论 | 现状 |
|---|---|---|
| B-1 | 「CMF 方案与 pass 不是同一个模型版本」（E0 的 B2） | ❌ **撤回**。`AI渲染1` 的 **32 个 `.3dm` 文件 SHA-256 全同**（`08ba3012e49f10b7bf78…`）。文件名在变（保存次数），内容一模一样。**"选定唯一权威 .3dm"这一步不需要。** |
| B-2 | 「方案分配的 4 个部位在 10 个机位全不可见」 | ❌ **撤回**。正确读取下，单机位可见 **325–392** 个、八面共 **744** 个部件，**4 个分配部位全都可见**（`物体.2491` 还是合计像素第 2 大）。 |
| B-3 | 「设计语言写法的改动落在背景 / 未分配部件上」 | ❌ **撤回**。front 的变亮像素 **83.1% 落在 `物体.019`（分配部位之一）**，背景只占 5.2%。 |
| B-4 | 「`objectid.png` 是 8 位、ID 被压成 10 个桶」 | ❌ **撤回**。文件**本来就是 16 位**（读 IHDR 第 25 字节 `bit_depth=16`）。看着像 8 位是 **PIL 读 16 位 RGBA 时静默降位**造成的。 |
| B-5 | 「B1：现有 PBR 底图不可追溯」 | ✅ **已解决**。按显式参数（`plastic_fine_matte` / `#3a4148` / `studio`）重生成，**`渲染3` 与 `渲染444` 各 8 机位完成，均 1 个 `scene_id`、`fresh` 8/8**。 |
| B-6 | 「抽样读 objectid 会漏细部件」 | ✅ **已修**。`visible_object_ids()` 改全像素 + numpy 连续数组；实测同图从 **26 → 63** 个可见 ID（旧抽样漏 59%）。 |
| B-7 | 「16 位解码精度没验证」 | ✅ **已完成（M0）**。`web/test_objectid_precision.py` 7 项全过；两条独立解码路径在真机 10/10 机位完全一致。 |
| B-8 | 「自检的清理任务表警告」 | ⚠️ **本次复现不到**。已知这类「通过但清理失败」多为**管道 SIGPIPE 打断收尾**；跑自检请重定向到文件、别接 `\| grep`。 |

**根因归总**：B-1/B-2/B-3/B-4 四条，**全部源于同一个错误 —— 用 PIL 读 16 位 `objectid.png`**。
详见 [`docs/更正记录-PIL位深误导导致的两处错误结论-20261010.md`](更正记录-PIL位深误导导致的两处错误结论-20261010.md)。
**正确做法：用 `scripts/objectid_mask.py::read_ids()`（项目本来就自带纯标准库 16 位解码器）。**

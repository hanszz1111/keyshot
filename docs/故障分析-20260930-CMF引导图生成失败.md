# 故障分析：多材质配色引导图生成失败（2026-09-30）

> **现象**：用户在界面上配置 CMF 方案后出图，**一整组机位全部失败**（10:53–10:57 共 10 条任务）。
> **定性**：Windows 端环境特有的缺陷，**Mac 端与本机自检都无法复现**。
> **状态**：已定位、已修复、已在真实链路上验证通过。

## 一、失败现象

任务库 `config/tasks.db` 里的原始记录：

| 任务 | 机位 | 错误 |
|---|---|---|
| #783 / #784 / #785 / #787 / #789 / #791 | `side_left` | 多材质配色参考生成失败：`cmf_guide.py` line 15, `from objectid_mask import read_ids` → **ModuleNotFoundError: No module named 'objectid_mask'** |
| #786 / #788 / #790 / #792 | `3q4_left` | 同系列主视图失败，未生成其他机位以避免外观不一致 |

**注意后四条的措辞**：它们其实**没有自己的错误** —— 是主视图失败后，
v3.13 的「候选系列」联动保护主动拒绝了后续机位（防止外观不一致）。
所以真正需要修的是**一处**，但它一次坏掉一整组。

## 二、根因

`scripts/cmf_guide.py` 第 15 行依赖同目录的 `objectid_mask`：

```python
from objectid_mask import read_ids
```

这种写法**要求脚本所在目录在 `sys.path` 里**。而本项目的 Web 服务在 Windows 上
**优先使用 ComfyUI 的嵌入式 Python**（`python_embeded\python.exe`）来跑子进程
（`server.py` 的 `Get-WebPython` 逻辑，这样才有 numpy/Pillow）。

嵌入式发行版带一个 **`python313._pth`** 文件。**`_pth` 模式下 Python 不会把脚本所在目录
放进 `sys.path`** —— 实测：

```
[A] ComfyUI 嵌入 Python
    sys.path[0] = 'F:\AI-Renderer\packs\ComfyUI_windows_portable\ComfyUI'   ← 工作目录，不是脚本目录
    结果：ModuleNotFoundError: No module named 'objectid_mask'

[B] 托管 Python（.workbuddy 下的独立解释器，不带 _pth）
    sys.path[0] = 脚本所在目录 scripts\
    结果：正常运行
```

**这就是「Mac 端测过、自检也过、生产却挂」的原因**：
两边的解释器**不是同一个**。`_pth` 只存在于嵌入发行版里。

## 三、修复

在 `scripts/cmf_guide.py` 里显式补上脚本目录（任何调用方式都生效）：

```python
import sys
sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))

from objectid_mask import read_ids  # noqa: E402
```

**同类隐患一并修**：`scripts/test_cmf_guide.py` 也 `from cmf_guide import make_guide`，
同样会在嵌入 Python 下失败，已加同样的 `sys.path` 处理。
（`web/test_cmf_guide.py` 原本就带了 sys.path 处理，无需改。）

**没有采用**的替代方案及理由：
- 调用侧设 `PYTHONPATH` —— `_pth` 模式下环境变量会被忽略，不可靠；
- 把 `read_ids` 内联进 `cmf_guide.py` —— 会造成两份 16 位 PNG 解码逻辑，埋更大的坑。

## 四、验证（两条独立证据）

| 验证 | 方法 | 结果 |
|---|---|---|
| 单元 | 用 **ComfyUI 嵌入 Python** 直接跑 `cmf_guide.py`（修复前报错、修复后成功） | ✅ `{"parts": 3, "width": 1232, "height": 752}` |
| 端到端 | 用**真实方案**（`AI渲染1.json` v5，4 个部件）+ 真实白模走完整链路 | ✅ 提交 HTTP 200、**引导图生成**（`_部件/AI渲染1/side_left/guides/9c77310722df9db1_cmf_guide.png`，117 KB）、出图完成（`qwen21_00129_.png`） |

端到端那一轮正是**复现用户失败场景**：同 SKU、同机位（`side_left`）、同触发条件
（`input_kind=clay` + `cmf_scheme`），修复前报错、修复后跑通。

## 五、排查中确认的两件正常行为（不是缺陷）

1. **方案校验拒绝伪造值**：第一次测试我用了假的 `fingerprint`/`version`，
   服务端直接返回「材质方案或源模型在任务建立后已改变」—— **这是对的**，
   说明「方案变了就拒绝旧任务」的防串味机制有效。
2. **主视图失败会阻断同系列其他机位** —— v3.13 的设计意图，本次正是它把
   1 个 bug 放大成 10 条失败记录。行为正确，但**报错信息可以更醒目**
   （现在 8 条失败任务的错误只写「主视图失败」，不指出真正原因）。

## 六、为什么之前没发现

- 本机自检 `web/selftest.py` 与 `scripts/test_cmf_guide.py` 都用**托管 Python** 跑 → 不带 `_pth`；
- Mac 端没有 Windows 嵌入 Python，更复现不了；
- `cmf_guide.py` 是 v3.14 才引入的（对方 `7bdec22`），本次是它**第一次在真实生产链路里
  被触发**（需要用户先配好 CMF 方案才会走这条路）—— 所以属于「第一次真跑才暴露」。

## 七、遗留建议（未做，供后续判断）

- **同类风险自查**：任何新增的 `scripts/*.py` 若 `import` 同目录模块，都应加
  `sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))`。
  建议写进 `CONTRIBUTING.md`，或加一条自检断言扫这个模式。
- **失败信息聚合**：一组任务因主视图失败被阻断时，建议在错误里附上主视图的**原始原因**，
  否则用户只看到「主视图失败」，还得再去翻一遍任务列表才知道真正原因。
- 本次未改动生成参数、任务顺序与产物格式。

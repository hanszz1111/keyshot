# ★★ 更正记录：两处结论被 `PIL` 的 16 位降位误导（2026-10-10）

> 本文撤回我在 2026-10-09 ~ 10-10 之间做出的**两处错误结论**。
> 两处**同一个根因**，值得单独留一份文档，避免以后重犯。

---

## 1. 根因（一句话）

**`PIL` 打开 16 位 RGBA 的 PNG 时，会静默降成 8 位**（`np.asarray(im)` 得到 `uint8`、`max=255`）。

而本项目的 `objectid.png` 存的是 `部件号 / 65535`、**文件本来就是 16 位**（读 PNG 头 IHDR 可证实：
`bit_depth = 16`）。经 PIL 降位后，`部件号 / 65535 × 255 = 部件号 / 257`，
于是 **2530 个部件被压成大约 10 个“桶值”**（0…10）。

我拿这些桶值当成了部件号，于是所有基于它的判断全错。

**判据与做法**：
```python
# ✗ 错的：静默降成 8 位
a = np.asarray(Image.open(p).convert("L"))        # 值 = id/257 的桶，不是 id

# ✓ 对的（本机已验证）：在 Blender 里读，float 像素 × 65535
img = bpy.data.images.load(p); img.colorspace_settings.name = "Non-Color"
buf = np.empty(w*h*4, dtype=np.float32); img.pixels.foreach_get(buf)
ids = np.rint(buf[0::4] * 65535.0).astype(np.int32)   # 还原真实部件号
```
也可以用 `scripts/inspect_3dm.py` 之外的方式读 IHDR 判断位深：
`bit_depth` 在 PNG 头第 25 字节。

> 另一条独立的、也让我误判的坑：**Blender 的 CWD 不是项目根**，
> 脚本里给 `bpy.data.images.load()` 传**相对路径会 `No such file or directory`**（表现为 `read_failed`）。
> 给 Blender 的路径一律写绝对路径。

## 2. 撤回的第一处：「CMF 方案与 pass 不是同一个模型版本」

| | 原文（已撤回） | 实测事实 |
|---|---|---|
| 说法 | 方案指向 `_30.3dm`，pass 记录 `_22/_23/_25/_26/_28` → 版本错配（E0 的 B2） | **32 个 `.3dm` 文件 SHA-256 全部相同**（`08ba3012e49f10b7bf78…`，也等于方案 `fingerprint`）。文件名在变，**内容一模一样** |
| 结论 | 需要用户「选定唯一权威 .3dm」 | **不需要选**。没有版本问题 |

这一处**与 PIL 无关**，是我把「文件名不同」当成了「内容不同」。**教训：比对文件是否同一份，必须比内容哈希，不能比文件名。**

## 4. 连带撤回：「设计语言写法的改动落在未分配材质的部分上」

这一处影响最大，因为它曾被用来**否定**那条提示词路线的价值。

| | 原文（已撤回） | 16 位正确读取后的实测 |
|---|---|---|
| front 变亮像素落点 | 「**88.1% 落在背景**」，其余落在**未分配材质**的部件上 | **83.1% 落在 `物体.019`（id 20，★ 正是方案分配的部位）**；背景仅 **5.2%**；`物体.2487`(1737) 0.8% |
| 3q4_left 变亮像素落点 | 「23.5% 落在背景」 | 背景 11.2%；**`物体.019`(20) 10.5% + `物体.2491`(1742) 10.2% 都是分配部位** |

**结论要改**：这条提示词写法**确实作用在方案指定的 CMF 部件上** —— 这比原先说的「模型在无约束对象上自由发挥」好得多。

**但有一条**原文**仍然成立**（因为它是从两张渲染图直接算的，没经过 objectid）：
- **跨视角变亮比例差异极大**：右侧 33.6% ／ 左前 3/4 14.2% ／ 正面 3.5% ／ **俯视 0.00%**
→ 「跨视角不一致」这条**站得住**；「改动落在未分配部件/背景上」这条**不成立**。

## 5. 现在站得住的结论（重述）

1. **`AI渲染1` 的 CMF 部位指派是可用的**：4 个分配部位在十个机位里都真实可见，且占比不小。
2. **但 `AI渲染1` 十机位合计有 747 个可见部件**，而方案只指派了 4 个 ——
   **其余 743 个部件目前没有任何材质指派**，会走主体材质。这仍是一个**待补**项，但性质是
   「覆盖不全」，**不是「指派到看不见的部件」**。
3. **设计语言型提示词的作用确实落在被指派的部件上**，方向是对的；
   **真正的问题是跨视角不一致**（0% ～ 33.6%），这才是要继续攻的点。
4. 我先前基于 PIL 做的**全部 objectid 归因**（含 E0 记录里「引导图 81.59% 是 `#F0F0F0`」那段推理）
   **都不可信**，应以 16 位重算为准。

---

## 6. 我给自己定的两条硬规矩

1. **凡是要读 `.png` 的部件号/位深，一律先确认位深，再选读取方式**；
   能用 Blender 那一套（已与生产同源）就别用 PIL 自己写一套。
   PIL 对 16 位 RGBA **没有任何提示地降位**，这是最危险的一类错误 —— **不报错、结果全错**。
2. **「文件不同」不等于「内容不同」；「内容相同」也不等于「同一份用在不同地方」** ——
   前者比哈希，后者比清单里记录的来源字段，两者都要做。

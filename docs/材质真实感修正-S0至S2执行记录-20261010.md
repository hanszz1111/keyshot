## 1. ★★ 重要更正：`AI渲染1` **没有**「模型版本不一致」问题

### 1.1 我上一轮说错了

`AI渲染1` 的 CMF 方案指向 `_30.3dm`，而各机位 `pass_manifest.json` 记录的是
`_22 / _23 / _25 / _26 / _28`。我在 `AI-RESULT-R4.md` 与 E0 记录里据此判定
**「方案与 pass 不是同一份模型版本」**，并把它列为阻断项 **B2**。

**这个判断是错的。** 本轮按 S0 要求做只读清点时实测：

**`AI渲染1` 的 32 个 `.3dm` 文件，SHA-256 全部相同** ——

```
方案 fingerprint          : 08ba3012e49f10b7bf7857a18288d31e51be1d4ebfa36dfe154ce53ea613c1c2
32 个文件的不同内容份数   : 1
  AI渲染1.3dm  AI渲染1_2.3dm  AI渲染1_3.3dm  …  AI渲染1_30.3dm  AI渲染1_31.3dm  AI渲染1_32.3dm
  → 全部 = 08ba3012e49f10b7bf78…（与方案指纹逐字符相同）
网格数 2530 ｜ 顶点 136201 ｜ 面 113373 ｜ 包围盒 0.0415 × 0.1113 × 0.0741 m
```

→ **文件名在变（`_22`…`_32` 是保存次数），内容一模一样。**
「方案与 pass 不同版本」这个前提不成立，**B2 应撤回**。

### 1.2 真正的病因：**方案把材质分配给了任何机位都看不见的部件**

用全像素扫描统计 `AI渲染1` 十个机位里 `objectid` 图**实际出现过**的部件号：

| 机位 | 该机位可见部件数 |
|---|---|
| front / 3q4_left / detail_keypad | 8–9 |
| back | 3 |
| top / bottom | 9 |
| side / side_left / 3q4_right / detail_window | 7–10 |

**十个机位合计只出现过 9 个部件**，而且就是最前面那 9 个：

| id | 部件名 |
|---|---|
| 1 | `物体` |
| 2 | `物体.001` |
| 3 | `物体.002` |
| 4 | `物体.003` |
| 5 | `物体.004` |
| 6 | `物体.005` |
| 7 | `物体.006` |
| 8 | `物体.007` |

而 CMF 方案分配的部位是 **id 20 / 1737 / 1742 / 2530**
（`物体.019`、`物体.2487`、`物体.2491`、以及那个乱码名）——
**一个都不在上面这 9 个里**。

**所以「分配部位在 10 个机位全不可见」的真实原因是：它们本来就不出现在任何标准机位的画面里**
（该模型有 2530 个网格，但只有最前面 9 个构成可见外壳，其余是内部/微小件）。
**不是版本错配。**

### 1.3 因此决策方向要改

原计划要求「由用户选定唯一的权威 `.3dm`」。**现在不需要选了 —— 只有一个内容。**
真正要做的是：**把 CMF 重新指派到实际可见的那 9 个部件上**。

这仍是用户的决定（哪个部件配什么材质），但问题的性质从
「找对文件」变成了「**在可见部件上重新配色**」，工作量和风险都小得多。

> 附带确认：`AI渲染1` 的源文件里**对象名本身带乱码**（`name_has_mojibake: true`，
> Rhino 导出时就坏了）。所以方案里那个 `锟叫筹拷--锟斤拷2` 是**忠实复制**，不是后处理引入的。

| S2 要求 | 落实 |

## 7. ★ 本轮我自己引入并修掉的一个死锁（值得记住）

把哈希逻辑抽成 `_hash_model_file()` 时，我给它加了 `with CMF_SCHEME_LOCK:` 保护缓存 ——
**但 `_cmf_model()` 在好几处是「已经持有 `CMF_SCHEME_LOCK` 的情况下」被调用的**
（`load_cmf_scheme()` 在 `save_cmf_scheme()` / `reset_cmf_scheme()` / 部件指派等入口里，
都是先 `with CMF_SCHEME_LOCK:` 再调用它）。

于是调用链变成：

```
with CMF_SCHEME_LOCK:          # 外层已持有
    load_cmf_scheme()
        _cmf_model()
            _hash_model_file()
                with CMF_SCHEME_LOCK:   # ← 同一线程再抢一把不可重入的 Lock → 死锁
```

`threading.Lock` **不可重入**，所以服务直接卡住；表现出来是
**自检的 HTTP 请求超时**（`TimeoutError: timed out`），而不是一条清晰的报错 ——
很容易被误判成「服务掉了」而去重启，白折腾。

**修法**：把 `CMF_SCHEME_LOCK = threading.Lock()` 改成 `threading.RLock()`（可重入）。
最小改动，且 `RLock` 是 `Lock` 的超集，其余用法不受影响。

**验证**：写了个 45 秒超时的探针，在 `with CMF_SCHEME_LOCK:` 里调 `load_cmf_scheme()` ——
改前会卡住，改后正常返回 `fingerprint=08ba3012e49f10b7`；随后 `web/selftest.py` **93/93、exit=0**。

**教训**：给一个**被内部函数间接调用**的工具函数加锁之前，先确认调用链上有没有人已经持有同一把锁。
「加锁保护缓存」在这种嵌套结构下很容易变成自锁。
